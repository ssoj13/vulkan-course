Instance знает обо всех GPU в машине. В ноутбуке их бывает два (встроенный и дискретный), в рабочей станции —
несколько, на CI-сервере может не быть ни одного, кроме программного растеризатора. Прежде чем работать с GPU, его
нужно выбрать, а чтобы выбрать — расспросить каждый: кто ты, что умеешь и где твои пределы. Об этом урок.

## Где мы на карте

Модуль «Устройства и очереди» начинается здесь. Позади — уровень instance: [загрузчик](lesson:loader-and-instance) и
[валидация](lesson:validation). Впереди — [семейства очередей](lesson:queue-families) и
[логическое устройство](lesson:logical-device), а оба они требуют уже выбранного GPU. Этот урок — мост от «Vulkan
вообще» к «вот этой конкретной видеокарте».

`GPU → драйвер → загрузчик → VkInstance → VkPhysicalDevice → (properties, features, limits) → VkDevice`

[VkPhysicalDevice](term:vk-physical-device) построен на двух вещах сразу: на [instance](term:vk-instance), через который
мы его видим, и на самом [GPU](term:gpu), который он описывает. Его частями являются [features](term:features),
[limits](term:limits) и [семейства очередей](term:queue-family). А [VkDevice](term:vk-device) из следующих уроков будет
построен на физическом устройстве и воспользуется его features.

## Физические устройства находят, а не создают

**`VkPhysicalDevice`** — хэндл одного GPU в том виде, в каком его видит instance. Вы его не создаёте и никогда не
уничтожаете: instance **перечисляет** существующие GPU, и хэндлы живут, пока живёт instance. Это третий способ получить
объект из [карты объектов](lesson:object-map) — не create, не allocate, а enumerate.

<Step file="03_physical_devices" region="enumerate" />

Внутри — классический для Vulkan запрос в два вызова: сначала узнать количество, потом заполнить массив. Обе привязки
делают оба вызова за нас. Пустой список — тоже ответ: значит, ни один драйвер не показал GPU.

## Три вопроса к каждому GPU

Сначала общая картина, потому что три слова ниже звучат похоже, а означают разное:

| Вопрос | Что это | Можно ли изменить |
| --- | --- | --- |
| **Кто ты?** — properties | неизменные факты: имя, тип, версия Vulkan, производитель | нет, только прочитать |
| **Что ты умеешь?** — features | необязательные возможности, каждая да или нет | да: включить при создании устройства |
| **Докуда можно?** — limits | числа, которые GPU гарантирует | нет: код обязан в них укладываться |

Из этого следует порядок работы: properties и limits мы только *читаем*, а features *читаем, чтобы потом попросить*.

### Кто ты? Properties

<Step file="03_physical_devices" region="properties" />

- **deviceType**: дискретный, встроенный, виртуальный, CPU (программная реализация) или другой.
- **apiVersion**: старшая версия Vulkan, которую драйвер поддерживает для этого GPU. Использовать можно *меньшую* из
  двух: этой и той `apiVersion`, что мы попросили у instance.
- **driverVersion**: каждый производитель кодирует её по-своему, поэтому печатаем как есть; `vulkaninfo` умеет её
  расшифровывать.
- **vendorID**: PCI-идентификатор производителя — `0x10DE` NVIDIA, `0x1002` AMD, `0x8086` Intel.

### Что ты умеешь, если попросят? Features

<Step file="03_physical_devices" region="features" />

**Features** — необязательные возможности: анизотропная фильтрация, геометрические шейдеры, dynamic rendering...
Поддерживаемая GPU возможность всё равно **выключена**, пока вы не включите её при создании логического устройства
([урок о логическом устройстве](lesson:logical-device)). Это снова принцип Vulkan «скажи всё заранее»: драйвер может
подготовиться ровно к тому, чем вы будете пользоваться.

Возможности, появившиеся в поздних версиях Vulkan, лежат в отдельных структурах (`VkPhysicalDeviceVulkan13Features`,
`VkPhysicalDeviceVulkan14Features`...). Чтобы их спросить, мы цепляем эти структуры к `VkPhysicalDeviceFeatures2` через
`pNext` — тот же приём с цепочкой, что и в [уроке о валидации](lesson:validation). Один вызов заполняет все структуры
цепочки. Есть тонкость: структуру более новой версии ядра можно спрашивать только у устройства, которое эту версию
поддерживает, поэтому структуру 1.4 код цепляет, лишь если `apiVersion` устройства не ниже 1.4.

<Aside type="tip" title="Аналогия из CG">
Features похожи на возможности узлов рендер-фермы. На узле *есть* GPU и 128 ГБ памяти, но задача получит их, только
если попросит при отправке. Просьба заранее позволяет ферме спланировать работу.
</Aside>

### Где твои пределы? Limits

<Step file="03_physical_devices" region="limits" />

**Limits** — числа, которые GPU гарантирует: максимальный размер 2D-изображения, сколько байт push constants, какое
выравнивание нужно смещениям в uniform-буферах. Изменить их нельзя, ваш код обязан их соблюдать; выход за предел —
ошибка, которую обычно ловит валидация. Отдельно стоит `timestampPeriod`: сколько наносекунд в одном тике GPU-таймера,
без него замеры времени на GPU не перевести в секунды.

## Реальный ответ

Вот что напечатал шаг 03 на машине, где делался курс:

```txt
GPU 0: NVIDIA GeForce RTX 3080 Ti
  type:       DISCRETE_GPU
  api:        1.4.351
  vendor id:  0x10de
  features:
    sampler_anisotropy (1.0): true
    dynamic_rendering  (1.3): true
    synchronization2   (1.3): true
    push_descriptor    (1.4): true
    maintenance5       (1.4): true
  limits:
    max_image_dimension2_d:           32768
    max_push_constants_size:          256 bytes
    min_uniform_buffer_offset_alignment: 64 bytes
    timestamp_period:                 1 ns/tick
```

Драйвер поддерживает Vulkan 1.4, instance просит 1.4 — значит, нам доступна 1.4. Все пять флагов выше на любом
устройстве 1.4 на самом деле гарантированы: спецификация делает их обязательными. Так что проверка нужна для более
старых устройств и для по-настоящему необязательных возможностей, которые встретятся в следующих уроках. Пометки
`(1.3)` и `(1.4)` показывают, из структуры какой версии взят каждый флаг.

## Выбираем один

<Step file="03_physical_devices" region="pick" />

Сначала отсеиваем GPU, которые нашу программу вообще не потянут: версия ниже 1.4 или нет dynamic rendering и
synchronization2. Порядок проверок важен — сперва версия, потом features 1.3, иначе мы спросили бы структуру,
которую старое устройство не понимает. Среди оставшихся предпочитаем вероятно самый быстрый: дискретную карту (своя
VRAM) встроенной (делит память с системой), затем виртуальную, затем программную. При равенстве очков остаётся
найденный первым. Настоящие приложения часто ещё и дают пользователю выбрать GPU самому.

## Что под капотом

- Каждый драйвер сообщает о своих GPU, а загрузчик сливает списки всех драйверов в один. Поэтому хэндл физического
  устройства — dispatchable: по нему загрузчик понимает, какому драйверу этот GPU принадлежит.
- Properties, features и limits читаются из драйвера — на GPU пока ничего не выполняется. GPU даже не «открыт»: это
  случится, только когда мы создадим логическое устройство.
