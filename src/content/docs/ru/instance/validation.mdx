В [уроке о том, зачем нужен Vulkan](lesson:why-vulkan) мы договорились: драйвер Vulkan не проверяет, правильно ли вы
пользуетесь API. Передали неверное значение — и получите падение, чёрный экран или, хуже всего, программу, которая
работает на вашем GPU и ломается на чужом. Вопрос этого урока: как вернуть проверки на время разработки и как сделать
так, чтобы их сообщения доходили до нашего кода.

## Место в курсе

Мы всё ещё на слое загрузчика и драйвера, на уровне instance, между программой и драйвером. В [предыдущем уроке](lesson:loader-and-instance) появились
загрузчик, слои и расширения; здесь мы впервые включаем и то и другое — один слой и одно расширение, — и видно, почему
это два разных механизма. С этого урока каждая следующая программа курса работает под присмотром валидации.

`наш вызов → загрузчик → слой валидации → драйвер`, а сообщения идут обратно: `слой валидации → debug messenger → наш callback`

Отношения понятий: [слой валидации](term:validation-layer) — это частный случай [слоя](term:layer).
[Debug messenger](term:debug-messenger) построен на [instance](term:vk-instance) и на [расширении](term:extension)
`VK_EXT_debug_utils`, а пользуется он слоем валидации как источником сообщений. Иначе говоря: слой *находит* ошибку,
расширение даёт *канал*, messenger — *приёмник* на нашей стороне.

## Слой валидации

`VK_LAYER_KHRONOS_validation` — явный слой из Vulkan SDK. Он встаёт между программой и драйвером и сверяет каждый вызов
с **правилами допустимого использования** (valid usage) из спецификации. Правил тысячи, и у каждого есть свой
идентификатор — **VUID**, например `VUID-vkDestroyInstance-instance-00629`. Нарушили правило — слой назовёт его и
процитирует спецификацию.

Это инструмент разработки: каждый вызов с ним становится заметно медленнее. В программу, которую получат пользователи,
его не включают.

<Aside type="tip" title="Аналогия из CG">
Валидация — как строгий lint сцены перед отправкой на ферму: проверяет пути к текстурам, имена, единицы. На ферме его
не гоняют на каждом кадре — он нужен, пока сцену собирают.
</Aside>

## Как до нас доходят сообщения: debug messenger

Слою нужно куда-то отправлять отчёты. Для этого есть **debug messenger** (`VkDebugUtilsMessengerEXT`): объект, который
на каждое сообщение вызывает нашу функцию. Он принадлежит расширению instance `VK_EXT_debug_utils`, так что это
расширение тоже нужно включить.

Обратите внимание, сколько здесь участников и какие списки они занимают при создании instance:

| Что | Чем является | Куда записывается |
| --- | --- | --- |
| `VK_LAYER_KHRONOS_validation` | слой | список слоёв (`ppEnabledLayerNames`) |
| `VK_EXT_debug_utils` | расширение instance | список расширений (`ppEnabledExtensionNames`) |
| `VkDebugUtilsMessengerEXT` | объект, дочерний для instance | создаётся после instance |

### 1. Проверяем, что слой есть

<Step file="02_validation" region="layers-available" />

Слои ставятся отдельно от драйвера, и на машине пользователя этого слоя может не оказаться. Если попросить
отсутствующий слой, создание instance завершится ошибкой `VK_ERROR_LAYER_NOT_PRESENT`, поэтому мы проверяем заранее и
выдаём понятную подсказку: «поставьте Vulkan SDK».

### 2. Callback

<Step file="02_validation" region="debug-callback" />

Слой вызывает эту функцию и передаёт **уровень важности** (severity: verbose, info, warning, error), **тип** (general — общее,
validation — нарушение правил, performance — совет по скорости) и текст сообщения. Приложение всегда должно возвращать
`false`: значение `true` зарезервировано для разработки самих слоёв. Слой вызывает функцию через C ABI Vulkan
(`VKAPI_CALL`), поэтому в Rust у неё соглашение о вызовах `extern "system"`, а в C++ из неё не должно вылететь ни одно
исключение: раскрутка стека через код слоя недопустима.

### 3. Что мы хотим слышать

<Step file="02_validation" region="messenger-info" />

Просим только предупреждения и ошибки. Сообщения info и verbose — это в основном загрузчик, рассказывающий о себе:
больше сотни строк за запуск, и в них утонет та единственная строка, ради которой всё затевалось.

доходят до callback и как при этом выглядит create info; в [полностраничной версии](lab:messenger-filter) просторнее.

### 4. Instance со слоем, потом messenger

<Step file="02_validation" region="create-with-validation" />

Здесь проблема курицы и яйца: messenger создаётся *из* instance — кто же тогда сообщит о проблемах внутри
`vkCreateInstance` и `vkDestroyInstance`? Ответ — цепочка `pNext` из [карты объектов](lesson:object-map): мы вешаем ту
же самую create info для messenger на create info instance, и слой пользуется ею ровно для этих двух вызовов. В Rust это
делает `.push(...)`, в C++ — `vk::StructureChain`.

<Step file="02_validation" region="create-messenger" />

А это уже постоянный messenger: он слушает всё, что происходит между созданием и уничтожением instance, то есть все
наши дальнейшие вызовы. В Rust функции расширения не входят в основную таблицу функций `ash::Instance` (это устройство самой
`ash`, а не загрузчика), поэтому `ash` подгружает их отдельной структурой `debug_utils::Instance`.

<Step file="02_validation" region="cleanup" />

Уничтожаем в обратном порядке: messenger принадлежит instance и должен умереть раньше него.

## Ломаем правило нарочно

<Aside type="tip" title="Попробуйте сами">
В Rust-программе закомментируйте строку с `destroy_debug_utils_messenger` (в C++ RAII-порядок уничтожения делает эту
ошибку невозможной — ещё один довод в пользу RAII). Запустите: когда instance уничтожается, а messenger ещё жив, слой
сообщит о `VUID-vkDestroyInstance-instance-00629` — все дочерние объекты instance должны быть уничтожены до него
самого. Этот идентификатор — ключ для поиска в спецификации.
</Aside>

Вот настоящий вывод этого эксперимента (сокращено: обычные строки перед ошибкой убраны, а те же две строки ошибки в реальном запуске напечатались ещё раз):

```txt
…
[ERROR][VALIDATION] vkDestroyInstance(): Object Tracking - For VkInstance 0x15d991071a0, VkDebugUtilsMessengerEXT 0x10000000001 has not been destroyed.
The Vulkan spec states: All child objects that were created with instance or with a VkPhysicalDevice retrieved from it, and that can be destroyed or freed, must have been destroyed or freed prior to destroying instance (https://docs.vulkan.org/spec/latest/chapters/initialization.html#VUID-vkDestroyInstance-instance-00629)
…
```

Читать его удобно с конца: **VUID** называет правило, «The Vulkan spec states» цитирует его, а первая строка говорит,
какие объекты его нарушили. Сообщение пришло к нам по всей цепочке из урока: слой заметил нарушение, `VK_EXT_debug_utils`
доставил его, messenger вызвал наш callback, тот напечатал `[ERROR][VALIDATION]`.

## Без кода: vkconfig

**Vulkan Configurator** (`vkconfig`) включает слой валидации для любой Vulkan-программы — в том числе для тех, что
писали не вы, — и выводит его сообщения в консоль или в файл. Удобно, чтобы проверить чужой инструмент или игру, и
чтобы проверить свою программу, не трогая её код.

## Что под капотом

- Слой валидации — одна большая библиотека, перехватывающая все точки входа Vulkan. Он отслеживает состояние каждого
  объекта (какие существуют, какие сейчас заняты GPU, в каком layout находится каждое изображение) — потому-то он так
  дорог по времени и памяти.
- Кроме базовых проверок у него есть необязательные режимы: **synchronization validation** (ищет пропущенные барьеры),
  **GPU-assisted validation** (встраивает проверки в шейдеры, чтобы ловить выход за границы) и **best practices**
  (советы по производительности). Включаются они в vkconfig или из кода через `VkLayerSettingsCreateInfoEXT`
  (`VK_EXT_layer_settings`; старый `VkValidationFeaturesEXT` объявлен устаревшим).
