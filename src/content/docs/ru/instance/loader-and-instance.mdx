Наша первая программа создаёт ровно один объект — `VkInstance`. Вопрос урока: что это за объект, с кем он нас
соединяет, и почему уже на этом шаге приходится говорить о слоях и расширениях. Чтобы ответить, сначала знакомимся с
программой, к которой instance подключается: с **загрузчиком**.

## Где мы на карте

Мы на самом нижнем программном этаже Vulkan, сразу над драйвером. В [прошлом уроке](lesson:toolchain) мы поставили
драйвер и SDK; на [карте объектов](lesson:object-map) instance стоял в самом корне дерева. Сейчас мы этот корень
создадим, и всё дальнейшее — валидация, выбор GPU, логическое устройство — растёт из него.

`GPU → драйвер (ICD) → загрузчик → [слои] → VkInstance → VkPhysicalDevice → VkDevice → VkQueue`

Как понятия опираются друг на друга: [загрузчик](term:loader) построен на [драйвере](term:driver) — без драйвера ему
некуда передавать вызовы. [Слой](term:layer) построен на загрузчике — это загрузчик вставляет его в цепочку вызовов.
[VkInstance](term:vk-instance) построен на загрузчике и пользуется слоями и [расширениями](term:extension): при
создании мы говорим, какие из них включить.

## Загрузчик: коммутатор между программой и драйверами

Программа никогда не разговаривает с драйвером GPU напрямую. Она разговаривает с **загрузчиком Vulkan**
(`vulkan-1.dll`) — небольшой библиотекой от Khronos, которая ставится с каждым драйвером. При старте загрузчик:

1. находит установленные **драйверы** (по одному на производителя GPU — в машине могут одновременно жить NVIDIA и
   Intel);
2. находит установленные **слои** — библиотеки, которые могут встать между программой и драйвером;
3. проводит каждый наш вызов через включённые слои к нужному драйверу.

```
ваша программа -> загрузчик -> [слой] -> [слой] -> драйвер (ICD) -> GPU
```

Представьте коммутационную панель в студии: программа подключается в одно гнездо, а загрузчик сам решает, через какие
приборы (слои) пройдёт сигнал и на какой выход (драйвер) он попадёт. Драйвер в терминах загрузчика называется **ICD**
(Installable Client Driver) — «устанавливаемый драйвер».

## Слои: явные и неявные

**Слой** видит каждый вызов, который через него проходит. Валидация, захват кадров (RenderDoc), оверлеи (Steam,
программы записи экрана), профайлеры — всё это слои. Различаются они тем, кто их включает:

- **Явные (explicit) слои** загружаются, только если приложение (или `vkconfig`) попросит их по имени. Слой валидации —
  явный.
- **Неявные (implicit) слои** попадают в *каждую* Vulkan-программу автоматически, потому что их зарегистрировал
  какой-то установленный софт.

<Aside type="caution" title="Живой пример с машины, на которой делался курс">
На Windows загрузчик ищет слои в реестре: `SOFTWARE\Khronos\Vulkan\ImplicitLayers` и `...\ExplicitLayers` — и в
`HKEY_LOCAL_MACHINE`, и в `HKEY_CURRENT_USER`, — а также в ключах, которые драйвер GPU пишет в запись своего
видеоадаптера. На машине разработки неявных слоёв оказалось **восемь**: шесть зарегистрировал установленный софт
(RenderDoc, Bandicam, оверлей Epic Games, оверлей Steam, Fossilize из Steam, Nsight Systems) и два — сам драйвер
NVIDIA (`VK_LAYER_NV_optimus`, `VK_LAYER_NV_present`). Все восемь загружаются в каждую Vulkan-программу на этом
компьютере, включая нашу, а слой Bandicam ещё и печатает предупреждение, что его версия API старше нашей. К нашему коду
это предупреждение отношения не имеет. В JSON-манифесте каждого неявного слоя указана переменная окружения, которая его
отключает (например, `DISABLE_LAYER_NV_OPTIMUS_1`) — на случай, если слой когда-нибудь начнёт мешать.
</Aside>

## Слой, расширение, feature: три разных добавки

Эти три слова в Vulkan встречаются постоянно, и их легко смешать. Они отвечают на разные вопросы:

| Понятие | Что это | Где включается |
| --- | --- | --- |
| **слой** (layer) | библиотека, которая перехватывает вызовы на пути к драйверу | при создании instance (или через `vkconfig`) |
| **расширение** (extension) | дополнительный именованный кусок API: новые функции, структуры, флаги | при создании instance или device |
| **feature** | необязательная возможность самого GPU | при создании логического устройства |

Слой в первую очередь *наблюдает* за вызовами (хотя может и сам принести расширения). Расширение *добавляет* API.
Feature *включает* то, что GPU умеет, но держит выключенным, пока не попросят. Расширения, в свою очередь, бывают двух
уровней: **расширения instance** расширяют загрузчик и instance (поверхности окон, отладочные сообщения), а
**расширения устройства** — то, что умеет GPU (до них дойдём в [уроке о логическом устройстве](lesson:logical-device)).
Features разберём в [уроке о физических устройствах](lesson:physical-devices).

## Instance

**`VkInstance`** — это подключение вашей программы к загрузчику. По сути, одно заявление: «я такое-то приложение,
пишу под Vulkan 1.4, и мне нужны вот эти слои и вот эти расширения». Instance — корень дерева объектов: всё остальное
создаётся из него, напрямую или через посредников.

Пройдём по шагу 01.

### 1. Загружаем загрузчик

<Step file="01_instance" region="load-loader" />

Пока instance нет, доступна лишь горстка **глобальных** функций: создать instance, перечислить расширения и слои
instance, спросить версию загрузчика. Ровно эти функции и держат `Entry` в Rust и `vk::raii::Context` в C++. Обе
привязки открывают `vulkan-1.dll` и ищут в ней функции по имени. Версию спрашиваем сразу: она показывает, до какой
версии Vulkan дорос *загрузчик* (что умеет конкретный GPU, мы узнаем позже).

### 2. Говорим, кто мы

<Step file="01_instance" region="app-info" />

Вся эта структура — необязательные метаданные, и только одно поле действительно на что-то влияет: `apiVersion`,
**старшая** версия Vulkan, под которую написана программа. Имена приложения и движка драйвер тоже может читать —
чтобы включить исправления для конкретной игры.

### 3. Смотрим, что есть

<Step file="01_instance" region="list-extensions" />

**Расширение** — необязательная функциональность API с именем вроде `VK_KHR_surface`. Список, который мы печатаем, —
это расширения самой реализации Vulkan и неявных слоёв (а не всех установленных слоёв вообще). Главное правило:
расширение нужно **включить при создании**, а то, что оно есть в списке, лишь говорит, что его *можно* включить.
Список — это меню, а не заказ.

### 4. Создаём instance

<Step file="01_instance" region="create-instance" />

Здесь впервые появляется шаблон из [карты объектов](lesson:object-map): заполняем структуру `*CreateInfo`, передаём её
в функцию `create`, получаем хэндл. Поле `sType` привязки заполняют сами. Слоёв и расширений мы пока не просим —
списки пустые.

### 5. Уборка

<Step file="01_instance" region="cleanup" />

У Vulkan нет сборщика мусора: всё, что создали, уничтожаем сами, сначала детей, потом родителей. В Rust это явный
вызов `destroy_instance`; в C++ RAII делает то же самое в деструкторах, в обратном порядке объявления.

## Что под капотом

- Загрузчик — открытый код ([KhronosGroup/Vulkan-Loader](https://github.com/KhronosGroup/Vulkan-Loader)). На Windows
  современные драйверы регистрируют свой JSON-манифест через собственные ключи реестра видеоадаптера; старый ключ
  `HKEY_LOCAL_MACHINE\SOFTWARE\Khronos\Vulkan\Drivers` загрузчик тоже читает (на машине разработки его не было вовсе).
- Каждый вызов уровня instance проходит через **trampoline**-код загрузчика, затем через каждый включённый слой и
  наконец попадает в **terminator** загрузчика, который рассылает его всем драйверам. Слои выстроены в цепочку:
  каждый вызывает следующий.
- `vkCreateInstance` сам по себе GPU не трогает. Он лишь поднимает загрузчик, слои и состояние instance в каждом
  драйвере.
