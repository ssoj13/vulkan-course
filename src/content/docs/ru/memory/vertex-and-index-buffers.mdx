Первый треугольник хранил свои три угла константами в шейдере. У настоящего меша тысячи вершин, и приходят они из
файла, а не из исходника шейдера. Как GPU находит вершины в буфере, откуда он знает, где внутри одной вершины лежит
каждый атрибут, как индексный буфер позволяет хранить один раз вершину, общую для шести треугольников, и во что
обходится самое простое размещение — в памяти, которую CPU может отобразить?

## Место в курсе

Второй урок модуля «Ресурсы и память». Слой API, плюс взгляд на блок железа, который читает вершины.
[Кучи и типы памяти](lesson:memory-types) дали нам буферы и память под ними; здесь два буфера получают первую
настоящую работу. Цепочка от байтов до входа шейдера:

`struct Vertex → буфер вершин (VERTEX_BUFFER) → привязка входа вершин (слот, stride, частота) → атрибут входа вершин (location, формат, смещение) → [[vk::location]] в Slang → вершинный шейдер`

а рядом с ней путь индексов: `индексный буфер (UINT16) → vkCmdDrawIndexed → какую вершину берёт каждый угол`.

[Буфер вершин](term:vertex-buffer) — это [VkBuffer](term:vk-buffer) с usage `VERTEX_BUFFER`;
[привязка входа вершин](term:vertex-input-binding) — слот [пайплайна](term:vk-pipeline), к которому привязывается буфер
вершин; [атрибут входа вершин](term:vertex-input-attribute) — один вход [шейдера](term:shader), который читается из
привязки по смещению; [индексный буфер](term:index-buffer) — буфер номеров вершин, по которому проходит отрисовка.
[Урок о графическом пайплайне](lesson:graphics-pipeline) оставил стадию входа вершин пустой; этот урок её заполняет.

## Точки, вершины и индексы

Пользователи Houdini эту модель уже знают, только под другими именами. В Houdini есть **точки** (позиции и атрибуты
точек) и **примитивы**, которые ссылаются на точки через свои **вершины**. У куба 8 точек и 24 вершины: каждую угловую
точку делят три грани.

Vulkan делит данные по той же идее, но слова сдвинуты на одну ступеньку:

| Houdini | Vulkan | Где хранится |
|---|---|---|
| точка (позиция, `Cd`, `N`, `uv` как атрибуты точки) | **вершина**: один элемент буфера вершин | буфер вершин |
| вершина (ссылка примитива на точку) | **индекс**: число в индексном буфере | индексный буфер |
| примитив (полигон) | примитив топологии: здесь каждые 3 индекса — 1 треугольник | следует из `TRIANGLE_LIST` |

То есть «вершина» Vulkan ближе к точке Houdini, а вершине Houdini соответствует индекс. И здесь аналогия ломается:
вершина Houdini может нести собственные атрибуты (UV на вершинах, нормали на вершинах для жёстких рёбер), а индекс
Vulkan не несёт ничего, кроме числа. Поэтому угол, у которого на двух гранях разные нормали, или шов UV требуют **двух
вершин** в буфере; экспортёры разделяют такие вершины (vertex splitting), когда пишут меш для real-time.

Шаг 14 рисует шестиугольник: 7 вершин (центр и шесть углов) и 6 треугольников, каждый — `(центр, угол i, угол i+1)`.
Без индексного буфера понадобилось бы 18 вершин; с ним — 7 вершин и 18 маленьких индексов.

## 1. Одна вершина в памяти

Два float позиции и три float цвета — 20 байт без выравнивающих пропусков. Раскладка структуры — договор ещё с двумя
местами: vertex input пайплайна повторит её смещения (0 и 8) и размер (stride, 20), а шейдер объявит те же два входа.
`repr(C)` в Rust и standard-layout структура в C++ закрепляют порядок полей, а проверка размера в обоих языках ловит
изменение, которое иначе тихо сломало бы договор.

## 2. Меш

<Step file="14_vertex_buffer" region="mesh" />

Две детали. Координаты x умножены на 600/800: clip space растянут на окно 800x600, и без поправки правильный

## 3. Сторона шейдера: location

<Snippet src="shaders/mesh.slang" />

`[[vk::location(0)]]` и `[[vk::location(1)]]` превращаются в SPIR-V в декорации `Location` на входах вершинного
шейдера. Семантические имена после двоеточия, `POSITION` и `COLOR`, для Vulkan ничего не значат: это наследство HLSL,
а пайплайн сопоставляет входы только по **location**. В отличие от `triangle.slang`, вершинный шейдер больше вообще не
смотрит на номер вершины: входы приходят к нему уже выбранными из памяти.

## 4. Привязки и атрибуты

Пайплайн описывает раскладку вершины двумя списками:

<Step file="14_vertex_buffer" region="vertex-input" />

```text
Vertex input: binding 0, stride 20 bytes, per vertex
  location 0: R32G32_SFLOAT at offset 0
  location 1: R32G32B32_SFLOAT at offset 8
```

[Привязка](term:vertex-input-binding) — это **слот** для буфера: его номер, **stride** (сколько байт от одной вершины
до следующей) и **частота** (input rate: шаг на каждую вершину или, для инстансинга, на каждый экземпляр).
[Атрибут](term:vertex-input-attribute) — это **один вход шейдера**: какой location он питает, из какой привязки читает,
в каком формате лежат данные (`R32G32_SFLOAT` — два 32-битных float, `float2` в Slang) и на каком смещении внутри
вершины. Адрес атрибута спецификация записывает одной строкой арифметики (здесь упрощённо, для частоты «на вершину»):

```c
attribAddress = bufferBindingAddress + vertexIndex * stride + attribDesc.offset;
```

где `bufferBindingAddress` — буфер, привязанный к этому слоту, плюс смещение привязки. Иерархия такая:
`привязка (где лежат байты) → атрибуты (как их читать)`, и она допускает разные раскладки при одном и том же шейдере:
всё **вперемешку** (interleaved) в одной привязке, как здесь, или каждый атрибут в своей привязке (позиции в одном
буфере, цвета в другом) — это помогает, когда проходу только с глубиной нужны одни позиции. Этот GPU допускает 32
привязки и 32 атрибута, stride до 2048 байт и смещение атрибута до 2047 (`maxVertexInputBindings`,
`maxVertexInputAttributes`, `maxVertexInputBindingStride`, `maxVertexInputAttributeOffset`).

Правила, которые связывают три места вместе, записаны в valid usage спецификации:

- каждый атрибут называет существующую привязку (`VUID-VkPipelineVertexInputStateCreateInfo-binding-00615`);
- у каждого входа вершинного шейдера с location есть атрибут с тем же location
  (`VUID-VkGraphicsPipelineCreateInfo-Input-07904`, если только это не смягчает одна из двух более новых возможностей);
- числовой тип входа шейдера совпадает с форматом атрибута (`VUID-VkGraphicsPipelineCreateInfo-Input-08733`):
  вход float питается из формата с плавающей точкой, целочисленный — из целочисленного.

## Почему это размещение простое, а не быстрое

Тип памяти 3 — это **системная память**. CPU пишет в неё один раз, а GPU читает её при **каждой отрисовке**, через
PCIe: буфер вершин при привязке никуда не копируется, выборка вершин читает привязанную память там, где она лежит.
Вспомните цифры из урока [Что такое GPU](lesson:gpu#своя-память): около 912 ГБ/с из VRAM, около 32 ГБ/с номинально по
PCIe 4.0 x16, и каждая выборка из системной памяти ещё и ждёт поездки через контроллер памяти CPU и обратно.

Заметно ли это? Для шестиугольника — нет. Три двухсекундных release-запуска шага 14 на Rust (вершины в системной
памяти) дали 2903, 2914 и 2999 fps; такие же запуски шага 15 (вершины в VRAM, следующий урок) — 2907, 2915 и 2936 fps.
176 байт помещаются в уголок кэшей GPU, а время кадра занято всем остальным. Цена растёт вместе с объёмом данных,
которые каждый кадр пересекают шину: меш на 64 МиБ пришлось бы гнать по шине при каждой отрисовке, а копирование 64 МиБ
по той же шине шаг 15 измерил в 5–7 мс — треть кадра при 60 fps уходит на трафик по шине, ещё до всякого шейдинга. Это
оценка по нашему копированию, а не замер отрисовки; интерактив [Где живут данные](lab:memory-path) ставит такие числа
рядом.

Значит, системная память — правильный дом для данных, которые CPU переписывает каждый кадр, а GPU читает один раз (и
даже у них есть дом получше, куча BAR, о ней в следующем уроке), и неправильный дом для меша, который рисуют каждый
кадр минутами. Как перенести его в `DEVICE_LOCAL`-память, которую CPU обычно отобразить не может, — тема урока
[Загрузка через staging](lesson:staging-uploads).

## 6. Привязка и отрисовка

<Step file="14_vertex_buffer" region="bind-and-draw" />

Две привязки и одна отрисовка, записанные внутри dynamic rendering из шага 09:

- `vkCmdBindVertexBuffers(cmd, firstBinding 0, [buffer], [offset 0])` ставит буфер вершин в слот 0. У буфера должен
  быть usage `VERTEX_BUFFER` (`VUID-vkCmdBindVertexBuffers-pBuffers-00627`);
- `vkCmdBindIndexBuffer(cmd, buffer, offset 0, UINT16)` — индексный буфер и размер одного индекса. Ему нужен usage
  `INDEX_BUFFER` (`VUID-vkCmdBindIndexBuffer-buffer-08784`), а смещение плюс адрес буфера в памяти должно быть кратно
  размеру индекса (`VUID-vkCmdBindIndexBuffer-offset-08783`): при `UINT16` смещение кратно 2, при `UINT32` — 4.
  Выравнивание 4, которое индексный буфер сообщил в шаге 13, следует из usage `INDEX_BUFFER`, а не из типа индекса,
  так что буфер, привязанный с этим выравниванием, удовлетворяет обоим правилам;
- `vkCmdDrawIndexed(cmd, indexCount 18, instanceCount 1, firstIndex 0, vertexOffset 0, firstInstance 0)`. Для каждого
  из 18 индексов номер вершины равен `index + vertexOffset`; ненулевой `vertexOffset` позволяет нескольким мешам делить
  один буфер вершин, а их индексам по-прежнему начинаться с 0.

**Типы индексов.** `UINT16` покрывает 65 536 вершин по 2 байта на индекс, `UINT32` — всё остальное по 4. В Vulkan 1.4
есть ещё `UINT8` (возможность `indexTypeUint8`, на этом GPU поддерживается) для крошечных мешей. Берите самый
маленький, который подходит: байты индексов тоже читаются при каждой отрисовке.

**Общая вершина не всегда шейдится один раз.** Спецификация такое переиспользование разрешает, но не обещает: «the
implementation may reuse the results of vertex shading if it can statically determine that the vertex shader
invocations will produce identical results» и «it is implementation-dependent when and if results of vertex shading are
reused». GPU держат маленький кэш недавно обработанных вершин, и поэтому оптимизаторы мешей переставляют индексы ради
локальности.

## Что под капотом

- **Выборка вершин** (vertex fetch) — первое, что делает отрисовка. Смотря по GPU, это либо блок с фиксированной
  функцией, либо инструкции загрузки, которые драйвер ставит в начало вершинного шейдера (AMD описывает такой «fetch
  shader» для своего поколения GCN). В любом случае описания атрибутов компилируются в пайплайн: форматы, смещения и
  stride известны при его сборке, и это одна из причин, почему vertex input — часть пайплайна.
- **Чтение из системной памяти** уходит с GPU запросами чтения PCIe, проходит через корневой комплекс процессора к
  его контроллеру памяти и возвращается обратно. По шине чтение медленнее записи, потому что каждое ждёт ответа; GPU
  прячет часть задержки, держа много запросов в полёте и кэшируя прочитанное в своём L2.
- **Индексный буфер** читает тот же фронтенд до выборки вершин: он превращает индексы в адреса вершин по формуле выше и
  сверяется со своим маленьким кэшем обработанных вершин, прежде чем запускать новую работу вершинного шейдера.
