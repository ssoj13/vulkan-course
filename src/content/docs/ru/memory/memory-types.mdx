До сих пор у каждого байта, который трогал GPU, был готовый хозяин: изображения swapchain пришли со своей памятью, а
три угла треугольника жили константами прямо в шейдере. Дальше данные наши: вершины, индексы, потом uniform-данные и
текстуры. Где лежат эти байты, кто решает, где им лежать, и как программа выбирает подходящую память из списка,
который сообщает GPU?

## Место в курсе

Первый урок модуля «Ресурсы и память». Он проходит сквозь все слои курса сразу: железо (VRAM, системная память и шина
PCIe между ними), то, что драйвер об этом железе сообщает, и объекты API, которые программа строит поверх. Лестница
железа знакома по первому модулю: `память CPU → шина PCIe → VRAM`. На ней стоят две цепочки, которые несут весь модуль:

`VRAM / системная память → куча памяти → тип памяти (флаги свойств) → VkDeviceMemory → VkBuffer, привязанный по смещению`

`vkCreateBuffer → требования к памяти (size, alignment, memoryTypeBits) → правило выбора типа → vkAllocateMemory → vkBindBufferMemory → vkMapMemory`

[Куча памяти](term:memory-heap) — это физический запас памяти; [тип памяти](term:memory-type) — один из способов
пользоваться кучей, описанный флагами свойств вроде [DEVICE_LOCAL](term:device-local) и
[HOST_VISIBLE](term:host-visible); [VkDeviceMemory](term:vk-device-memory) — выделение из одного типа;
[VkBuffer](term:vk-buffer) привязывается к нему, после того как драйвер назвал [требования к памяти](term:memory-requirements)
буфера, а среди них — [memoryTypeBits](term:memory-type-bits). В [уроке о барьерах](lesson:barriers-and-layouts#1-offscreen-изображение)
мы уже выделяли память изображению по формуле «первый тип `DEVICE_LOCAL`, который принимает изображение»; здесь эта
формула получает объяснение. Следующие уроки стоят на этом: [буферы вершин и индексов](lesson:vertex-and-index-buffers),
[загрузка через staging](lesson:staging-uploads) и [аллокаторы](lesson:allocators).

## Буфер только описывает данные

В Nuke нода с подписью «1920x1080, half float, RGBA» — ещё не картинка. Пиксели лежат где-то в кэше кадров, а нода
лишь указывает на них. Vulkan делит буфер так же, на два объекта:

- [VkBuffer](term:vk-buffer) — описание: размер и **флаги usage** (данные вершин, индексы, uniform, источник или
  приёмник копирования...). `vkCreateBuffer` не выделяет памяти под содержимое;
- [VkDeviceMemory](term:vk-device-memory) — хранилище: блок байтов одного типа памяти, его создаёт `vkAllocateMemory`.

`vkBindBufferMemory(buffer, memory, offset)` связывает их, один раз и навсегда: с этого момента байты буфера — это
диапазон `[offset, offset + size)` того блока. Почему не один вызов на всё, как `glBufferData` в OpenGL? Потому что
эти два решения принимают разные стороны. Только драйвер знает, что нужно от памяти буферу с таким usage; только
программа знает, как будут использоваться данные, сколько будет буферов и какие из них могут жить в одном блоке.
Разделение даёт драйверу назвать ограничения, а программе — выбрать, и позволяет тысячам буферов поселиться в
нескольких блоках. [Урок об аллокаторах](lesson:allocators) покажет, что без этого не обойтись.

## Кучи: физические запасы памяти

`vkGetPhysicalDeviceMemoryProperties` возвращает два списка. Первый — **кучи**: у каждой размер и флаг, device-local
ли она. Шаг 13 печатает их для GPU курса:

```text
Memory heaps: 3
  heap 0: 12673089536 bytes = 12086.0 MiB, DEVICE_LOCAL
  heap 1: 34315264000 bytes = 32725.6 MiB, (none)
  heap 2: 224395264 bytes = 214.0 MiB, DEVICE_LOCAL
```

- **Куча 0** — VRAM видеокарты: те самые 12 ГБ GDDR6X из урока [Что такое GPU](lesson:gpu#своя-память), чуть меньше
  12 ГиБ.
- **Куча 1** — системная память, которой может пользоваться GPU. Не вся: Windows сообщает на этой машине 68630528000
  байт RAM, и куча — ровно половина. GPU достаёт до неё через PCIe.
- **Куча 2** — снова VRAM, но особые 214 МиБ: та её часть, к которой CPU может обращаться через окно **BAR** на шине
  PCIe.

Так ступеньки железа получают имена: куча 1 — память CPU, куча 0 — VRAM, а куча 2 — кусок VRAM, видимый с другой
стороны шины.

Куча — это запас, а не обещание. Её размер — верхняя граница: той же памятью пользуются операционная система, драйвер
и другие программы. Разницу видно в `vulkaninfo`, потому что он включает `VK_EXT_memory_budget` (запуск 2026-10-11,
сокращено):

```text
memoryHeaps[0]:
	size   = 12673089536 (0x2f3600000) (11.80 GiB)
	budget = 11867783168 (0x2c3600000) (11.05 GiB)
memoryHeaps[2]:
	size   = 224395264 (0x0d600000) (214.00 MiB)
	budget = 223043584 (0x0d4b6000) (212.71 MiB)
	usage  = 1351680 (0x0014a000) (1.29 MiB)
```

Бюджет — это «сколько этот процесс может занять прямо сейчас, не создавая проблем», и меняется он прямо во время
работы. Программы курса проверяют только размер кучи и честно говорят об этом в своих сообщениях об ошибках.

## Типы: как пользоваться кучей

Второй список — **типы памяти**. Каждый тип указывает на одну кучу и несёт **флаги свойств**; на одну кучу могут
указывать несколько типов. Та же машина:

```text
Memory types: 6
  type 0: heap 1, (none)
  type 1: heap 0, DEVICE_LOCAL
  type 2: heap 0, DEVICE_LOCAL
  type 3: heap 1, HOST_VISIBLE | HOST_COHERENT
  type 4: heap 1, HOST_VISIBLE | HOST_COHERENT | HOST_CACHED
  type 5: heap 2, DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT
```

Словарь флагов маленький, и флаги складываются в лестницу. Со стороны GPU у неё одна ступенька, со стороны CPU — три,
и каждая стоит на предыдущей:

| Флаг | Что говорит спецификация | Что это значит на практике |
|---|---|---|
| [DEVICE_LOCAL](term:device-local) | «the most efficient for device access»; стоит ровно тогда, когда куча device-local | у дискретного GPU это VRAM: там, где GPU хочет видеть свои данные |
| [HOST_VISIBLE](term:host-visible) | «can be mapped for host access using `vkMapMemory`» | CPU может получить указатель внутрь |
| [HOST_COHERENT](term:host-coherent) | команды flush и invalidate «are not needed to manage availability and visibility on the host» | не нужен flush после записи CPU и invalidate перед чтением |
| [HOST_CACHED](term:host-cached) | «cached on the host»; «uncached memory is always host coherent» | **чтение** CPU идёт через его кэши: читать обратно быстро |
| [LAZILY_ALLOCATED](term:lazily-allocated) | «only allows device access»; физическая память может выделяться лениво | временные аттачменты на тайловых GPU; здесь такого типа нет |

Последняя строка стоит отдельной фразы. Ленивый тип нужен изображениям с usage `TRANSIENT_ATTACHMENT`: MSAA-аттачменту
или аттачменту глубины, который живёт только внутри прохода рендеринга на тайловом GPU (это материал модуля 10).
Буферам спецификация запрещает его прямым текстом: «lazily allocated memory is disallowed for buffers in all cases».
Есть и ещё несколько флагов (`PROTECTED` для защищённого контента, два флага AMD и один NVIDIA), но на GPU курса их
нет.

Теперь прочитаем шесть типов, держа флаги в голове:

- **тип 0** — системная память без `HOST_VISIBLE`: GPU ей пользоваться может, а CPU отобразить её не может. Нарочно
  его выбирают редко;
- **типы 1 и 2** — VRAM: два типа с одинаковыми флагами на одной куче. Зачем их два — в
  [разделе ниже](#memorytypebits--59-и-пропавший-тип-2);
- **тип 3** — системная память, которую CPU может отобразить, когерентная и *некэшируемая*. На x86 такая память обычно
  write-combined: записи CPU копятся и уходят по шине пачками, а чтение медленное. Естественный дом
  [staging-буфера](term:staging-buffer);
- **тип 4** — та же RAM, но ещё и `HOST_CACHED`: тип для данных, которые пишет GPU, а читает обратно CPU;
- **тип 5** — VRAM, которую CPU может отобразить: [окно BAR](term:bar). Записи CPU идут по PCIe прямо в видеопамять.

## Шаг 13: спрашиваем драйвер

У шага 13 нет окна. Он создаёт устройство, как шаг 05, а дальше задаёт только вопросы о памяти, по порядку: какая
память есть, какие лимиты действуют, что нужно разным буферам, какой тип взять для каждого вида данных и, наконец,
весь ручной путь для одного буфера.

### 1. Кучи и типы

Два цикла по двум массивам `VkPhysicalDeviceMemoryProperties`. Имена флагов печатаются из таблицы, чтобы оба языка

### 2. Лимиты, важные для памяти

<Step file="13_memory_types" region="memory-limits" />

```text
Limits: maxMemoryAllocationCount 4294967295, minMemoryMapAlignment 64, nonCoherentAtomSize 64, bufferImageGranularity 1024
```

- `maxMemoryAllocationCount` — сколько объектов `VkDeviceMemory` может существовать одновременно. Этот драйвер сообщает
  4294967295, наибольшее 32-битное число. Спецификация гарантирует только 4096, и именно на это число рассчитывает
  переносимая программа: если у каждого из 10 000 буферов своё выделение, программа сломается на драйвере, который
  сообщает минимум. Почему так не стоит делать даже при огромном лимите, измеряет [урок об аллокаторах](lesson:allocators);
- `minMemoryMapAlignment` — выравнивание отображённого выделения в адресном пространстве CPU. Указатель, который
  вернул `vkMapMemory`, за вычетом переданного ему `offset` здесь всегда кратен 64; значит, отображение со смещения 0
  начинается с адреса, выровненного на 64 байта;
- `nonCoherentAtomSize` — гранулярность flush и invalidate для *некогерентной* памяти. Все `HOST_VISIBLE`-типы этого GPU
  заодно и `HOST_COHERENT`, так что здесь лимит не применяется; на GPU с кэшируемым некогерентным типом — применяется;
- `bufferImageGranularity` — насколько далеко друг от друга должны стоять буферы и изображения с optimal tiling, если
  они делят одно выделение (это тоже в уроке об аллокаторах).

### 3. Что нужно буферу: требования к памяти

<Step file="13_memory_types" region="requirements" />

Буфер создаётся без памяти, а потом `vkGetBufferMemoryRequirements` возвращает его
[требования к памяти](term:memory-requirements). Шесть пробных буферов:

```text
Buffer requirements (vkGetBufferMemoryRequirements):
  vertex                VERTEX_BUFFER, 1000 bytes -> size 1008, alignment 16, memoryTypeBits 0b111011 (types 0, 1, 3, 4, 5)
  index                 INDEX_BUFFER, 100 bytes -> size 100, alignment 4, memoryTypeBits 0b111011 (types 0, 1, 3, 4, 5)
  uniform               UNIFORM_BUFFER, 100 bytes -> size 128, alignment 64, memoryTypeBits 0b111011 (types 0, 1, 3, 4, 5)
  storage               STORAGE_BUFFER, 1000 bytes -> size 1008, alignment 16, memoryTypeBits 0b111011 (types 0, 1, 3, 4, 5)
  staging               TRANSFER_SRC, 65536 bytes -> size 65536, alignment 16, memoryTypeBits 0b111011 (types 0, 1, 3, 4, 5)
  vertex (copy target)  TRANSFER_DST | VERTEX_BUFFER, 65536 bytes -> size 65536, alignment 16, memoryTypeBits 0b111011 (types 0, 1, 3, 4, 5)
```

На каждый буфер три числа:

- **size** — сколько байт выделить. Бывает больше запрошенного: 1000 байт превращаются в 1008, ближайшее кратное
  выравниванию 16;
- **alignment** — смещение привязки должно быть ему кратно. Оно зависит от usage: 4 у индексного буфера, 16 у
  большинства, 64, как только стоит `UNIFORM_BUFFER`. Эти 64 не случайны: спецификация требует, чтобы выравнивание
  удовлетворяло правилам смещений дескрипторов для данного usage, а `minUniformBufferOffsetAlignment` на этом GPU равен
  64;
- **memoryTypeBits** — в каких типах памяти буфер может жить. Установлен бит *i* — значит, разрешён тип *i*.

## memoryTypeBits = 59 и пропавший тип 2

`0b111011` — это 59: биты 0, 1, 3, 4 и 5. У всех буферов здесь одна и та же маска, и это не случайность шести проб:
инструмент курса запросил все 63 комбинации шести флагов usage при пяти размерах (`src/data/buffer-requirements.json`),
и каждый ответ был 59. Часть этой картины спецификация гарантирует:

- маска одинакова у всех буферов с одинаковыми usage и флагами создания;
- обычный буфер всегда допускает хотя бы один тип `HOST_VISIBLE | HOST_COHERENT` («mappable coherent memory can always
  be attached») и хотя бы один тип `DEVICE_LOCAL`;
- типа `LAZILY_ALLOCATED` в маске не бывает никогда.

А вот того, что буферам разрешён каждый тип устройства, спецификация не обещает, и здесь один тип действительно не
разрешён: **тип 2 буферу не достаётся никогда**, хотя флаги у него в точности как у типа 1. Может, он для изображений?
`vulkaninfo` перечисляет, какие изображения может хранить каждый тип, и для типа 2 ответ тоже «никакие» (2026-10-11,
сокращено):

```text
	memoryTypes[1]:
		heapIndex     = 0
		propertyFlags = 0x0001: count = 1
			MEMORY_PROPERTY_DEVICE_LOCAL_BIT
		usable for:
			IMAGE_TILING_OPTIMAL:
				color images
				FORMAT_D16_UNORM
				...
	memoryTypes[2]:
		heapIndex     = 0
		propertyFlags = 0x0001: count = 1
			MEMORY_PROPERTY_DEVICE_LOCAL_BIT
		usable for:
			IMAGE_TILING_OPTIMAL:
				None
			IMAGE_TILING_LINEAR:
				None
```

Значит, тип 2 служит чему-то, чего не видит ни одна из двух проверок, а чему именно — не говорят ни спецификация, ни
драйвер. Честный ответ: «мы не знаем, и знать нам не нужно». Урок здесь — само правило: флаги типа говорят, **что он
такое**, а `memoryTypeBits` — можно ли **этому ресурсу** им пользоваться. Программа, которая зашила «тип 1 — это VRAM»
или выбирает тип по одним флагам, без маски, однажды привяжет память, которую ресурс не допускает
(`VUID-vkBindBufferMemory-memory-01035`).

## Правило выбора типа памяти

Есть маска и есть желание («хочу `DEVICE_LOCAL`») — какой тип взять? Спецификация отвечает циклом из пяти строк в
главе «Device Memory». Работает он благодаря правилу порядка, которое обязан соблюдать каждый драйвер: из двух типов X
и Y первым идёт X, если «the set of bit flags returned in the propertyFlags member of X is a strict subset of the set of
bit flags returned in the propertyFlags member of Y», либо если флаги равны, а куча X быстрее. Поэтому **первый по
порядку индексов тип, который разрешён и имеет все нужные флаги**, — заодно и самый простой из подходящих. Вариант
шага 13:

<Step file="13_memory_types" region="find-memory-type" />

`find_type` — это цикл из спецификации; `choose_type` прогоняет его дважды, как пример в той же главе: сначала с
обязательными флагами плюс желательными, а если такого типа нет — с одними обязательными. Интерактивы курса пользуются
тем же правилом (`findType` в `src/lib/labs/memory.ts`). Затем шаг 13 задаёт ему вопрос о четырёх видах данных:

<Step file="13_memory_types" region="choose-types" />

```text
Choosing memory types for memoryTypeBits 0b111011 (first type in index order with the flags; preferred flags tried first):
  GPU-only mesh         required DEVICE_LOCAL, preferred (none) -> type 1 (heap 0)
  staging upload        required HOST_VISIBLE | HOST_COHERENT, preferred (none) -> type 3 (heap 1)
  readback              required HOST_VISIBLE, preferred HOST_CACHED -> type 4 (heap 1)
  per-frame data        required HOST_VISIBLE | HOST_COHERENT, preferred DEVICE_LOCAL -> type 5 (heap 2)
  (LAZILY_ALLOCATED: never for buffers, only for images with TRANSIENT_ATTACHMENT usage, module 10)
```

У каждого ответа своя причина:

- **меш только для GPU → тип 1.** `DEVICE_LOCAL` есть у типов 1, 2 и 5; тип 2 не разрешён, а тип 1 стоит раньше типа
  5, потому что его флаги — строгое подмножество флагов типа 5. Без правила порядка наивный цикл мог бы попасть в
  маленькую кучу BAR и забить её мешами;
- **staging → тип 3**, а не 4 и не 5: самый простой тип `HOST_VISIBLE | HOST_COHERENT`, обычная системная память;
- **чтение обратно → тип 4.** `HOST_CACHED` был лишь желательным, но первый проход его находит, и CPU будет читать
  через свои кэши. Здесь тип 4 ещё и когерентный; на GPU, где кэшируемый тип некогерентный, то же правило выберет
  память, которой перед каждым чтением нужен `vkInvalidateMappedMemoryRanges`;
- **данные кадра → тип 5**: маленькие данные, которые CPU переписывает каждый кадр, желательно в VRAM. Куча за этим
  типом здесь всего 214 МиБ, поэтому следующие уроки обращаются с ней как с дефицитом.

Настоящий движок формулирует те же желания своими словами (у VMA, например, есть подсказки вроде «prefer device») и
взвешивает их более сложным поиском, но входов у этого поиска те же два: `memoryTypeBits` ресурса и флаги типов.

### 4. Выделить, привязать, отобразить

Весь ручной путь для одного буфера, в который пишет CPU:

<Step file="13_memory_types" region="allocate-and-bind" />

Создать буфер, спросить требования, выбрать тип, выделить `requirements.size` байт этого типа и привязать по смещению
0 (оно кратно любому выравниванию). Потом CPU получает указатель:

<Step file="13_memory_types" region="map" />

```text
Upload buffer: 4096 bytes (TRANSFER_SRC), memory type 3, allocation 4096 bytes, bound at offset 0
Mapped: pointer aligned to minMemoryMapAlignment (64): yes
Wrote 1024 floats through the pointer, read back: sum 523776 (expected 523776)
Unmapped (HOST_COHERENT: no flush was needed)
```

`vkMapMemory` требует тип `HOST_VISIBLE` (`VUID-vkMapMemory-memory-00682`) и возвращает обычный указатель: дальше
начинается территория `memcpy`. Что нужно сверх этого, решают два свойства типа 3:

- он **когерентный**, поэтому записям не нужен `vkFlushMappedMemoryRanges`. Цепочка по спецификации такая: когерентные
  записи хоста «automatically made available to the host domain», а каждая отправка в очередь выполняет «domain
  operation from host to device» для записей, сделанных до неё, и тем самым делает их видимыми устройству. Коротко:
  записал, отправил — готово. Записи хоста *после* отправки в эту гарантию не входят: им нужен event (`vkSetEvent` на
  хосте и `vkCmdWaitEvents2` со стадией-источником `HOST`), а не барьер;
- он **некэшируемый**, поэтому сумма при чтении обратно сходится, но читается медленно. Для проверки 4 КиБ это неважно;
  для настоящего чтения обратно программа выбрала бы тип 4.

### 5. Два буфера в одном выделении

<Step file="13_memory_types" region="two-buffers-one-allocation" />

```text
One allocation, two buffers: memory type 1, 1108 bytes; vertex buffer (1008 bytes) at offset 0, index buffer (100 bytes) at offset 1008 (alignment 4)
```

Ничто не обязывает буфер иметь собственное выделение. Два буфера могут жить в одном блоке, если его тип разрешён
**обеими** масками (их AND), и каждый лежит по смещению, кратному своему выравниванию: 1008 уже кратно 4. Этот
маленький опыт — вся идея аллокатора, сделанная вручную.

## Что под капотом

- **Куча 0** — это GDDR6X на плате видеокарты, подключённая к контроллерам памяти GPU. **Куча 1** — обычная DDR4 на
  материнской плате: когда GPU её читает, каждое обращение идёт по PCIe и через контроллер памяти CPU. То, что куча
  равна половине RAM, совпадает со стандартным ограничением Windows на «общую память» GPU.
- **BAR** (Base Address Register) — способ, которым устройство PCIe показывает процессору свою память: диапазон
  физических адресов, который корневой комплекс PCIe процессора переадресует видеокарте. 256 МиБ — классический размер
  BAR; с Resizable BAR диапазон может покрыть всю VRAM. Отображение выделения типа 5 даёт CPU указатель в этот
  диапазон, и каждая запись становится транзакцией PCIe к видеокарте; поэтому такая память некэшируемая и
  write-combined.
- **Выделение — событие уровня операционной системы.** В Windows выделение создают часть драйвера, работающая в ядре, и
  менеджер видеопамяти ОС: они вносят его в таблицы страниц GPU и следят, резидентно ли оно. Поэтому `vkAllocateMemory`
  медленный, поэтому число выделений ограничено, и поэтому в модуле есть [урок об аллокаторах](lesson:allocators).
- **Набор типов, который выбрал драйвер**, отражает возможности его железа: тип — это не «сорт RAM», а «сорт
  отображения»: какая куча, кэшируется ли, видна ли CPU. Два типа с одинаковыми флагами на одной куче, как 1 и 2 здесь,
  могут отличаться тем, для чего у Vulkan просто нет флага.
