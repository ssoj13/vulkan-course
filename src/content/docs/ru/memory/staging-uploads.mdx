Прошлый урок оставил меш в системной памяти, и GPU читает его по PCIe при каждой отрисовке. Настоящий дом меша —
`DEVICE_LOCAL`-память, VRAM, а её CPU обычно отобразить не может. Как же байты туда попадают? Дорог три, у каждой своя
синхронизация и своя цена, и есть одна тонкая ловушка, на которую не укажет ни одно сообщение валидации: копирование,
которое *закончилось*, — ещё не копирование, результат которого отрисовки *видят*.

## Место в курсе

Третий урок модуля «Ресурсы и память», где память встречается с модулем о синхронизации. Слои: API (команды
копирования, барьеры, владение семействами очередей), модель памяти под ними (доступность и видимость) и железо
(копирующие движки, PCIe, окно BAR). Цепочка основного пути:

`memcpy на CPU → staging-буфер (HOST_VISIBLE) → отправка → vkCmdCopyBuffer → DEVICE_LOCAL-буфер → барьер (или release / семафор / acquire) → вход вершин`

[Staging-буфер](term:staging-buffer) — это [VkBuffer](term:vk-buffer) в [HOST_VISIBLE](term:host-visible)-памяти, из
которого копирует GPU; результат копирования доходит до отрисовок через [зависимость по памяти](term:memory-dependency):
[барьер](term:pipeline-barrier) в одной очереди или, между семействами очередей,
[передачу владения](term:queue-family-ownership-transfer), упорядоченную [семафором](term:vk-semaphore). Третий путь
обходит всё это через [окно BAR](term:bar). До этого урока: [кучи и типы памяти](lesson:memory-types) (откуда берутся
типы), [буферы вершин и индексов](lesson:vertex-and-index-buffers) (что мы загружаем) и
[барьеры](lesson:barriers-and-layouts) (доступность и видимость). После: [аллокаторы](lesson:allocators) и текстуры
модуля 10, которые приезжают тем же путём.

## Три дороги в VRAM

На рендерферме сцены лежат на файловом сервере, а у каждой рендерноды есть быстрый локальный scratch-диск. Перед
рендером служба копирования переносит файлы кэша с сервера на scratch ноды, и рендерер читает их локально, на полной
скорости. А маленький файл можно записать прямо на ноду через сетевой ресурс: лишней копии нет, но каждый байт идёт по
медленному каналу, пока вы ждёте. Шаг 15 реализует оба способа и ещё вариант первого:

| Путь | Куда идут байты | Кто переносит их через PCIe | Что ставит это раньше отрисовок |
|---|---|---|---|
| по умолчанию | CPU → staging (тип 3) → `vkCmdCopyBuffer` в **графической** очереди → VRAM (тип 1) | GPU, во время копирования | один барьер конвейера |
| `--transfer-queue` | то же, но копирование идёт в **выделенной очереди передачи** | копирующий движок GPU | барьер release, семафор, барьер acquire |
| `--bar` | CPU → сразу в VRAM (тип 5) | CPU, во время своих записей | ничего сверх отправки |

`--mib N` дополняет буфер вершин нулями до N МиБ, чтобы тайминги показывали пропускную способность, а не только
задержку (рисуются по-прежнему только 7 настоящих вершин):

## Путь 1: копирование в графической очереди

### Staging-буфер

<Step file="15_staging" region="staging-buffer" />

Один буфер на 176 байт (вершины со смещения 0, индексы со смещения 140), usage `TRANSFER_SRC`, тип 3 — самый простой
тип `HOST_VISIBLE | HOST_COHERENT`, обычная системная память. У источника копирования такой usage обязателен
(`VUID-vkCmdCopyBuffer-srcBuffer-00118`).

### Настоящие буферы

<Step file="15_staging" region="device-local-buffers" />

Буфер вершин и индексный буфер в типе 1, `DEVICE_LOCAL`, и к их usage добавлен `TRANSFER_DST`: без него копированию
запрещено в них писать (`VUID-vkCmdCopyBuffer-dstBuffer-00120`). Тип 1 CPU отобразить не может; единственный путь
внутрь — команда.

### Записываем копирование

<Step file="15_staging" region="record-copy" />

Одноразовый command buffer из `TRANSIENT`-пула того семейства, которое будет копировать, и два региона копирования:
`[0, 140)` staging-буфера — в буфер вершин, `[140, 176)` — в индексный буфер.

Обратите внимание, чего здесь *нет*: барьера для записей CPU в staging-буфер. Их покрывает «host write ordering
guarantee» спецификации: отправка в очередь «defines a memory dependency with prior host operations», её первая область
доступа — «all host writes to mappable device memory that are available to the host memory domain» (когерентная память
делает записи такими сама), а вторая — «all memory access performed by the device». Записал, отправил — копирование
видит байты. Гарантия касается только записей, сделанных *до* отправки; если хосту нужно писать уже после неё, нужен
event: `vkSetEvent` на хосте и `vkCmdWaitEvents2` со стадией-источником `HOST` и доступом `HOST_WRITE` (барьер тут не
поможет: `HOST` — не стадия ни одной записанной команды).

### Барьер после копирования

<Step file="15_staging" region="copy-barrier" />

Один глобальный барьер памяти в конце command buffer копирования:

- **источник**: стадия `COPY`, доступ `TRANSFER_WRITE` — записи копирования;
- **назначение**: стадии `VERTEX_ATTRIBUTE_INPUT | INDEX_INPUT`, доступы `VERTEX_ATTRIBUTE_READ | INDEX_READ` — чтения
  отрисовок.

Вторая область барьера дотягивается до команд, которые позже **в порядке отправки в эту очередь**, поэтому она
покрывает отрисовки в command buffer каждого кадра, отправленного потом, — как [урок о барьерах](lesson:barriers-and-layouts#маски-стадий-какая-работа-кого-ждёт)
показывал для изображений. Барьер для буфера с именами двух буферов сделал бы то же самое; для буферов глобальный
барьер проще, и именно его используют примеры синхронизации Khronos для копирования, за которым следует чтение вершин.

### Ждём, потом убираем

<Step file="15_staging" region="finish-upload" />

CPU ждёт fence, и только после этого staging-буфер можно уничтожить: копирование читает его до самого конца. Настоящий
движок здесь не блокировался бы: он держал бы кольцо staging-памяти, проверял fence или
[значение timeline](lesson:timeline-semaphores) позже, а первый кадр, рисующий меш, ждал бы загрузку на стороне GPU.
Ожидание оставляет шаг простым и делает копирование измеримым.

## Доступно ещё не значит видимо

Перечитайте комментарии двух последних регионов: fence говорит, что копирование **завершено**, и программа ждёт его
ещё до того, как записана первая отрисовка. Зачем тогда вообще барьер? Затем, что «завершено» — утверждение об
исполнении, а отрисовкам нужно утверждение о памяти. [Урок о барьерах](lesson:barriers-and-layouts#почему-одного-порядка-мало)
разделил зависимость по памяти на две половины: **доступность** (записи вытолкнуты из кэшей писателя в домен памяти)
и **видимость** (взгляд читателей на эту память обновлён). Теперь посмотрите, что спецификация даёт сигналу fence:

> The first access scope includes all memory access performed by the device.
> The second access scope is empty.

Первая половина: записи копирования становятся **доступными**. Вторая: видимыми — **никому**. И ожидание fence на
хосте тоже не добавляет никакой области доступа устройства. Значит, после ожидания fence результаты копирования лежат
в памяти, доступные, но видимыми для стадии входа вершин их не сделал никто. Это и есть работа барьера: его область
доступа назначения, `VERTEX_ATTRIBUTE_READ | INDEX_READ`, — ровно та видимость, которая нужна отрисовкам. Подошло бы и
ожидание семафора: его вторая область доступа — «all memory access performed by the device».

Вся лестница «кто что делает доступным и видимым» для загрузок этого модуля:

| Операция | Делает доступным | Делает видимым для |
|---|---|---|
| записи CPU в `HOST_COHERENT`-память | эти записи, в домене хоста (сами собой) | (пока никого) |
| `vkFlushMappedMemoryRanges` | записи CPU в некогерентную память, в домене хоста (диапазоны округляются до `nonCoherentAtomSize`) | (пока никого) |
| отправка в очередь | записи хоста, сделанные до неё: домен хоста → домен устройства | всех обращений устройства в этой отправке и позже |
| event для записей хоста *после* отправки: `vkSetEvent` на хосте → `vkCmdWaitEvents2` с источником `HOST` / `HOST_WRITE` | записи хоста до `vkSetEvent`: домен хоста → домен устройства | обращений области назначения ожидания |
| сигнал fence | все записи устройства до него | **никого** |
| барьер конвейера | записи его области доступа источника | обращений его области доступа назначения |
| сигнал семафора → ожидание | все записи устройства до сигнала (в пределах маски стадий сигнала) | всех обращений устройства после ожидания (в пределах маски стадий ожидания) |
| барьер с назначением `HOST` / `HOST_READ` | записи устройства: домен устройства → домен хоста | чтений хоста из когерентной памяти |
| `vkInvalidateMappedMemoryRanges` | (ничего) | записи устройства, уже доступные в домене хоста → чтения хоста из некогерентной памяти (с тем же округлением) |

Последние строки — ответ на обещание из [урока о fence](lesson:fences-and-semaphores#fence-gpu-сообщает-хосту): чтобы
прочитать результаты GPU на CPU, запишите барьер от стадии и доступа писателя к `HOST` / `HOST_READ` *до* конца
отправки с fence, потом дождитесь fence, потом читайте (а для некогерентной памяти сначала вызовите
`vkInvalidateMappedMemoryRanges`). Спецификация говорит это в примечании к ожиданию fence: «Signaling a fence and
waiting on the host does not guarantee that the results of memory accesses will be visible to the host, as the access
scope of a memory dependency defined by a fence only includes device access. A memory barrier or other memory
dependency must be used to guarantee this.»

<Aside type="caution" title="Почему никто не жалуется, если барьера нет">
Удалите барьер — и шаг 15 по-прежнему рисует правильный шестиугольник, а слой валидации молчит. Причин две. Базовая
валидация сверяет каждый вызов с его valid usage, а каждый вызов остаётся корректным; следит, какое обращение было
раньше какого, только **синхронизационная валидация**, а она по умолчанию выключена (включается переменной
`VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true`, как в [уроке о барьерах](lesson:barriers-and-layouts#доказательство-уберём-одну-стадию)).
Но и с ней, как мы проверили 2026-10-11, убрав барьер после копирования, а на пути с очередью передачи — барьер
acquire, оба раза слой промолчал. Вероятная причина — ожидание на хосте: слой считает ожидание fence процессором концом
обращений копирования, и когда отрисовки отправляются позже, сравнивать их уже не с чем. Это бухгалтерия слоя, а не
модель памяти: по спецификации отрисовки читают память, которую им никто не сделал видимой, и на GPU, где выборка
вершин читает через кэш с устаревшими строками, они прочитали бы старые данные. Барьеры шага 15 следуют спецификации и
примерам синхронизации Khronos, а не сообщению валидации.
</Aside>

## Путь 2: выделенная очередь передачи

У дискретного GPU есть копирующие движки — DMA-блоки, которые переносят память, не занимая шейдерные ядра. У NVIDIA
они видны как семейство очередей с `TRANSFER`, но без `GRAPHICS` и `COMPUTE`
([семейства очередей](lesson:queue-families)). На GPU курса это семейство 1 с двумя очередями:

<Step file="15_staging" region="transfer-family" />

Копирование там идёт **рядом** с графической очередью: следующий уровень может подгружаться, пока рендерится текущий.
Цена в том, что буферы теперь пересекают границу между семействами очередей.

### Зачем передавать владение

Буферы созданы с `VK_SHARING_MODE_EXCLUSIVE`, режимом по умолчанию: в каждый момент они принадлежат **одному**
семейству очередей. Спецификация: такие ресурсы «must have their ownership explicitly transferred from one queue family
to another in order to access their content in a well-defined manner on a queue in a different queue family». Какое
буферу дело, какое семейство его трогает? Железо за двумя семействами может хранить данные по-разному (кэши, сжатие у
изображений), и передача — то место, где драйвер может их преобразовать. Альтернатива,
`VK_SHARING_MODE_CONCURRENT`, заранее перечисляет несколько семейств и обходится без передач, но «may result in lower
performance access».

[Передача владения между семействами очередей](term:queue-family-ownership-transfer) состоит из двух половин — двух
барьеров с одним и тем же диапазоном буфера и одной и той же парой индексов семейств:

- **release** в очереди исходного семейства (transfer, 1 → 0): его область источника покрывает записи копирования, а
  стадия и доступ назначения игнорируются;
- **acquire** в очереди целевого семейства (graphics, 1 → 0): стадия и доступ источника игнорируются, а область
  назначения покрывает чтения, которые идут следом;
- а между ними — зависимость исполнения, «e.g. using a semaphore»: release должен произойти раньше acquire.

### Release: отдаём владение

<Step file="15_staging" region="release-ownership" />

Копирование, затем барьер release в том же command buffer; отправка в очередь передачи с сигналом семафора и fence.
Стадия сигнала семафора — `ALL_COMMANDS`, и это не лень. Спецификация: «Prior to the introduction of
`VK_DEPENDENCY_QUEUE_FAMILY_OWNERSHIP_TRANSFER_USE_ALL_STAGES_BIT_KHR`, `VK_PIPELINE_STAGE_ALL_COMMANDS_BIT` is the only
valid stage to wait on or wait for these operations, as the acquire and release operations do not occur in a defined
stage.»

**Исключение.** Если этот флаг стоит в `dependencyFlags` барьеров, стадии, которые release или acquire иначе
игнорировали бы, участвуют в синхронизации, и тогда семафор может назвать точные стадии и не останавливать весь
конвейер. Флаг принадлежит `VK_KHR_maintenance8` и его возможности `maintenance8`. Правило valid usage, которое требует
эту возможность, написано для команды sync1 (`VUID-vkCmdPipelineBarrier-maintenance8-10206`) и для
`vkCmdWaitEvents2`; для `vkCmdPipelineBarrier2`, которым пользуется шаг 15, в реестре SDK 1.4.341 такого правила нет,
так что прежде чем полагаться на флаг, включите возможность в любом случае. GPU курса её поддерживает (vulkaninfo:
`maintenance8 = true`), но шаг 15 держится ядра Vulkan 1.4 и использует `ALL_COMMANDS`.

### Acquire: принимаем владение

<Step file="15_staging" region="acquire-ownership" />

Второй command buffer, из пула графического семейства, с одними барьерами acquire; отправка в графическую очередь с
ожиданием семафора (снова на `ALL_COMMANDS`). Области назначения у каждого буфера свои: `VERTEX_ATTRIBUTE_INPUT` /
`VERTEX_ATTRIBUTE_READ` для буфера вершин, `INDEX_INPUT` / `INDEX_READ` для индексного.

Здесь модель памяти приготовила второй сюрприз. Ожидание семафора само по себе уже делает записи копирования
**видимыми** всем обращениям устройства после него. То есть по части памяти acquire ничего не добавляет — и всё же он
обязателен: «If memory dependencies are correctly expressed between uses of such a resource between two queues in
different families, but no ownership transfer is defined, the contents of that resource are undefined for any read
accesses performed by the second queue family.» Видимость отвечает на вопрос «может ли читатель увидеть байты?»,
владение — «в том ли виде лежат байты, который понимает семейство читателя?». Нужно и то, и другое.

## Путь 3: напрямую через окно BAR

<Step file="15_staging" region="bar-write" />

Ни staging-буфера, ни копирования, ни command buffer: оба буфера создаются в типе `DEVICE_LOCAL | HOST_VISIBLE |
HOST_COHERENT` (тип 5 на куче 2), отображаются, и CPU пишет в них. Записи идут по PCIe прямо по ходу дела и ложатся в
VRAM; следующая отправка делает их видимыми отрисовкам, как любую когерентную запись хоста. Это самый короткий путь, и
у него два ограничения:

- **размер**: при выключенном Resizable BAR куча 2 — 214 МиБ. Программа запрашивает требования обоих буферов *до*
  их создания (`vkGetDeviceBufferMemoryRequirements`, Vulkan 1.3) и сверяет их сумму с кучей: выделение больше своей
  кучи недопустимо (`VUID-vkAllocateMemory-pAllocateInfo-01713`), а два выделения, каждое из которых помещается, вместе
  всё равно могут её переполнить. С `--bar --mib 300`:

  ```text
  Error: "vertex + index buffers need 314572836 bytes, but heap 2 has only 224395264 bytes (an upper bound, not the budget: see VK_EXT_memory_budget)"
  ```

- **время CPU**: переносит данные сам CPU, со скоростью некэшируемых записей по шине (замеры ниже).

С включённым ReBAR память `DEVICE_LOCAL | HOST_VISIBLE` должна вырасти примерно до размера VRAM, но на машине курса
это ещё не измерено, и драйвер может показать её иначе — например, как тип на куче 0, а не как большую кучу 2. Это
измерим, когда ReBAR будет включён (см. проверку в уроке
[Кучи и типы памяти](lesson:memory-types#типы-как-пользоваться-кучей)). Ограничение по времени CPU остаётся в любом
случае.

## Сколько стоит каждая дорога

Замеры на машине курса (RTX 3080 Ti на PCIe 4.0 x16, Ryzen 9 5900X, Windows 11, драйвер 616.64), 2026-10-11:
release-сборки обоих языков, слой валидации включён, синхронизационная валидация выключена, по три запуска на язык с
чередованием Rust и C++, на машине, занятой и другой работой. Диапазоны — наименьшее и наибольшее из шести запусков.
«Копирование на GPU» измеряется на CPU от записи команд до конца ожидания fence, так что включает отправку и
пробуждение, а не только само копирование.

| Загрузка | Записи CPU | Копирование на GPU (запись + отправка + ожидание) |
|---|---|---|
| 64 МиБ через staging, графическая очередь | 6,2–9,8 мс (6,9–10,8 ГБ/с) в тип 3 | 5,3–6,7 мс (10,0–12,6 ГБ/с) |
| 64 МиБ через staging, очередь передачи | 5,9–7,4 мс (9,1–11,5 ГБ/с) в тип 3 | 5,1–6,1 мс (11,0–13,1 ГБ/с) |
| 64 МиБ через BAR | 13,0–16,0 мс (4,2–5,2 ГБ/с) в тип 5 | нет |
| 176 байт через staging, графическая очередь | 0,012–0,019 мс | 0,83–0,98 мс |
| 176 байт через staging, очередь передачи | 0,010–0,023 мс | 1,19–1,74 мс |
| 176 байт через BAR | 0,017–0,027 мс | нет |

```text

Vertex + index buffers: memory type 5 (DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT), heap 2
[timing] upload of 67108900 bytes: CPU writes 13.014 ms (5157 MB/s) straight into VRAM, no copy
```

Что эти числа говорят и чего не говорят:

- **Для больших данных обе дороги в сумме стоят примерно одинаково**, 11–17 мс на 64 МиБ, но тратят разные ресурсы.
  Staging тратит вдвое больше трафика памяти и копирование на GPU, зато CPU свободен после быстрого `memcpy` в RAM.
  BAR не тратит ни времени GPU, ни лишней RAM, но занимает CPU до двух раз дольше: он пишет через шину со скоростью
  4–5 ГБ/с.
- **Обе очереди копируют одинаково быстро**: само копирование упирается в шину (измерено около 11–13 ГБ/с при
  номинальных 32 ГБ/с), а не в то, какой движок его выполняет. Очередь передачи покупает параллельность с рендерингом,
  которую разовая загрузка до первого кадра показать не может, а стоит лишней отправки и семафора: её путь туда и
  обратно для 176 байт — самый медленный.
- **На маленьких данных BAR выигрывает в 30 раз и больше**: 0,02 мс против 0,8–1,7 мс. «Копирование» 176 байт — это
  сплошная задержка (записать команды, отправить, дождаться, пока GPU возьмёт работу, разбудить CPU по fence), а не
  пропускная способность. Поэтому данным кадра, например [uniform-данным следующего модуля](lesson:uniform-buffers), место в куче BAR, если они
  туда помещаются.
- **Мы не выяснили, почему** записи через BAR идут со скоростью 4–5 ГБ/с, когда копирующие движки получают от той же
  шины 11–13 ГБ/с; обычный подозреваемый — путь write-combining у CPU. Считайте это соотношение свойством этой машины,
  а не законом.
- **Синхронизационная валидация замедляет кадры, а не записи хоста**: с `VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true`
  (Rust, по три запуска на путь, 2026-10-11) запись 64 МиБ заняла 7,4–13,4 мс в тип 3 и 13,1–16,4 мс в тип 5 — тот же
  диапазон, что и без неё: `memcpy` в отображённую память не делает ни одного вызова Vulkan, который слою было бы
  проверять. А цикл рендеринга после загрузки упал с 2600–2800 до 1500–2000 кадров в секунду. И всё же никогда не
  измеряйте с ней.

## Что под капотом

- **Копирующий движок** — это DMA-блок: он читает из одного диапазона адресов и пишет в другой, большими пачками, без
  шейдерных ядер. Чтение staging-буфера означает запросы чтения PCIe в системную память; поэтому драйверы обычно держат
  HOST_VISIBLE системную память закреплённой (page-locked), чтобы ОС не перемещала её, пока GPU может её читать.
- **Записи через BAR** — это сохранения CPU в диапазон адресов, принадлежащий видеокарте. CPU отображает такую память
  как write-combining: сохранения собираются в нескольких буферах write-combining и уходят пачками. Поэтому
  последовательная запись достаточно быстрая, а чтение обратно очень медленное: каждое чтение — поездка до видеокарты и
  обратно.
- **Передача владения между семействами очередей** — то место, где драйвер может преобразовать ресурс между
  представлениями, которыми пользуются два аппаратных движка. Для обычного буфера на этом GPU она, вероятно, почти
  бесплатна; для сжатого изображения это может быть настоящая распаковка. Vulkan не обещает ни того, ни другого,
  поэтому API и делает её явной.
- **Барьер после копирования** превращается в обслуживание кэшей в конце копирования: убедиться, что записи
  копирования покинули буферы движка и что в кэшах, через которые читает выборка вершин, нет устаревших строк. Какие
  именно это кэши и нужна ли вообще какая-то работа, знает драйвер, а не мы; наша часть — сказать, кто пишет и кто
  читает.
