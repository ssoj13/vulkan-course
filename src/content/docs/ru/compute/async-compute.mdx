В шаге 26 симуляция и отрисовка делят одну очередь и один буфер, и барьеры заставляют их работать по очереди: dispatch
ждёт предыдущую отрисовку, отрисовка ждёт dispatch. А у GPU курса есть семейство очередей, которое умеет считать, но не
рисовать, — семейство 2. Может ли симуляция *следующего* кадра идти в этой очереди, пока рисуется *этот*? Чего это
стоит в буферах и синхронизации — и становится ли от этого здесь хоть что-нибудь быстрее?

## Место в курсе

Последний урок модуля **«Compute»** — и тот, где в дело идёт всё, что курс построил вокруг очередей:
[семейства очередей](lesson:queue-families) из модуля 3 (семейство 2 тогда напечатали и отложили),
[timeline-семафоры](lesson:timeline-semaphores) из модуля 7, [передача владения между
семействами](lesson:staging-uploads) из модуля 8 и [частицы](lesson:particles) прошлого урока. Цепочка:

`compute-only queue family → its own VkQueue and command pool → ping-pong buffers P[0], P[1] (CONCURRENT) → timeline "computed": graphics frame n waits computed ≥ n → timeline "rendered": compute step n waits rendered ≥ n-2 → device timestamps on both queues → overlap measured`

[Async compute](term:async-compute) — это отправка вычислений в собственную очередь, чтобы они *могли* идти рядом с
графикой; идут ли они рядом на самом деле — вопрос [параллельности очередей](term:queue-concurrency), которую Vulkan
разрешает, но никогда не обещает. Раз отрисовка и следующий шаг симуляции теперь идут одновременно, состояние живёт в
паре [ping-pong-буферов](term:ping-pong-buffer), которую два семейства делят согласно её
[sharing mode](term:sharing-mode). Ожидания — это [timeline-семафоры](term:timeline-semaphore), по одному на очередь.

## Два пула фермы и граф зависимостей

Возьмём рендер-ферму с двумя пулами: скажем, GPU-ноды под рендер и CPU-пул под симуляцию. Задачу симуляции и задачу
рендера она гонит бок о бок, насколько позволяют зависимости: «рендер кадра 12» ждёт «симуляцию кадра 12», а
«симуляция кадра 13» может стартовать, пока кадр 12 рендерится. Вот и вся идея, и ферма сразу показывает обе её цены.
Задачам нужны свои копии данных (рендер читает кэш кадра 12, пока симуляция пишет кадр 13), и каждую зависимость надо
прописать явно, потому что сама ферма её не угадает. В Houdini это знакомо по TOP-сети, где кэш симуляции и рендер
кадров — отдельные узлы с явными рёбрами между ними.

В Vulkan пулы — это очереди двух семейств, копии — два буфера частиц, зависимости — семафоры. План для кадра n:

```text
compute queue:   [step 1] [step 2]  [step 3]  [step 4]  ...
graphics queue:           [frame 1] [frame 2] [frame 3] ...
                 step n writes P[n % 2] from P[(n-1) % 2];  frame n draws P[n % 2]
```

Шаг compute n+1 отправляется сразу после кадра n, так что GPU *может* выполнять их одновременно: шаг n+1 читает
P[n % 2], который рисует кадр n (два чтения, конфликта нет), и пишет P[(n+1) % 2], который рисовал кадр n-1 и который
никто не читает, как только кадр n-1 закончен (это одно из ожиданий ниже). Ради этого перекрытия шаг и написан.

## Ping-pong-буферы

<Step file="27_async_compute" region="sharing" />

Два буфера, P[0] и P[1], в каждом все 2^20 частиц. Шаг n читает P[(n-1) % 2] и пишет P[n % 2]; кадр n рисует P[n % 2].
У шейдера появляется пятая точка входа, `advance`: вместо обновления одного буфера на месте она читает `previous`
(binding 1) и пишет `state` (binding 0):

```text
state[i] = update(previous[i], params.dt, params.time);
```

Ровно так устроен SOP Solver в Houdini: его вход `Prev_Frame` — прошлое состояние, а сеть внутри пишет следующее.

## CONCURRENT или EXCLUSIVE

Буферы частиц трогают два семейства очередей: compute их пишет, графика читает как вход вершин. Как это разрешено,
говорит **sharing mode** буфера:

| | `EXCLUSIVE` | `CONCURRENT` |
|---|---|---|
| Владелец | одно семейство в каждый момент | все семейства, перечисленные при создании, сразу |
| Смена семейства | [передача владения](term:queue-family-ownership-transfer): release-барьер в одной очереди, acquire-барьер в другой | ничего |
| Без передачи | «the contents of that resource are undefined for any read accesses performed by the second queue family» (спецификация) | не применимо |
| Цена | сами передачи и их упорядочивание | «`VK_SHARING_MODE_CONCURRENT` may result in lower performance access to the buffer or image than `VK_SHARING_MODE_EXCLUSIVE`» (спецификация) |

Здесь каждое состояние читают *оба* семейства одновременно: кадр n рисует P[n % 2], пока шаг n+1 читает его в очереди
compute. С `EXCLUSIVE` каждому буферу понадобились бы release и acquire при каждой смене рук, и эта передача выстроила бы
в цепочку ровно то перекрытие, ради которого всё затевалось. Поэтому буферы `CONCURRENT` с семействами 0 и 2. Во что
обходится «lower performance», решает реализация; обычно беспокоятся об изображениях, сжатие которых некоторые GPU при
совместном доступе отключают. Для буферов, которые читаются раз за кадр, это разумная цена.

`--same-queue` использует одно семейство, и тогда выбор только один, `EXCLUSIVE`: `CONCURRENT` требует больше одного
индекса семейства (`VUID-VkBufferCreateInfo-sharingMode-00914`), причём индексы должны быть разными
(`VUID-VkBufferCreateInfo-sharingMode-01419`), то есть нужны минимум два различных семейства.

## Два timeline-семафора, четыре ожидания

<Step file="27_async_compute" region="timelines" />

По одному [timeline-семафору](term:timeline-semaphore) на производителя, и каждый считает законченную работу своей
очереди: `computed` доходит до n, когда закончен шаг n (начинает он с 0 — это `init`), `rendered` доходит до n, когда
закончен кадр n. Всякое ожидание в программе звучит как «другая очередь дошла до значения v» или, для CPU, «этот слот
снова свободен»:

| Кто | Ждёт | Зачем | Конфликт |
|---|---|---|---|
| графика, кадр n | `computed ≥ n` | он рисует P[n % 2], который пишет шаг n | чтение после записи, между очередями |
| compute, шаг n | `rendered ≥ n-2` | он перезаписывает P[n % 2], который рисовал кадр n-2 | запись после чтения, между очередями |
| compute, шаг n (в той же очереди, что шаг n-1) | барьер в своём начале | он читает то, что записал шаг n-1, и перезаписывает то, что шаг n-1 читал | чтение после записи, запись после чтения |
| CPU, перед кадром n / шагом n | `rendered ≥ n-2` / `computed ≥ n-2` | слот снова использует свой command buffer, семафор и запросы | (повторное использование хостом) |

### Ожидание, которое проглядела валидация

Вторую строку таблицы, `rendered ≥ n-2`, проще всего забыть, потому что кажется, будто она ни к чему. Проверим, что
ещё могло бы поставить записи шага n после чтений кадра n-2:

- CPU: отправляя шаг n (сразу после кадра n-1), он дождался только `rendered ≥ n-3` (слот кадра n-1) и
  `computed ≥ n-2` (слот шага n). Кадр n-2 может ещё быть на GPU.
- очередь compute: шаг n-1, стоящий прямо перед шагом n, ждал `rendered ≥ n-3`. О кадре n-2 — опять ничего.

Значит, без этого ожидания шаг n может начать перезаписывать P[n % 2], пока вход вершин кадра n-2 ещё его читает:
конфликт записи после чтения между очередями. Как любой WAR, он закрывается одной зависимостью исполнения, и ожидание
семафора — как раз она.

Валидация синхронизации этого не заметила. С обеими переменными (`VK_KHRONOS_VALIDATION_VALIDATE_SYNC` и
`VK_KHRONOS_VALIDATION_SYNCVAL_SHADER_ACCESSES_HEURISTIC`, см. [что она видит, а что
нет](lesson:barriers-and-layouts#что-она-видит-а-что-нет)) временная правка, убравшая ожидание `rendered ≥ n-2`,
отработала без сообщений: ложноотрицательный результат. Обратную ошибку тот же инструмент поймал: без ожидания
`computed ≥ n` в отправке графики он выдал «vkQueueSubmit2(): READ_RACING_WRITE hazard detected. vkCmdDraw ... reads
VkBuffer ..., which was previously written by vkCmdDispatch (... submitted on VkQueue ...)» (фрагмент, как он записан в
заметках проекта). А межочередной WAR проскочил. Ожидание стоит в программе потому, что его требует таблица выше;
чистый прогон валидации готового шага (оба языка, оба режима, только предупреждение слоя bandicam) говорит о том, что
остальное согласовано, но не доказывает, что ничего не пропущено.

### Почему каждое ожидание на ALL_COMMANDS

Обе отправки ждут и сигналят на `ALL_COMMANDS` — включая `image_available` изображения swapchain, которое шаг 10 ждал
на `COLOR_ATTACHMENT_OUTPUT`. Причина — измерение: каждый command buffer начинается с timestamp на `TOP_OF_PIPE`, а курс
понимает `ALL_COMMANDS` как охват всех операций пакета, timestamp в том числе, так что timestamp идёт после ожиданий, и
интервал меряет работу, а не ожидание. Ожидание на более поздней стадии позволило бы `TOP_OF_PIPE` проскочить раньше, и
интервал графики включил бы ожидание изображения или симуляции.

Цена: с `image_available` на `ALL_COMMANDS` вершинная работа уже не может начаться до получения изображения, а узкая
стадия шага 10 это позволяла. В этих запусках цена не измерялась: время графики было 269–277 мкс на кадр с широким
ожиданием и 272–282 мкс с узким (MAILBOX, где acquire почти не ждёт). Переход layout в `COLOR_ATTACHMENT_OPTIMAL`
по-прежнему сцеплен с ожиданием, потому что `COLOR_ATTACHMENT_OUTPUT` входит в `ALL_COMMANDS`.

## Timestamps из двух очередей

<Step file="27_async_compute" region="timestamps" />

Каждая отправка пишет два timestamp: в начале (`TOP_OF_PIPE`) и в конце. Сравнивать timestamp графики с timestamp
compute имеет смысл, только если оба считают одни и те же часы, — и это так: все device-timestamps лежат в
`VK_TIME_DOMAIN_DEVICE_KHR`, значения которого «comparable with device timestamp values captured using
vkCmdWriteTimestamp or vkCmdWriteTimestamp2» (спецификация). Программа ставит в пару кадр графики n и шаг compute n+1,
ту пару, что может перекрываться, а перекрытие — это длина пересечения двух интервалов.

Значение имеют только младшие `timestampValidBits` бит timestamp, и на них счётчик заворачивается. У обоих семейств здесь
64 бита, но код на это не полагается: каждое значение он берёт как знаковое смещение от начала графики по модулю
2^bits, так что заворот между двумя отсчётами не сломает минимум и максимум.

Честный итог: **на этом GPU измеримого выигрыша нет**. Очереди действительно перекрываются, немного: несколько
микросекунд из каждого 46-микросекундного шага идут во время отрисовки кадра — против ровно нуля в одной очереди. Но
частота кадров не растёт, а разброс между запусками перекрывает любую разницу. Причина видна в тех же цифрах: GPU-время
кадра — около 0,32 мс, а по настенным часам кадр длится 0,6–1,1 мс. Большую часть времени GPU простаивает; частоту
кадров задают CPU и показ, так что даже идеальное перекрытие, спрятавшее все 46 мкс симуляции, ускорять было бы нечего.
Async compute сокращает критический путь GPU, а здесь GPU на нём не лежит.

### Когда async compute действительно помогает

Общий случай, без цифр этого курса (их не измеряли): async compute окупается в основном тогда, когда узкое место —
GPU, и какая-то графическая работа недогружает шейдерные ядра. Типичный пример — проходы, упирающиеся в
fixed-function-железо, вроде рендера shadow map или depth-only: они загружают растеризатор и блоки глубины, а
значительная часть ALU шейдеров стоит. Вычисления, не зависящие от такого прохода (light culling, ambient occlusion
предыдущего кадра, симуляция частиц и ткани, постобработка предыдущего кадра), могут заполнить эту дыру. А могут и
навредить: две очереди делят одни и те же кэши и пропускную способность памяти, и две нагрузки, упирающиеся в
пропускную способность, бок о бок могут работать медленнее, чем друг за другом. Движки, которые этим пользуются, меряют
на каждом GPU и часто держат переключатель, чтобы выключить async compute. Опыт, в котором узким местом становится GPU
(ядро потяжелее, гораздо больше частиц или FIFO с кадром, упирающимся в GPU), показал бы, где на этом GPU точка
безубыточности; в курс он пока не входит.

## Что под капотом

- **Что значит «своя очередь» в железе.** У front end GPU обычно несколько каналов, из которых он выбирает команды:
  графическая работа идёт в графический конвейер, а очереди только для compute — в отдельные compute-front end (у AMD
  они называются Asynchronous Compute Engines). Шейдерные ядра у них общие: async compute не добавляет ядер, он добавляет
  второй источник работы для ядер, которые иначе ждали бы. Как очереди Vulkan ложатся на эти каналы и получают ли две
  очереди семейства 2 разные каналы, API не документирует — это выбор драйвера.
- **Одна очередь — нулевое перекрытие.** В одной очереди Vulkan всё равно разрешает командам разных отправок
  перекрываться там, где этого не запрещают барьер или семафор. В этих запусках измеренное перекрытие было ровно
  0,0 мкс. Это наблюдение на этой машине, а не правило, и даже не доказательство того, что отправки шли строго одна за
  другой: реализации «may write the timestamp at any stage that is logically later than stage» (`vkCmdWriteTimestamp2`),
  и timestamp начала, зафиксированный с опозданием, может спрятать настоящее перекрытие.
- **Передача владения, если она нужна.** `EXCLUSIVE` с парами release/acquire — верный выбор, когда ресурс меняет
  семейство редко (загрузка из очереди передачи, как в [уроке о staging](lesson:staging-uploads)), или для изображений,
  сжатие которых `CONCURRENT` может отключить. Баланс переворачивается, когда ресурсом каждый кадр пользуются оба
  семейства, как здесь.
