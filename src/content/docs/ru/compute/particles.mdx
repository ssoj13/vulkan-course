В прошлом уроке результаты уходили обратно на CPU. Большая часть compute-работы в рендерере туда не возвращается
никогда: она готовит данные, которые тут же съедает следующая отрисовка. Шаг 26 каждый кадр двигает compute-шейдером
миллион частиц и рисует их точками из того же буфера — с двумя кадрами в полёте и без единой копии. Кто и когда пишет
буфер, кто и когда его читает, и что не даёт отрисовке кадра увидеть частицы, сдвинутые наполовину, а симуляции
следующего кадра — двигать частицы, которые ещё читает предыдущая отрисовка?

## Место в курсе

Второй урок модуля **«Compute»**. Он стыкует [compute pipeline](lesson:compute-pipelines) прошлого урока с циклом кадра
из [урока о кадрах в полёте](lesson:frames-in-flight), а его главный вопрос — вопрос [барьеров](lesson:barriers-and-layouts):
какие [конфликты доступа](term:data-hazard) здесь есть и какой барьер закрывает каждый. Цепочка:

`init dispatch (fence-waited once) → per frame: barrier (previous frame → this dispatch) → dispatch simulate (writes the buffer) → barrier (COMPUTE_SHADER write → VERTEX_ATTRIBUTE_INPUT read) → draw POINT_LIST (vertex input reads the same buffer) → present`

[Система частиц на GPU](term:gpu-particles) держит состояние в одном буфере, который одновременно
[storage-буфер](term:storage-buffer) и [вершинный буфер](term:vertex-buffer); отрисовка превращает каждый его элемент в
[точечный примитив](term:point-primitive). Между двумя применениями стоят [pipeline barrier](term:pipeline-barrier), а
главное утверждение урока касается [кадров в полёте](term:frames-in-flight): копии на каждый кадр нужны только данным,
которые пишет CPU. Дальше: [async compute](lesson:async-compute), где симуляция переезжает в собственную очередь.

## Буфер частиц — это и есть вершинный буфер

POP-сеть в Houdini держит точки внутри солвера: каждый кадр солвер читает точки, применяет силы и записывает их
обратно, а вьюпорт рисует то, что там лежит. Между кадрами ничего не уходит на диск. Шаг 26 — та же картина на GPU:
один буфер хранит все частицы, compute-шейдер — это солвер, графический пайплайн — вьюпорт.

<Step file="26_particles" region="particle" />

Частица — 16 байт: позиция и скорость, по `float2`. Шейдер объявляет ту же структуру:

<Snippet src="shaders/particles.slang" />

Один модуль, четыре точки входа: `init` пишет начальное состояние, `simulate` сдвигает каждую частицу на один шаг
времени, `vertexMain` и `fragmentMain` рисуют. Интегратор — полунеявный (симплектический) метод Эйлера: сначала
обновляется скорость, а позиция затем сдвигается уже с *новой* скоростью. Ускорение направлено к аттрактору, который
кружит по окну, плюс лёгкое сопротивление и отскок от краёв. Пятая точка входа, `advance`, понадобится в
[следующем уроке](lesson:async-compute).

<Step file="26_particles" region="particle-buffer" />

У буфера два usage: `STORAGE_BUFFER`, чтобы compute-шейдер привязал его через дескриптор, и `VERTEX_BUFFER`, чтобы
`vkCmdBindVertexBuffers` привязал те же байты для отрисовки. У `VkBuffer` может быть любая комбинация usage; флаги
говорят только, какими способами к нему будут обращаться, чтобы драйвер разместил и выровнял его под все. Память —
`DEVICE_LOCAL` (тип 1): CPU не читает и не пишет ни одной частицы, так что держать их где-то ещё незачем, и загрузка
через staging тоже не нужна — начальное состояние GPU пишет сам.

При 2^20 частиц буфер занимает 16 МиБ. Ещё шаг отказывается от буфера больше `maxStorageBufferRange`: его дескриптор
привязывает весь буфер как storage-буфер, и этот диапазон не может превышать лимит
(`VUID-VkWriteDescriptorSet-descriptorType-00333`). Спецификация гарантирует лишь 2^27 байт (128 МиБ), а это меньше, чем
2^24 x 16 байт, которые допускает `--count`; RTX 3080 Ti сообщает 4294967295, так что здесь проверка не срабатывает.

## Одна очередь на всё

Dispatch и отрисовка записываются в один command buffer, значит, идут в одну очередь, значит, её семейство должно
уметь и `GRAPHICS`, и `COMPUTE` (и показ).

<Step file="26_particles" region="pick-device" />

На настольных GPU графическое семейство обычно умеет и вычисления, но спецификация обещает меньше, чем «любое
графическое семейство умеет compute»: «If an implementation exposes any queue family that supports graphics operations,
at least one queue family of at least one physical device exposed by the implementation must support both graphics and
compute operations.» Поэтому шаг проверяет оба флага. У RTX 3080 Ti они есть у семейства 0.

## Два пайплайна и отрисовка точек

<Step file="26_particles" region="compute-pipelines" />

У `init` и `simulate` общий layout (набор 0, binding 0 — буфер частиц; 16-байтовый диапазон push-констант для стадии
compute), и один вызов `vkCreateComputePipelines` создаёт оба пайплайна из одного модуля.

<Step file="26_particles" region="graphics-pipeline" />

Отрисовка читает частицы через **вход вершин**, а не через дескриптор: binding 0 с шагом 16, позиция — атрибут 0 по
смещению 0, скорость — атрибут 1 по смещению 8 (вершинный шейдер красит точку по скорости). Топология `POINT_LIST`:
каждая вершина — одна [точка](term:point-primitive), квадрат в `PointSize` пикселей с центром в ней.

У точек свои правила. Пайплайн, рисующий `POINT_LIST` только с вершинным шейдером, обязан писать `PointSize`
(`VUID-VkGraphicsPipelineCreateInfo-topology-08773`, если не включена возможность `maintenance5`, а этот курс её не
включает), поэтому `vertexMain` пишет `SV_PointSize = 1.0`. И бесплатен только размер 1.0: возможность `largePoints`
«specifies whether points with size greater than 1.0 are supported. If this feature is not enabled, only a point size
of 1.0 written by a shader is supported.» Крупные, мягкие или текстурированные частицы обычно рисуют квадами, развёрнутыми
к камере (два треугольника на частицу, которые вершинный шейдер строит по индексу вершины); заодно это обходит и
`pointSizeRange` устройства.

## Начальное состояние пишет GPU

<Step file="26_particles" region="init" />

`init` вычисляет каждую частицу только по её индексу: 32-битный целочисленный хеш разбрасывает соседние индексы в
несвязанные битовые узоры, из которых получаются радиус и угол в диске радиуса 0,8, и каждая частица кружит вокруг
центра. Никаких случайных чисел с CPU, никакой загрузки: один dispatch из 4096 workgroup, отправленный один раз, и fence,
которого программа ждёт до первого кадра. Fence достаточно, чтобы *хост* узнал, что `init` закончил; а видимыми для
первого `simulate` записи `init` делает барьер в начале каждого кадра (ниже). Его первая область синхронизации включает
стадию compute всего, что раньше отправлено в очередь, в том числе `init`.

## Кадр: три конфликта и два барьера

Каждый кадр записывает в один command buffer:

<Step file="26_particles" region="simulate" />

<Step file="26_particles" region="draw" />

`simulate` обновляет буфер на месте: вызов `i` читает частицу `i` и записывает её обратно, других частиц не трогает,
поэтому ни один вызов не увидит наполовину обновлённого соседа и барьер *внутри* dispatch не нужен. Затем отрисовка
читает каждую частицу как вершину. Dispatch нельзя записывать внутри рендеринга, поэтому compute-работа идёт до
`vkCmdBeginRendering`.

Теперь перечислим, кто трогает буфер, в порядке очереди, при двух кадрах в полёте:

| Раньше | Позже | Конфликт | Что нужно |
|---|---|---|---|
| кадр n: `simulate` пишет (compute) | кадр n: отрисовка читает (вход вершин) | чтение после записи | зависимость памяти: сделать записи видимыми для `VERTEX_ATTRIBUTE_READ` |
| кадр n-1: отрисовка читает (вход вершин) | кадр n: `simulate` пишет (compute) | запись после чтения | только зависимость исполнения |
| кадр n-1: `simulate` пишет (compute) | кадр n: `simulate` читает и пишет | чтение после записи, запись после записи | зависимость памяти: видимость для `SHADER_STORAGE_READ \| WRITE` |

<Step file="26_particles" region="frame-barriers" />

Два барьера кадра закрывают всю таблицу:

- **Перед dispatch** — два барьера памяти в одном `vkCmdPipelineBarrier2`. Первый, `VERTEX_ATTRIBUTE_INPUT` / `NONE` →
  `COMPUTE_SHADER` / `NONE`, — это запись после чтения: dispatch не должен начать писать, пока выборка вершин
  предыдущего кадра, может быть, ещё читает. После чтения нечего делать доступным, так что маски доступа `NONE`
  правильны: конфликту WAR нужна только зависимость исполнения. Второй, `COMPUTE_SHADER` / `SHADER_STORAGE_WRITE` →
  `COMPUTE_SHADER` / `SHADER_STORAGE_READ | SHADER_STORAGE_WRITE`, делает результаты симуляции предыдущего кадра
  доступными и видимыми для этого.
- **Между dispatch и отрисовкой** — `COMPUTE_SHADER` / `SHADER_STORAGE_WRITE` → `VERTEX_ATTRIBUTE_INPUT` /
  `VERTEX_ATTRIBUTE_READ`: отрисовка этого кадра читает позиции этого кадра.

Барьеры перед dispatch дотягиваются до *предыдущего* кадра потому, что первая область pipeline barrier — это все
команды раньше по порядку отправки в ту же очередь, включая другие command buffer и другие отправки. По той же причине
один барьер прикрывал общее изображение глубины в [уроке о буфере глубины](lesson:depth), и по ней же барьер первого
кадра ставит `simulate` после `init`.

### Что увидела валидация синхронизации

Барьеры выше выведены из спецификации, а потом каждый по очереди убирался временной правкой (её откатывали), чтобы
посмотреть, что скажет валидация синхронизации. Сама по себе `VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true` не отслеживает,
к чему шейдеры обращаются через дескрипторы, поэтому в этих запусках была задана ещё и
`VK_KHRONOS_VALIDATION_SYNCVAL_SHADER_ACCESSES_HEURISTIC=true` ([что она видит, а что
нет](lesson:barriers-and-layouts#что-она-видит-а-что-нет)). Фрагменты сообщений, как они записаны в заметках проекта:

- без барьера compute → вершины: «vkCmdDraw(): READ_AFTER_WRITE hazard detected. vkCmdDraw reads vertex VkBuffer ...,
  which was previously written by vkCmdDispatch»;
- без барьера записи после чтения: «vkQueueSubmit2(): WRITE_AFTER_READ hazard detected. vkCmdDispatch ... writes to
  VkBuffer ..., which was previously read by vkCmdDraw ... Vulkan insight: an execution dependency is sufficient»;
- без барьера compute → compute: **ничего**, даже с эвристикой.

Последняя строка — весь урок в миниатюре: эвристика читает SPIR-V статически и, по её же описанию, может «ignore certain
types of accesses», и dispatch, который читает и пишет то, что записал предыдущий dispatch, проскочил мимо неё. Чистый
запуск значит, что инструмент ничего не нашёл, а не что ничего нет. Со всеми барьерами на месте шаг 26 при обеих
переменных отрабатывает без сообщений, кроме предупреждения слоя bandicam, на обоих языках.

## Почему хватает одного буфера

[Кадры в полёте](lesson:frames-in-flight) научили держать по копии на кадр всего, что кадр пишет: command buffer,
семафоры, а в [уроке об uniform-буферах](lesson:uniform-buffers) — по uniform-буферу на кадр. Почему же у шага 26 при
двух кадрах в полёте буфер частиц только *один*?

Потому что копии существуют для данных, которые пишет **CPU**. Uniform-буфер CPU пишет, пока GPU, возможно, ещё читает
из него содержимое предыдущего кадра; продвижение GPU CPU видит только через fence, поэтому надёжнее дать ему на каждый
кадр в полёте свой буфер. Частицы же пишет только GPU, а работу в одной очереди упорядочивают барьеры, как выше. CPU
буфер не трогает, значит, и дублировать нечего.

Цена барьеров — перекрытие на GPU: симуляция кадра n ждёт, пока закончится выборка вершин кадра n-1. Кадры в полёте
при этом делают своё дело — не дают ждать *CPU*: он записывает кадр n+1, пока GPU работает над кадром n. Сторона CPU в
кадре та же, что в шаге 10. А программа при старте описывает получившееся устройство кадра так:

```text
Per frame: barrier -> dispatch simulate 4096 x 1 x 1 -> barrier COMPUTE_SHADER/SHADER_STORAGE_WRITE -> VERTEX_ATTRIBUTE_INPUT/VERTEX_ATTRIBUTE_READ -> draw 1048576 points
2 frames in flight, ONE particle buffer: the GPU orders the frames with barriers, the CPU never touches it
```

Если симуляция кадра n+1 должна идти *во время* отрисовки кадра n, одного буфера уже мало: отрисовка читает состояние
n, пока симуляция пишет состояние n+1, значит, нужны два буфера, а GPU нужен повод выполнять их бок о бок. Это
[async compute](lesson:async-compute).

Шаг времени берётся из часов CPU, но не больше 1/60 с, чтобы застрявший кадр (окно тащат мышью, сработала точка
останова) не заставил шаг Эйлера перебросить частицы через всё окно; на GPU он едет в push-константах — единственных
данных кадра, которые производит CPU.

## Что под капотом

- **Одна память, два пути.** Compute-шейдер пишет буфер через путь загрузки и записи шейдерных ядер (кэши L1 и L2), а
  отрисовка читает его через путь выборки вершин. Барьер между ними — это обычно то место, где драйвер следит, чтобы
  записи дошли до уровня иерархии кэшей, общего для обоих путей (на настольных GPU — L2), и чтобы в кэше, из которого
  читает выборка вершин, не осталось устаревшей копии; и, конечно, ждёт, пока dispatch закончится.
- **Барьеры осушают конвейер.** В одной очереди барьер от `COMPUTE_SHADER` к `VERTEX_ATTRIBUTE_INPUT` обычно означает:
  дать workgroup dispatch закончить, прежде чем стартуют вершины отрисовки. На этот миг части GPU простаивают. Этот
  маленький пузырь в каждом кадре — одна из вещей, которые пытается заполнить [async compute](lesson:async-compute).
- **Точки дёшево растеризовать**, но 2^20 точек покрывают здесь всего около 175000 пикселей, так что большинство
  фрагментов перезаписывает пиксель, уже записанный другой частицей. При выключенном смешивании побеждает последняя
  частица в порядке примитивов; при аддитивном смешивании (обычный вид искр) порядок был бы неважен, а перерисовка
  превратилась бы в яркость.
