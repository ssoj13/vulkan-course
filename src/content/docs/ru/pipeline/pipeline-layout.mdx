Настоящие шейдеры читают данные снаружи: матрицу камеры, параметры материала, текстуры. До первой отрисовки пайплайн
должен знать *форму* всех этих данных — какие слоты существуют и какого они типа. Эта форма и есть **pipeline
layout**. Наш треугольник ничего не читает, так что его layout пуст — и всё равно обязателен. Почему, и что кладут в
layout, когда он не пуст?

## Место в курсе

Третий урок модуля «Графический пайплайн», короткий, но с далёким прицелом. Это чистый слой Vulkan API: layout —
договор между кодом на CPU и шейдерами, а во что его превращает драйвер, расскажет «Что под капотом».

`VkDescriptorSetLayout × N + диапазоны push-констант → VkPipelineLayout → VkPipeline`

[Pipeline layout](term:vk-pipeline-layout) построен на устройстве и, по желанию, на layout наборов дескрипторов.
[Графическому пайплайну](lesson:graphics-pipeline) он нужен обязательно; наполнит его содержимым модуль о
дескрипторах (uniform-буферы, наборы дескрипторов, push-константы, bindless). Здесь мы разбираемся, что layout
объявляет, и создаём пустой layout шага 08.

## Сигнатура, а не аргументы

Вспомните цифровой ассет (HDA) в Houdini. Его **интерфейс параметров** — какие параметры есть, как называются, какого
типа — фиксируется, когда ассет определён. **Значения** выставляются на каждом экземпляре и могут меняться хоть
каждый кадр.

Pipeline layout — интерфейс параметров пайплайна:

- **layout наборов дескрипторов** — группы слотов для ресурсов. У каждого слота (*binding*) есть номер, тип
  (uniform-буфер, текстура для выборки, storage-буфер...) и стадии, которые его видят. Одну группу описывает
  [layout набора дескрипторов](term:vk-descriptor-set-layout); pipeline layout перечисляет до
  `maxBoundDescriptorSets` таких групп (32 на GPU курса, `VUID-VkPipelineLayoutCreateInfo-setLayoutCount-00286`).
- **диапазоны push-констант** — небольшой блок байтов, записанный прямо в command buffer, для значений, которые
  меняются от отрисовки к отрисовке (индекс объекта, матрица). GPU курса разрешает `maxPushConstantsSize` = 256 байт в
  сумме.

Аргументы приходят позже и отдельно: наборы дескрипторов с настоящими буферами и изображениями *привязываются* во
время записи, а push-константы *заталкиваются* туда же. Layout говорит только, какой формы они будут. В шейдере та же
форма выглядит как номера `set` и `binding`, и layout пайплайна обязан совпадать с тем, что объявили шейдеры
(`VUID-VkGraphicsPipelineCreateInfo-layout-07988`).

Иерархия снаружи внутрь: **pipeline layout** → его **layout наборов дескрипторов** (set 0, set 1, ...) → их
**binding** (binding 0, 1, ...) → по **дескриптору** на binding (хэндл одного ресурса). А рядом с наборами —
**диапазоны push-констант**.

## 1. Пустой layout

<Step file="08_pipeline" region="pipeline-layout" />

Ни одного layout набора, ни одного диапазона push-констант: наши шейдеры пользуются только константами, вкомпилированными
в них самих. Объект всё равно нужен: графический пайплайн с шейдерными стадиями обязан назвать допустимый layout
(`VUID-VkGraphicsPipelineCreateInfo-layout-06602`; единственное исключение — новое расширение с кучей дескрипторов
(descriptor heap), которым курс не пользуется). Потом `layout(pipeline_layout)` в структуре создания из
[предыдущего урока](lesson:graphics-pipeline#3-создаём-пайплайн) передаёт его пайплайну.

## Почему layout отдельный объект

Если бы пайплайн описывал слоты своих ресурсов внутри себя, у каждого пайплайна была бы своя копия, и никто не мог бы
сказать, что два пайплайна принимают аргументы одного вида. Отдельным объектом layout можно делить:

- много пайплайнов можно создать с одним layout;
- наборы дескрипторов, привязанные для одного пайплайна, остаются привязанными, когда вы переключаетесь на другой
  пайплайн с совместимым layout. Спецификация точно определяет, когда два layout совместимы (одинаковые layout
  наборов до некоторого номера set, одинаковые диапазоны push-констант). Рендерер этим пользуется: данные кадра
  (камеру, свет) привязывают один раз в set 0, а потом переключают материалы и пайплайны, не трогая их.

Поэтому на карте объектов layout — родитель пайплайна, и поэтому модуль о дескрипторах начнётся именно с этого
объекта.

## Что под капотом

- Во что превращается layout, решает драйвер. Обычно он определяет, где для шейдеров будут лежать дескрипторы каждого
  набора и push-константы: в выделенных регистрах, в таблице, которую читает железо, или в памяти. Это распределение
  влияет на код шейдера — и это одна из причин, по которым layout должен быть известен при компиляции пайплайна.
- Push-константы дёшевы, потому что едут вместе с command buffer: не нужно ни выделять, ни обновлять буфер, значения
  записываются прямо рядом с отрисовкой. По той же причине места для них мало.
