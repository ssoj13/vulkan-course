Шестиугольник из модуля о памяти стоит на месте: его углы раз и навсегда записаны в vertex buffer. В настоящем вьюпорте
камера меняется каждый кадр, и шейдеру нужна новая матрица раньше, чем он поставит на место хоть одну вершину. Как
значение, которое CPU считает каждый кадр, попадает в шейдер? И как структура на C++ или Rust с одной стороны и
структура шейдера с другой договариваются, где лежит каждый её байт?

## Место в курсе

Первый урок модуля **«Дескрипторы»**: как шейдер получает данные, которые не являются атрибутами вершин. Слои снизу
вверх: структура на хосте и память, в которую её пишут (модуль о памяти); буфер, который читает шейдер (этот урок);
дескриптор, который говорит шейдеру, какой это буфер ([следующий урок](lesson:descriptor-sets)); и под всем этим правила
компилятора, раскладывающие члены структуры по байтовым смещениям. Цепочка:

`host struct (repr(C) / C++) → mapped HOST_VISIBLE memory → VkBuffer with UNIFORM_BUFFER usage → descriptor at set 0, binding 0 → ConstantBuffer<FrameUniforms> in Slang → SPIR-V block with Offset / MatrixStride decorations`

[Uniform-буфер](term:uniform-buffer) (UBO) — это [VkBuffer](term:vk-buffer), который шейдеры читают как блок констант,
одинаковых для всех вызовов одной отрисовки. Где лежат его члены, решает правило раскладки: [std140](term:std140) для
uniform-буферов, [std430](term:std430) для push-констант и storage-буферов или
[скалярная раскладка](term:scalar-block-layout); у матриц сверху ещё [раскладка матрицы](term:matrix-layout). CPU пишет
в буфер через [постоянное отображение](term:persistent-mapping). До этого: [vertex и index buffer](lesson:vertex-and-index-buffers)
(буферы в отображаемой памяти) и [кадры в полёте](lesson:frames-in-flight) (почему всё, что живёт один кадр, заводится
в двух экземплярах). Дальше: [descriptor set](lesson:descriptor-sets), потом более короткие дороги
[push-констант](lesson:push-constants).

## Параметры, а не геометрия

У шейдерной сети в Maya два вида входов. Данные точек приходят вместе с геометрией: позиции, нормали, UV — по значению
на вершину. Всё остальное — **параметры**: матрица камеры, цвет источника, номер кадра, одно значение на весь объект.
Вьюпорт выставляет параметры один раз и рисует с ними тысячи вершин.

В Vulkan то же разделение. Данные вершин приходят из vertex buffer через стадию vertex input. Данные отрисовки приходят
из **ресурсов**, которые шейдер читает напрямую: буферов и изображений, названных в шейдере номерами `set` и `binding`.
Самый простой такой ресурс — uniform-буфер. «Uniform» на языке шейдеров значит «одинаковое для всех вызовов»: каждая
вершина отрисовки видит одну и ту же матрицу.

Шаг 17 вращает шестиугольник шага 14. CPU каждый кадр строит матрицу 4x4 (поворот плюс поправка на соотношение сторон
окна), добавляет оттенок и время, а вершинный шейдер умножает на матрицу каждый угол.

## Сторона хоста

80 байт: матрица на смещении 0, `tint` на 64, `time` на 76. `repr(C)` в Rust и обычная структура в C++ дают ровно такие
смещения: каждый член — 4-байтовый float, а порядок подобран так, что выравнивание не требует пустых байт. `HOST_LAYOUT`
запоминает смещения на хосте через `offset_of!` (в C++ — `offsetof`), чтобы программа могла сравнить их со смещениями
шейдера.

<Step file="17_uniforms" region="transform" />

Матрица хранится как четыре столбца по четыре float, column-major, — соглашение GLM и glam. Математика — `S * R`:
поворот на `angle` вокруг z, затем масштаб по x на высоту / ширину, чтобы в окне 800x600 шестиугольник остался
правильным. Столбец 0 — `(aspect * cos, sin, 0, 0)`, это и есть первый столбец `S * R`.

## Правила раскладки: где лежит каждый байт

Неявной раскладки буферного блока в SPIR-V нет: смещение каждого члена, шаг каждого массива и шаг каждой матрицы
записаны в модуль декорациями. Числа выбирает компилятор по некоторому правилу, а Vulkan проверяет, что они подчиняются
его правилам выравнивания (раздел спецификации «Offset and Stride Assignment»). Важны три правила:

- **std140** (пришло из GLSL): векторы выровнены по своему размеру (3-компонентный — как 4-компонентный); массивы и
  структуры выровнены по 16 байт, и их размер округляется вверх до 16. В терминах Vulkan это *extended alignment*.
  Uniform-блоки обязаны ему следовать, если не включена возможность `uniformBufferStandardLayout`.
- **std430**: то же самое, но без округления массивов и структур до 16 — *base alignment*. По умолчанию его используют
  push-константы и storage-буферы.
- **scalar**: каждый член выровнен только по размеру своего компонента (`float3` — по 4 байта). Разрешено для
  uniform- и storage-блоков, push-констант и блоков buffer device address, если включена возможность
  `scalarBlockLayout`.

Каждое устройство Vulkan 1.2 поддерживает `uniformBufferStandardLayout`, а каждое устройство Vulkan 1.4 —
`scalarBlockLayout` (списки обязательных возможностей в спецификации). Но «поддерживается» ещё не значит «включено»:
программа, которой нужна любая из них, включает её при создании устройства. Шаг 17 не включает ни одну и оставляет
slangc std140, который принимает любое устройство. Под правилами спецификация оставила примечание: «Even if scalar
alignment is supported, it is generally more performant to use the base alignment.»

Насколько правила расходятся на деле? Мы скомпилировали одну пробную структуру slangc 2026.1 (тем, что в SDK) как
uniform-буфер, как push-константы и как storage-буфер, затем ещё раз с `-fvk-use-scalar-layout`, и прочитали декорации
`Offset` в выводе `spirv-dis` (2026-10-11):

```hlsl
struct Inner { float x; };
struct Probe { float3 a; float b; float3 c; float3 d; float e[2]; Inner s; float f; float2x2 m; float g; };
```

| Член | std140 (uniform-буфер) | std430 (push-константы, storage-буфер) | scalar (`-fvk-use-scalar-layout`) |
|---|---|---|---|
| `a` float3 | 0 | 0 | 0 |
| `b` float | 12 | 12 | 12 |
| `c` float3 | 16 | 16 | 16 |
| `d` float3 | 32 | 32 | **28** |
| `e` float[2] | **48**, ArrayStride 16 | 44, ArrayStride 4 | **40**, ArrayStride 4 |
| `s` struct Inner | **80** | 52 | **48** |
| `f` float | **96** | 56 | **52** |
| `m` float2x2 | **112**, MatrixStride 16 | 64, MatrixStride 8 | **56**, MatrixStride 8 |
| `g` float | **144** | 80 | **72** |
| шаг массива `Probe` в storage-буфере | (не используется) | 96 | 76 |

Читаем сверху вниз:

- `b` при любом правиле занимает последние 4 байта после float3 `a`: 3-компонентный вектор выровнен как
  4-компонентный, но длина у него 12 байт. Поэтому `FrameUniforms` может положить `time` на 76, сразу за `tint`.
- `d` — два float3 подряд. std140 и std430 начинают второй с ближайшей границы 16 байт, scalar кладёт его на 28.
  Структура на Rust или C++ с двумя `[f32; 3]` подряд тоже кладёт второй на +12, то есть совпадает **только** со
  scalar. Это классическая ошибка: хост пишет `d` на 28, шейдер читает его с 32.
- `e`: std140 отводит каждому элементу массива 16-байтовую ячейку, и `float[2]` занимает 32 байта; std430 и scalar
  обходятся шагом 4.
- `s`: std140 выравнивает член-структуру по 16 и округляет её размер до 16, так что сдвигается и следующий член.
- `m`: `float2x2` хранится как два вектора по 2 float. std140 округляет их шаг до 16, остальные правила берут 8. У
  матриц, хранимые векторы которых состоят из 3 или 4 float (как `float4x4` шага 17), шаг 16 и в std140, и в std430.

`FrameUniforms` спроектирована так, чтобы попасть туда, где все три правила согласны: матрица из 16-байтовых столбцов,
потом один float3 и за ним один float. Большинство движков поступают так же или добивают структуру явными членами
`_pad`, чтобы на хосте она читалась как обычная структура C.

### Матрицы: RowMajor, который значит column-major

Матрице нужно ещё одно решение: что лежит в памяти — её строки или её столбцы? SPIR-V говорит это для каждого члена
декорацией `RowMajor` или `ColMajor`, а `MatrixStride` — расстояние в байтах между двумя соседними хранимыми векторами.
По умолчанию Slang хранит матрицы column-major: подряд идущие float спускаются по столбцу, как в GLM, glam, Eigen или в
`MMatrix` Maya, сложенной по столбцам. И всё же в SPIR-V написано `RowMajor`:

```text
OpMemberDecorate %FrameUniforms_std140 0 RowMajor
OpMemberDecorate %FrameUniforms_std140 0 MatrixStride 16
%143 = OpVectorTimesMatrix %v4float %142 %30
```

Ошибки здесь нет. Slang следует HLSL, где `M[i]` — это строка `i`, и отображает строку HLSL в *столбец* SPIR-V: матрица
в SPIR-V — транспонированная версия той, что написана в исходнике. То, что HLSL называет column-major (память идёт
вниз по столбцу HLSL), для транспонированной матрицы SPIR-V — проход вдоль строки, отсюда `RowMajor`. Умножение
меняется вслед за этим: `mul(M, v)` со столбцом `v` превращается в `OpVectorTimesMatrix` (`v` на транспонированную
матрицу) — числа те же. Два транспонирования взаимно уничтожаются, и в памяти лежит то, чего ждёт хост: четыре столбца
через 16 байт. С флагом `-matrix-layout-row-major` slangc выдал бы `ColMajor`, и хосту пришлось бы загружать строки.

Картинка это подтверждает. Если бы хост загрузил строки, шейдер умножал бы на транспонированную матрицу,
`(S * R)ᵀ = R(-angle) * S`: сначала масштаб, потом поворот, причём в обратную сторону. Шестиугольник получился бы
сплюснутым, а не правильным, и вращался бы назад. На скриншоте он правильный:

## Доверяй, но читай SPIR-V

Во время работы Vulkan ничего из этого не проверяет. Если хост пишет `time` на 76, а шейдер читает его с 80, ни один
вызов не вернёт ошибку и слой валидации промолчит: шейдер просто прочитает не те байты. Поэтому шаг 17 проверяет всё
сам, до всего остального, — читает данные [рефлексии SPIR-V](term:spirv-reflection) прямо из модуля, который собирается
использовать:

<Step file="17_uniforms" region="reflect" />

Модуль SPIR-V — поток 32-битных слов: заголовок из 5 слов, затем инструкции, в первом слове которых записаны число слов
и опкод. `reflect` собирает шесть нужных ему инструкций (имена, имена членов, типы указателей, переменные, декорации
`DescriptorSet` / `Binding` и декорации членов `Offset` / `RowMajor` / `ColMajor` / `MatrixStride`), находит переменную
в set 0, binding 0, идёт по её типу-указателю к структуре и перечисляет члены. Библиотеки вроде SPIRV-Reflect или
`slangc -reflection-json` на этапе сборки делают то же самое и больше; здесь важно увидеть своими глазами, что раскладка
действительно лежит в модуле.

<Step file="17_uniforms" region="check-layout" />

Имя и смещение каждого члена должны совпасть с хостовыми, а матрица должна быть `RowMajor` с `MatrixStride 16` (на
хосте — четыре 16-байтовых столбца). Иначе программа отказывается стартовать. Когда в качестве негативного теста
`transform.spv` однажды собрали с `-matrix-layout-row-major`, шаг 17 остановился с сообщением:

```text
Error: "layout mismatch: shader transform is ColMajor MatrixStride 16, host expects RowMajor MatrixStride 16"
```

## По буферу на каждый кадр в полёте

Данные готовы; где они живут? В полёте два кадра, поэтому, пока CPU готовит кадр N, GPU ещё может выполнять вершинный
шейдер кадра N−1, который читает свою матрицу. С одним буфером на двоих CPU мог бы переписать матрицу, которую GPU как
раз читает. Поэтому каждый слот кадра получает собственный uniform-буфер, рядом со своим command buffer и fence:

<Step file="17_uniforms" region="frame-resources" />

<Step file="17_uniforms" region="uniform-buffers" />

Каждый буфер — 80 байт с usage `UNIFORM_BUFFER`, в первом типе памяти с `HOST_VISIBLE | HOST_COHERENT`; на GPU курса это
тип 3 (системная RAM). С uniform-буферами приходят два лимита:

- `maxUniformBufferRange` — наибольший диапазон, который может охватить один дескриптор uniform-буфера: здесь 65536 байт.
  Vulkan 1.0 гарантирует 16384; Vulkan 1.4 поднял минимум до 65536, ровно столько и сообщает этот GPU. Данным крупнее
  место в storage-буферах ([урок о bindless](lesson:bindless)).
- `minUniformBufferOffsetAlignment`: здесь 64 (спецификация допускает до 256). Дескриптор может указывать на смещение
  внутри большого буфера, но смещение должно быть кратно этому числу (`VUID-VkWriteDescriptorSet-descriptorType-00327`).
  По той же причине в уроке о памяти выравнивание буфера подскочило до 64, как только появился `UNIFORM_BUFFER`.

Частая альтернатива двум буферам — один буфер со слотом на кадр по смещениям 0, 128, … и дескриптор
`UNIFORM_BUFFER_DYNAMIC`, смещение которого передаётся при привязке (`pDynamicOffsets`, снова кратное выравниванию:
`VUID-vkCmdBindDescriptorSets-pDynamicOffsets-01971`). Идея та же, объектов меньше; шаг 17 держит два буфера, чтобы
каждая строка была очевидна.

### Постоянное отображение

Каждый буфер отображается **один раз**, сразу после создания, и указатель живёт всё время работы программы. Шаги 14
и 15 отображали, копировали и снимали отображение — для данных, которые пишутся один раз, это нормально. Для данных,
которые пишутся каждый кадр, отображать заново каждый раз — бессмысленный вызов; [постоянное
отображение](term:persistent-mapping) — обычная практика, и снимать его Vulkan не требует: «If a memory object is
mapped at the time it is freed, it is implicitly unmapped.» Указатель выровнен минимум на `minMemoryMapAlignment`
(здесь 64) — этого хватает, чтобы записать структуру целиком.

## Записываем значения кадра

<Step file="17_uniforms" region="update-uniforms" />

Порядок важен, и это порядок [кадров в полёте](lesson:frames-in-flight#1-ждём-слот-а-не-последний-кадр): сначала ждём
fence слота — он говорит, что GPU закончил кадр, который последним занимал этот слот, а значит, и его uniform-буфер; и
только потом пишем. Одна запись структуры через указатель, без `memcpy` отдельных членов: на старте мы доказали, что
раскладки совпадают.

Ни flush, ни барьера: память `HOST_COHERENT`, поэтому запись сама становится доступной (available) в домене хоста, а
`vkQueueSubmit2` несколькими строками ниже делает её видимой (visible) вершинному шейдеру. Это то же правило упорядочения
записей хоста, на которое [урок о staging](lesson:staging-uploads#записываем-копирование) опирался для источника
копирования.

<Aside type="note" title="Системная RAM или VRAM?">
Тип 3 — системная RAM: каждый кадр GPU читает эти 80 байт по PCIe, а дальше из своих кэшей, потому что все вершины
отрисовки читают одни и те же адреса. Для 80 байт это ничего заметного не стоит. Для крупных данных кадра (сотни
матриц) обычный дом — [куча BAR](lesson:staging-uploads#сколько-стоит-каждая-дорога): `DEVICE_LOCAL | HOST_VISIBLE`,
CPU пишет через шину, GPU читает из VRAM.
</Aside>

## Что под капотом

- **Зачем отдельный вид буфера?** «Одно значение для всех вызовов» железо обрабатывает особо. Обычно у GPU есть для
  таких данных путь дешевле обычных загрузок из памяти: кэш констант, а на многих архитектурах — загрузка в регистры,
  общие для всего варпа (скалярные регистры у AMD). Как именно драйвер сводит uniform-буфер к этому пути — его дело;
  флаг usage и тип дескриптора лишь сообщают ему, какие данные под это подходят.
- **Раскладка зафиксирована раньше, чем драйвер что-то увидит.** `Offset` и `MatrixStride` записывает компилятор
  шейдеров, а компилятор драйвера им только следует. Поэтому ошибки раскладки API не видит: «неправильного» смещения не
  бывает, пока оно соблюдает правила выравнивания, — бывает только смещение, не совпадающее с хостовым.
- **Когерентная память через PCIe.** 80-байтовая запись CPU уходит в системную RAM; GPU забирает её по шине, когда
  отрисовка начинает её читать. Записи, видимые в домене хоста к моменту отправки, — это то, что увидит первое чтение
  GPU; в этом весь контракт. А ожидание fence перед записью не даёт CPU обогнать предыдущее использование того же
  буфера.
