Шагу 17 понадобились layout набора, пул, два набора, два буфера, два постоянных отображения и вызов обновления — и всё
ради 80 байт на кадр. Для текстур и больших данных эта машинерия окупается, но для одной матрицы её многовато. Нет ли
дороги покороче? В Vulkan их две: записать в command buffer сами **байты** или записать туда **дескриптор** вместо
набора. Что стоит каждая, что она экономит и где её пределы?

## Место в курсе

Третий урок модуля **«Дескрипторы»**. Данные те же, что в [уроке об uniform-буферах](lesson:uniform-buffers), тот же
файл шейдера, тот же шестиугольник; меняется только дорога от CPU к шейдеру. Цепочки:

`push constants: host struct → vkCmdPushConstants (bytes copied into the command buffer at record time) → push constant range in the pipeline layout → [[vk::push_constant]] block (std430)`

`push descriptors: uniform buffer per frame → vkCmdPushDescriptorSet (descriptor copied into the command buffer) → set layout with PUSH_DESCRIPTOR → set 0, binding 0 in the shader`

[Push-константы](term:push-constant) — небольшой блок байт, который хранится прямо в command buffer; объявляет его
диапазон push-констант в [pipeline layout](term:vk-pipeline-layout). [Push-дескрипторы](term:push-descriptor) — это
[дескрипторы](term:descriptor), которые хранятся в command buffer, а не в [descriptor set](term:vk-descriptor-set), для
[layout набора](term:vk-descriptor-set-layout), созданного с `PUSH_DESCRIPTOR`. До этого: [наборы
дескрипторов](lesson:descriptor-sets). Дальше: [buffer device address](lesson:buffer-device-address), где вместо
дескриптора передаётся 8-байтовый указатель.

## Три способа передать шейдеру одни и те же 80 байт

Возьмём цифровой ассет в Houdini. Его параметры можно задать тремя способами: связать их с отдельной нодой параметров,
которую читают многие ассеты (uniform-буфер за descriptor set); прямо в сети указать ассету на другую ноду параметров
(push-дескриптор); или вбить значения прямо в сам ассет (push-константы). Значения одни и те же; различается, где они
хранятся и сколько подготовки требует каждый путь.

Шаг 18 умеет ходить двумя дорогами; третья, descriptor set, — это шаг 17:

По умолчанию — push-константы; `--push-descriptor` выбирает push-дескрипторы.

## Сколько помещается

<Step file="18_push_constants" region="limits" />

```text
Limits: maxPushConstantsSize = 256 bytes (at least 128 everywhere), maxPushDescriptors = 32
```

- `maxPushConstantsSize` — размер всего блока push-констант, на все стадии вместе. Vulkan 1.0 гарантирует 128 байт —
  отсюда старый совет «128 — переносимый бюджет». **Vulkan 1.4 поднял минимум до 256** (таблица обязательных лимитов в
  спецификации: «128 (Vulkan Core)» и «256 (Vulkan 1.4)»); GPU курса сообщает ровно 256. Программа, требующая
  устройство 1.4, как весь этот курс, может рассчитывать на 256; 128 важны только для устройств ниже 1.4. Строка самой
  программы говорит «at least 128 everywhere» — это остаётся верным для любого устройства Vulkan.
- `maxPushDescriptors` — сколько дескрипторов может держать один layout набора с push-дескрипторами: не меньше 32,
  здесь ровно 32.

Два `float4x4` — это 128 байт, так что матрица модели и матрица model-view-projection влезают даже в старый минимум, а в
256 помещаются четыре матрицы. Всё, что больше, едет в буферах.

## Дорога 1: push-константы

### Диапазон объявляет pipeline layout

<Step file="18_push_constants" region="push-constant-range" />

Layout набора нет вовсе: в pipeline layout один `VkPushConstantRange` (стадия VERTEX, смещение 0, размер 80). Диапазон
должен влезать в лимит (`VUID-VkPushConstantRange-size-00298`), и каждая стадия может встречаться не больше чем в одном
диапазоне (`VUID-VkPipelineLayoutCreateInfo-pPushConstantRanges-00292`): вершинный и фрагментный шейдеры могут
поделить блок на два диапазона или разделить один диапазон, указанный для обеих стадий.

Со стороны шейдера `[[vk::push_constant]] ConstantBuffer<FrameUniforms> pushed` — блок в классе памяти
`PushConstant`, и Slang раскладывает его по **std430** (структура в SPIR-V называется `FrameUniforms_std430`). Для
`FrameUniforms` это даёт те же смещения, что std140 (0, 64, 76), поэтому одна структура хоста обслуживает оба шага;
таблица в [уроке об uniform-буферах](lesson:uniform-buffers#правила-раскладки-где-лежит-каждый-байт) показывает
структуры, где правила расходятся.

### Записываем байты

<Step file="18_push_constants" region="push-constants" />

`vkCmdPushConstants` копирует 80 байт **в command buffer, в момент записи команд**. В этом весь фокус: буфера нет, а
значит, нет и ничего, что GPU прочитает позже и что CPU мог бы переписать слишком рано. Посмотрите, чего в этом шаге
больше нет:

<Step file="18_push_constants" region="frame-resources" />

На пути push-констант в слоте кадра нет ни одного буфера. Матрицу не охраняет никакой fence: у каждого command buffer
своя копия. Остаются правила самой записи:

- «When a command buffer begins recording, all push constant values are undefined»: в каждом command buffer записывайте
  push-константы до первой отрисовки, которая их читает;
- смещение и размер кратны 4 (`VUID-vkCmdPushConstants-offset-00368`, `VUID-vkCmdPushConstants-size-00369`), и каждый
  записанный байт должен лежать в диапазоне layout для каждой названной стадии (`VUID-vkCmdPushConstants-offset-01795`);
- запись инкрементальна: последующая запись байт 64..80 меняет только их, а отрисовка видит значения, записанные до
  неё. Поэтому значения на объект получаются сами собой: push, draw, push, draw.
- «Binding a pipeline with a layout that is not compatible with the push constant layout does not disturb the push
  constant values», но в момент отрисовки layout привязанного пайплайна должен быть совместим с layout, через которые
  значения записывали.

Как их характеризует сама спецификация: «Push constants represent a high speed path to modify constant data in
pipelines that is expected to outperform memory-backed resource updates.»

## Дорога 2: push-дескрипторы

Push-константы несут байты; для буфера или текстуры по-прежнему нужен дескриптор. Push-дескриптор — средний путь:
ресурс остаётся в памяти, а его дескриптор записывается в command buffer, без пула и без набора.

### Возможность ядра, которую надо включить

<Step file="18_push_constants" region="device-features" />

Push-дескрипторы были расширением `VK_KHR_push_descriptor` и вошли в ядро Vulkan 1.4 возможностью `pushDescriptor` в
`VkPhysicalDeviceVulkan14Features`. Каждое устройство 1.4 обязано её поддерживать (она есть в списке возможностей,
обязательных для 1.4), но поддерживаемая возможность выключена, пока программа её не включит:

> `VUID-vkCmdPushDescriptorSet-None-10356`: If the VK_KHR_push_descriptor extension is not enabled, pushDescriptor must
> be enabled

Шаг 18 включает её только на пути `--push-descriptor`; push-константы существуют с Vulkan 1.0 и ничего не требуют.
Разницу видно в выводе: «VkDevice created with VK_KHR_swapchain + feature pushDescriptor».

### Layout набора получает флаг

<Step file="18_push_constants" region="push-descriptor-layout" />

Layout набора из шага 17 плюс `PUSH_DESCRIPTOR`. Наборы с таким layout никогда не выделяются, пула нет. С флагом
приходят два правила:

- не больше одного набора с push-дескрипторами на pipeline layout
  (`VUID-VkPipelineLayoutCreateInfo-pSetLayouts-00293`), и номер набора в `vkCmdPushDescriptorSet` должен быть именно
  его номером (`VUID-vkCmdPushDescriptorSet-set-00365`);
- layout держит не больше `maxPushDescriptors` дескрипторов (`VUID-VkDescriptorSetLayoutCreateInfo-flags-00281`).

### Записываем дескриптор

<Step file="18_push_constants" region="push-descriptor" />

Та же `VkWriteDescriptorSet`, что при обновлении в шаге 17, «except the `dstSet` member is ignored», переданная в
`vkCmdPushDescriptorSet` вместе с pipeline layout и номером набора. Спецификация: «Push descriptors are a small bank of
descriptors whose storage is internally managed by the command buffer rather than being written into a descriptor set
and later bound to a command buffer.»

Копируется **дескриптор**, а не данные. Сами 80 байт по-прежнему живут в uniform-буфере слота и пишутся через постоянное
отображение после ожидания fence — в точности как в шаге 17. Значит, путь push-дескрипторов сохраняет буферы на слот и
дисциплину fence, а выбрасывает пул, наборы и вызов обновления. Как и push-константы, push-дескрипторы в начале записи
не определены. Записи инкрементальны: push перезаписывает только свои дескрипторы, остальные сохраняют значения для
последующих отрисовок — пока набор не испортят (правила из [урока о наборах
дескрипторов](lesson:descriptor-sets#2-pipeline-layout-перечисляет-layout-наборов-по-номерам)) или пока дескрипторы не
запишут с другим layout набора; тогда «all push descriptors are undefined». В шаге 18 один binding, и он записывается
каждый кадр, так что каждый push просто заменяет его.

Ещё спецификация замечает: «Push descriptors do not use dynamic offsets. Instead, the corresponding non-dynamic
descriptor types can be used and the offset member of `VkDescriptorBufferInfo` can be changed each time the descriptor
is written». То есть один большой буфер со слотом на кадр или на объект и новое смещение в каждом push.

## Три дороги рядом

Шаг 18 сам печатает сравнение:

<Step file="18_push_constants" region="compare" />

```text
Setup for the per-frame FrameUniforms:
  descriptor sets (step 17): set layout + pool + 2 sets + 2 uniform buffers + vkUpdateDescriptorSets; per frame: write buffer, bind set
  push descriptors:          set layout (PUSH_DESCRIPTOR) + 2 uniform buffers; per frame: write buffer, vkCmdPushDescriptorSet
  push constants:            a push constant range in the pipeline layout; per frame: vkCmdPushConstants (80 bytes)
```

| | Наборы дескрипторов | Push-дескрипторы | Push-константы |
|---|---|---|---|
| Где живут данные | в буфере | в буфере | в command buffer |
| Где живёт дескриптор | в наборе из пула | в command buffer | (его нет) |
| Что создать | layout набора, пул, наборы, буферы | layout набора, буферы | диапазон в pipeline layout |
| Предел размера | `maxUniformBufferRange` (здесь 65536) на буфер | то же на буфер; `maxPushDescriptors` (32) дескрипторов | `maxPushConstantsSize` (256) байт всего |
| Может держать текстуры | да | да | нет (только байты) |
| Правило времени жизни для CPU | буфер и набор не меняются, пока pending | буфер не меняется, пока pending | нет: копируется при записи |
| Переиспользуется между command buffer | да, привязать тот же набор | нет, push в каждом | нет, push в каждом |
| Версия Vulkan | 1.0 | ядро 1.4 (возможность `pushDescriptor`) | 1.0 |

Как выбирать, если коротко: значения на отрисовку, которые помещаются, — в push-константы; несколько ресурсов на
отрисовку (целевая текстура post-process прохода, временный буфер) — в push-дескрипторы; данные, общие для многих
отрисовок и привязанные надолго, или большие таблицы ресурсов — в наборы ([bindless](lesson:bindless) доводит это до
предела).

<Aside type="note" title="Чего мы не измеряли">
На машине курса все три дороги рисуют этот шестиугольник с одной скоростью (2300–2800 кадров в секунду в этих
запусках, упор во всё остальное в кадре); одна отрисовка на кадр не может показать цену работы с дескрипторами.
«High speed path» push-констант — ожидание спецификации, а не замер этого курса.
</Aside>

## Что под капотом

- **Push-константы**: обычно драйвер кладёт байты в константную память на кристалле (регистры или небольшую
  константную область) в момент отрисовки, перенося их в потоке команд, который он строит из command buffer. Так
  обычно и объясняют, почему они быстрые и почему места мало; спецификация же говорит только, что это «a high speed path
  ... that is expected to outperform memory-backed resource updates». Если на железе места меньше, чем блок, драйвер
  может держать часть в памяти; API эту разницу прячет.
- **Push-дескрипторы** превращаются в байты дескрипторов, которые драйвер пишет в память, управляемую им для каждого
  command buffer («small bank» из спецификации), а binding указывает шейдеру на них — так же, как набор. Экономия — на
  стороне приложения: нет пула, который надо рассчитать, и нет времени жизни набора, за которым надо следить.
- **Почему только один набор с push-дескрипторами на layout?** Спецификация даёт правило без объяснения. Она говорит, что
  «there is a separate set of push descriptor bindings for each pipeline type», — один банк на точку привязки; единственный
  номер набора на layout держит этот банк в одном фиксированном слоте layout. Вероятно, причина в этом (это наше
  прочтение, не слова спецификации).
