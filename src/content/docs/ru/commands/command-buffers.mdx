Всё, что было до сих пор, — *настройка*: объекты, которые создаются один раз. С рисованием иначе. GPU никогда не
выполняет вызов Vulkan в тот момент, когда мы его делаем: сначала работа записывается, а потом передаётся целиком.
Куда она записывается, что значит «запись» и как записанная работа добирается до GPU?

## Место в курсе

Урок открывает модуль «Команды и первый треугольник», последний шаг перед пикселями на экране. Сама идея не нова: в
уроке [о разговоре с GPU](lesson:talking-to-gpu) command buffer и очереди встретились нам на слое понятий. Теперь они
спускаются на слой Vulkan API и становятся объектами и вызовами, а в «Что под капотом» мы дойдём до слоя загрузчика и
драйвера и до командного процессора в слое железа:

`семейство очередей → VkCommandPool → VkCommandBuffer → запись (vkCmd*) → vkQueueSubmit2 → VkQueue → GPU`

[Command pool](term:vk-command-pool) построен на устройстве и **одном семействе очередей**;
[command buffer](term:vk-command-buffer) выделяется из пула; отправка идёт в очередь того же семейства.
[Первый треугольник](lesson:first-triangle) записывает и отправляет по одному command buffer на кадр, вместе с fence и
семафорами, которые держат кадры в порядке.

## Записать сейчас, выполнить потом

Хорошая картинка — рендер-ферма. Вы не ходите по нодам и не набираете команды на каждой: вы пишете скрипт задания,
отправляете его в очередь и занимаетесь своими делами, а ферма выполнит его позже, по своему расписанию.

Command buffer — это скрипт задания, а [запись команд](term:recording) (recording) — его написание: каждый вызов
`vkCmd*` (привязать пайплайн, задать viewport, нарисовать, вставить барьер) добавляет команду в буфер на CPU. Пока идёт
запись, до GPU не доходит ничего. Только [отправка](term:submission) (`vkQueueSubmit2`) передаёт готовый буфер в
очередь, и GPU выполнит его, когда до него дойдёт, — возможно, когда CPU уже записывает следующий кадр.

Это разделение и делает Vulkan быстрым на стороне CPU: запись — обычная запись в память, её можно вести в нескольких
потоках сразу, а записанный буфер можно разглядывать, переиспользовать или выбросить, вообще не беспокоя GPU.

У command buffer есть чётко определённые состояния:

1. **initial** — только что выделен или сброшен, пуст;
2. **recording** — между `vkBeginCommandBuffer` и `vkEndCommandBuffer`;
3. **executable** — записан и готов к отправке;
4. **pending** — отправлен, GPU с ним ещё не закончил. В этом состоянии его нельзя перезаписывать и освобождать;
5. **invalid** — например, буфер с флагом one-time-submit после выполнения или буфер, ресурсы которого уничтожены.

## 1. Очередь

<Step file="09_triangle" region="get-queue" />

Та самая единственная очередь, которую мы заказали в [шаге 05](lesson:logical-device#4-получаем-очередь). Сама очередь
ничего не записывает: она *выполняет* command buffer (`vkQueueSubmit2`) и *показывает* изображения
(`vkQueuePresentKHR`).

## 2. Command pool

<Step file="09_triangle" region="command-pool" />

Command pool — это память, из которой выделяются command buffer. Пул привязан к **одному семейству очередей**,
потому что команды кодируются для определённого вида аппаратного движка; буфер из него можно отправлять только в
очереди этого семейства (`VUID-vkQueueSubmit2-commandBuffer-03878`).

Флаг `RESET_COMMAND_BUFFER` позволяет сбрасывать каждый буфер пула по отдельности. Без него буфер сбрасывается только
вместе со всем пулом (`vkResetCommandPool`), а сброс отдельного буфера — нарушение правил
(`VUID-vkResetCommandBuffer-commandBuffer-00046`). Мы перезаписываем один и тот же буфер каждый кадр, так что флаг
нам нужен.

Пулы не потокобезопасны: два потока не должны одновременно записывать в буферы одного пула. Поэтому многопоточный
рендерер заводит каждому потоку свой пул.

## 3. Command buffer

<Step file="09_triangle" region="command-buffer" />

`vkAllocateCommandBuffers` берёт буферы из пула. **Первичные** (primary) буферы отправляются в очередь;
**вторичные** (secondary) записываются отдельно и выполняются изнутри первичного (это удобно для записи в нескольких
потоках). С одним кадром в полёте нам хватит одного первичного буфера. Command buffer не уничтожают по одному: они
уходят вместе со своим пулом.

## 4. Начинаем запись

<Step file="09_triangle" region="begin-recording" />

Каждый кадр начинается со сброса буфера (обратно в *initial*) и начала записи (*recording*). `ONE_TIME_SUBMIT`
обещает драйверу, что эту запись отправят один раз, а потом сбросят и запишут заново; драйвер может воспользоваться
обещанием для оптимизации, а после выполнения буфер становится *invalid*, пока его не сбросят. Всё, что записывается
между этим местом и `vkEndCommandBuffer` — барьеры, рендеринг, отрисовка, — тема
[первого треугольника](lesson:first-triangle).

## 5. Отправка

<Step file="09_triangle" region="submit" />

`vkQueueSubmit2` (версия из synchronization2, в ядре с Vulkan 1.3) отправляет один или несколько **пакетов** (batch).
Пакет несёт:

- **command buffer** для выполнения, по порядку;
- **семафоры ожидания**, каждый со своей *маской стадий*: работа этого пакета на GPU может дойти до этой стадии, пока
  семафор не просигналили, но дальше — нет;
- **семафоры сигнала** — каждый сигналится, когда *вся* работа пакета в указанной стадии и во всех более ранних
  стадиях завершена;
- и на весь вызов — необязательный **fence**, который сигналится, когда всё отправленное выполнено.

В нашем кадре пакет ждёт полученное изображение swapchain только на стадии `COLOR_ATTACHMENT_OUTPUT`: вершинный
шейдер может уже работать, пока presentation engine ещё отпускает изображение, и ждать нужно только записи цвета.
Зачем вообще нужны семафоры и fence, рассказывает [первый треугольник](lesson:first-triangle#цикл-кадра), а полная
теория — модуль 7.

`vkQueueSubmit2` возвращается сразу. Для CPU отправка дешёвая: сама работа произойдёт позже, на GPU.

## Собери сам

Command pool принадлежит устройству, его буферы — пулу. Выделите буфер, а потом уничтожьте пул, пока буфер
существует: пул освободит его сам. Попробуйте и уничтожить буфер отдельно — и сравните.

## Что под капотом

- Запись — это драйвер, который пишет собственный командный формат GPU в память, выделенную из пула: пакеты, которые
  задают состояние, указывают на пайплайн, запускают отрисовки. Это и есть «кодирование» из урока
  [о разговоре с GPU](lesson:talking-to-gpu); `vkCmdDraw` стоит CPU примерно столько же, сколько запись нескольких
  слов.
- При отправке драйвер передаёт эти пакеты аппаратному движку очереди: добавляет буфер в кольцо работы очереди и
  сообщает GPU, что работы прибавилось. Дальше [командный процессор](term:command-processor) сам читает буфер из
  памяти.
- Буфер в состоянии *pending* ещё читается GPU. Перезаписать его в этот момент значило бы переписать память, которую
  GPU читает, поэтому шаг 09 ждёт fence, прежде чем его сбросить.
