A Vulkan program is a tree of **objects**. Learning Vulkan is mostly learning this tree: what each object is, what it
is made from, and when it must be destroyed. Here is the whole tree. Click any box.

## How to read the map

- **An arrow from A to B** means "B is made from A": you pass A when you create B. A device is made from a physical
  device; a command buffer is made from a command pool.
- **Top to bottom is creation order.** You cannot create a box before the boxes that point to it.
- **Bottom to top is destruction order.** Children must be destroyed before their parents. Destroying the device while
  a buffer made from it is alive is an error.

<Aside type="tip" title="CG analogy">
It is a Houdini network where every node is created by you and never deleted automatically. Delete an upstream node
while downstream nodes still reference it and you get broken references - in Vulkan, a crash or garbage on screen.
</Aside>

## Handles

You never hold a Vulkan object itself. You hold a **handle**: an opaque value that names an object living inside the
loader or driver (`VkInstance`, `VkDevice`, `VkBuffer`...). There are two kinds:

- **Dispatchable handles** - in core Vulkan `VkInstance`, `VkPhysicalDevice`, `VkDevice`, `VkQueue`,
  `VkCommandBuffer` - are real pointers. The loader uses them to find which driver should receive a call.
- **Non-dispatchable handles** - everything else - are 64-bit values whose meaning is up to whoever owns the object:
  usually the driver, sometimes the loader or a layer (a debug messenger, for example).

## Four ways to get an object

| How | Calls | Who destroys it |
| --- | --- | --- |
| create | `vkCreateX` / `vkDestroyX` | you |
| allocate from a pool | `vkAllocateX` / `vkFreeX`, or destroy the pool (resetting a descriptor pool also frees its sets) | you, or the pool |
| enumerate | `vkEnumeratePhysicalDevices` | nobody - it lives as long as its parent |
| get | `vkGetDeviceQueue`, `vkGetSwapchainImagesKHR` | nobody - its owner does |

## The shape of every create call

Almost every creation looks the same:

```c
VkFooCreateInfo info = {
    .sType = VK_STRUCTURE_TYPE_FOO_CREATE_INFO, // which struct this is
    .pNext = NULL,                              // optional chain of extension structs
    /* ...the parameters... */
};
VkFoo foo;
VkResult r = vkCreateFoo(parent, &info, NULL /* allocator */, &foo);
```

- `sType` tells the driver which struct it is looking at; `pNext` lets you hang extra structs onto it (we use that in
  lessons 7, 8 and 10). The Rust and C++ bindings fill `sType` for you.
- Every call that can fail returns a `VkResult`. `VK_SUCCESS` is 0; errors are negative.

## Underneath

- Dispatchable handles start with a pointer to a **dispatch table**. When you call `vkCreateBuffer(device, ...)`, the
  loader reads that table from `device` and jumps to the right driver's function. That is how several GPUs from
  different vendors can work in one program.
- Because the driver does not check anything (lesson 3), using a destroyed handle is undefined behavior: it may work,
  crash, or corrupt something else. Validation layers catch it.
