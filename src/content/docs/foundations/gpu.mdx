Vulkan is a way to give work to a GPU. Before we talk to it, let us see what kind of machine it is, because almost
every strange rule in Vulkan comes from the shape of this machine.

## Where this fits

This is where the whole stack starts: the **hardware** layer. Nothing comes before it, and every later layer (the
driver, the loader, the Vulkan objects) exists only to feed this machine with work. The chain inside the chip:

`GPU → SMs / CUs → warps (lockstep groups) → threads, one per pixel or vertex`, plus `VRAM` next to it.

A GPU is built from SMs, an SM runs warps, a warp is a group of threads that share one instruction stream. Keep that
picture: when Vulkan later asks for big batches, explicit memory placement and explicit synchronization, the reason is
always somewhere in this lesson. Next, [how a program gets work onto it](lesson:talking-to-gpu).

## Two kinds of processors

A **CPU** has a few big, clever cores (8–24 on a desktop). Each core runs one long, branchy program very fast: it
predicts branches, reorders instructions, and has large caches so it rarely waits for memory. It is a team of a few
senior artists who can each handle any shot.

A **GPU** has thousands of small, simple cores. They are bad at decisions and great at doing *the same thing to a lot
of data*. It is a render farm: each node is modest, but there are thousands of them and they all run the same job.

<Aside type="tip" title="You already think this way">
A Houdini **Point Wrangle** is GPU thinking. You write one small VEX snippet; Houdini runs it for every point, with
`@P` and `@ptnum` different each time. A pixel shader is exactly that: one small program, run for every pixel.
</Aside>

## Lockstep groups

The cores are not independent. They are grouped into bundles that execute **the same instruction at the same time**
on different data: a *warp* of 32 threads on NVIDIA, a *wavefront* of 32 or 64 on AMD. The groups live inside bigger
blocks: NVIDIA calls them **SMs** (streaming multiprocessors), AMD calls them **CUs** (compute units).

Lockstep explains why GPUs dislike branches. If half of a warp takes the `if` and half the `else`, the warp runs
*both* paths one after another, with half its lanes switched off each time. Same work, twice the time.

Watch it happen below: pick a condition and step through the warp one instruction at a time (also on its own page,
[Warp divergence](lab:warp-divergence)).

## Its own memory

A discrete GPU sits on a card with its own memory, **VRAM**. For example, an RTX 3080 Ti has 12 GB of GDDR6X at
about 912 GB/s; the PCIe 4.0 x16 link to the CPU moves about 32 GB/s. So data that lives in VRAM is cheap for the GPU,
and data that has to cross from the CPU is expensive. Vulkan makes you decide **where every buffer lives** for exactly
this reason.

Put numbers on it: choose how much data a frame touches and where it lives, and compare the time with a 60 fps
frame (also on its own page, [Where the data lives](lab:memory-path)).

<MemoryPath />

GPUs hide memory latency differently from CPUs: rather than relying mainly on big caches, an SM keeps many warps in flight and switches
to another one whenever the current one waits for memory. That is why GPUs want *lots* of parallel work.

## What this means for Vulkan

| GPU fact | What Vulkan makes you do |
| --- | --- |
| Runs the same program on lots of data | Pack work into big batches (draws, dispatches), not many tiny calls |
| Has its own memory | Choose memory types, copy data across explicitly |
| Runs in parallel with the CPU | Synchronize explicitly: the CPU must know when the GPU is done |
| Is a separate device with its own engines | Submit work to queues, not "call functions on the GPU" |

## Underneath

- A frame of a game is millions of pixel-shader invocations, grouped into warps and spread over all SMs.
- The GPU does not fetch work by itself from your program. It reads **command buffers** that the driver prepared in
  memory. That is the next lesson.
