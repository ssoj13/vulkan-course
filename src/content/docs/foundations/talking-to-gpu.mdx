Your program runs on the CPU. A discrete GPU is a separate machine on the other side of a PCIe link (an integrated
GPU shares the chip and memory with the CPU, but is still a separate processor). It cannot call your
functions and you cannot call its. So how does a "draw" ever reach it?

## Where this fits

[Lesson 1](lesson:gpu) showed the machine; this lesson is the road to it. It is a **concept** lesson, but the road
crosses the stack: from your **application**, through the **driver** (and the operating system under it) in the
**loader & driver** layer, down to the GPU's **front end** in the **hardware** layer. The chain of one draw:

`application → user-mode driver → command buffer → queue → kernel-mode driver (schedules) → command processor → shader cores`

A command buffer is built *by* the user-mode driver *from* your calls; a queue is built on top of a hardware engine and feeds it
command buffers; the command processor is the part of the GPU that reads them. Vulkan's version of this road is the
subject of the [next lesson](lesson:why-vulkan): it hands the recording and submitting from the driver to you.

## The path of one draw

<Steps>

1. **Your application** calls a graphics API function, for example "draw 3 vertices with this pipeline".

2. **The driver** (vendor code from NVIDIA, AMD, Intel...) translates the call into the GPU's own binary command
   format and writes it into a block of memory. Nothing is sent yet.

3. Many such commands pile up into a **command buffer**: a recorded list of work, like a shot list.

4. The command buffer is **submitted to a queue**. The operating system's kernel-mode driver schedules it for the GPU.

5. On the GPU, the **command processor** (the GPU's front end) reads the commands from memory and hands the work to
   the shader cores and fixed-function units.

</Steps>

The key word is **later**. The CPU records and submits, then goes on with its life. The GPU executes when it gets
there, often a frame or two behind. CPU and GPU run *in parallel*, like an artist submitting jobs to a render farm
and continuing to work while the farm renders.

<Aside type="tip" title="CG analogy: the render queue">
Submitting a command buffer is like submitting a job to Deadline. You describe the job completely up front (scene,
frames, settings), drop it in a queue, and get on with your day. The farm picks it up when a node is free. If you
want the result, you must *check* that the job finished - you cannot just assume it did.
</Aside>

## Command buffers and queues

- A **command buffer** is the job description: "bind this, draw that, copy this image there".
- A **queue** is the line of submitted jobs in front of one of the GPU's engines. The order in which you submit is the
  queue's *submission order*: the logical order that barriers and semaphores refer to. By itself it is not a promise
  about timing. The specification says that submission order "does not itself define any execution or memory
  dependencies", and that apart from a few implicit ordering guarantees and the synchronization you add, submitted
  command buffers "may overlap or otherwise execute out of order". A job submitted later can finish before an earlier
  one unless you synchronize them.

In older APIs the driver built command buffers for you, behind the scenes, and decided when to submit them. In Vulkan
**you** record command buffers and **you** submit them. That is the single biggest idea of the whole API.

## Underneath

- The driver has two halves: a **user-mode driver** inside your process (it builds the command buffers) and a
  **kernel-mode driver** in the OS (on Windows, part of the WDDM driver model) that owns the hardware and schedules
  submissions from all programs.
- The GPU's command processor is itself a small processor running firmware. It parses the command stream, sets up
  state and launches work on the shader cores.
- Because CPU and GPU run in parallel, every resource both of them touch needs a rule about *who uses it when*. Vulkan
  calls these rules **synchronization**, and we will meet them many times.
