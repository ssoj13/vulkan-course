Everything so far was *setup*: objects created once. Drawing is different. The GPU never executes a Vulkan call the
moment we make it; we write the work down first and hand it over as a whole. Where is it written, what does "recording"
mean, and how does the written work reach the GPU?

## Where this fits

This opens the **commands** module, the last step before pixels appear. The idea itself is old: in
[how a program talks to the GPU](lesson:talking-to-gpu) we met command buffers and queues as concepts. Now they become
objects and calls:

`queue family → VkCommandPool → VkCommandBuffer → recording (vkCmd*) → vkQueueSubmit2 → VkQueue → GPU`

A command pool is built on the device and **one queue family**; a command buffer is allocated from a pool; a submission
goes to a queue of that same family. The [first triangle](lesson:first-triangle) records and submits one command
buffer per frame, with the fences and semaphores that keep frames in order.

## Record now, run later

A render farm job is a good picture. You do not walk to each render node and type commands; you write a job script,
submit it to a queue, and go on with your work while the farm runs it later, on its own schedule.

A [command buffer](term:vk-command-buffer) is the job script, and [recording](term:recording) is writing it: every
`vkCmd*` call (bind a pipeline, set the viewport, draw, insert a barrier) appends a command to the buffer on the CPU.
Nothing reaches the GPU while you record. Only [submission](term:submission) (`vkQueueSubmit2`) hands the finished buffer
to a queue, and the GPU executes it when it gets there - possibly while the CPU is already recording the next frame.

This split is what makes Vulkan fast on the CPU side: recording is plain writing into memory, it can happen on many
threads at once, and a recorded buffer can be inspected, reused or thrown away without the GPU ever being involved.

A command buffer goes through well-defined states:

1. **initial** - freshly allocated or reset, empty;
2. **recording** - between `vkBeginCommandBuffer` and `vkEndCommandBuffer`;
3. **executable** - recorded and ready to submit;
4. **pending** - submitted, the GPU has not finished it. It must not be re-recorded or freed in this state;
5. **invalid** - for example a one-time-submit buffer after it ran, or a buffer whose resources were destroyed.

## 1. The queue

<Step file="09_triangle" region="get-queue" />

The one queue we requested in [step 05](lesson:logical-device#4-get-the-queue). A queue records nothing itself: it
*executes* command buffers (`vkQueueSubmit2`) and *presents* images (`vkQueuePresentKHR`).

## 2. The command pool

<Step file="09_triangle" region="command-pool" />

A [command pool](term:vk-command-pool) is the memory that command buffers are allocated from. It is tied to **one queue
family**, because the commands are encoded for that kind of hardware engine; a buffer from it may be submitted only to
queues of that family (`VUID-vkQueueSubmit2-commandBuffer-03878`).

The flag `RESET_COMMAND_BUFFER` lets us reset each buffer of the pool on its own. Without it, a buffer can only be
reset together with the whole pool (`vkResetCommandPool`), and resetting a single buffer is invalid
(`VUID-vkResetCommandBuffer-commandBuffer-00046`). We re-record the same buffer every frame, so we want the flag.

Pools are not thread-safe: two threads must not record into buffers of one pool at the same time. That is why a
multithreaded renderer gives every thread its own pool.

## 3. The command buffer

<Step file="09_triangle" region="command-buffer" />

`vkAllocateCommandBuffers` takes buffers from the pool. **Primary** buffers are submitted to a queue; **secondary**
buffers are recorded separately and executed from inside a primary one (useful for recording on several threads).
With one frame in flight, one primary buffer is all we need. Command buffers are not destroyed one by one: they go back
with their pool.

## 4. Begin recording

<Step file="09_triangle" region="begin-recording" />

Each frame starts by resetting the buffer (back to *initial*) and beginning it (*recording*).
`ONE_TIME_SUBMIT` promises the driver that this recording will be submitted once and then reset and re-recorded; a
driver may use that promise to optimize, and after the run the buffer becomes *invalid* until it is reset. Everything recorded between here and `vkEndCommandBuffer` - barriers, the
rendering, the draw - is the subject of [the first triangle](lesson:first-triangle).

## 5. Submit

<Step file="09_triangle" region="submit" />

`vkQueueSubmit2` (the synchronization2 version, core in Vulkan 1.3) sends one or more **batches**. A batch carries:

- **command buffers** to execute, in order;
- **wait semaphores**, each with a *stage mask*: the GPU work of this batch may run up to that stage before the
  semaphore is signaled, but not past it;
- **signal semaphores**, signaled when the batch's work has reached the given stage;
- and for the whole call, an optional **fence**, signaled when everything submitted has completed.

In our frame the batch waits for the acquired swapchain image only at `COLOR_ATTACHMENT_OUTPUT`: the vertex shader may
already run while the presentation engine is still releasing the image, and only the writing of colors has to wait.
Why the semaphores and the fence are needed at all is the story of [the first triangle](lesson:first-triangle#the-frame-loop);
the full theory is module 7.

`vkQueueSubmit2` returns at once. Submitting is cheap for the CPU: the work happens later, on the GPU.

## Underneath

- Recording is the driver writing the GPU's own command format into memory it allocated from the pool: packets that
  set state, point at the pipeline, launch draws. That is the "encoding" of [how a program talks to the GPU](lesson:talking-to-gpu);
  `vkCmdDraw` costs the CPU about as much as writing a few words.
- At submission the driver hands those packets to the queue's hardware engine: it adds the buffer to the queue's ring
  of work and tells the GPU there is more. The [command processor](term:command-processor) then reads the buffer from
  memory by itself.
- A buffer in the *pending* state is still being read by the GPU. Re-recording it then would rewrite memory the GPU
  is reading, which is why step 09 waits on a fence before resetting it.
