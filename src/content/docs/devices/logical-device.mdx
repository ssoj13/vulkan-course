We have chosen a GPU and found the queue family that can draw. Now we **open** the GPU: create a **logical device**
(`VkDevice`). Almost every object from here on - buffers, images, pipelines, command pools - is created from it.

## Where this fits

This is the last step of the first section and the point where the **Vulkan API** layer reaches into the **driver**
for real: until now we only read facts, and this is the first point where the driver prepares the GPU itself for our
process (`vkCreateInstance` already created per-driver instance state, but did not touch the GPU). Before: the
[physical device](lesson:physical-devices) and its [queue families](lesson:queue-families). The whole chain is
complete:

`GPU → driver → loader → VkInstance → VkPhysicalDevice → VkDevice → VkQueue`

The logical device is built on a physical device plus our choices (features, queues, extensions); a queue is built on
the device and one queue family. Every later module - presentation, pipelines, commands, memory - creates its objects
from this device and submits its work to this queue.

## Physical vs logical

- `VkPhysicalDevice` is the GPU *as it exists*: read-only facts.
- `VkDevice` is *our session* with that GPU: the queues we asked for, the features we turned on, the extensions we
  enabled. Two programs on the same GPU each have their own logical device; one program could even open two.

## 1. Which queues

<Step file="05_logical_device" region="queue-create-info" />

Queues are created **together with the device** - there is no `vkCreateQueue`. For each family we want, one
`VkDeviceQueueCreateInfo` says how many queues and their **priorities** (0.0 to 1.0). Priorities are hints to the
driver about which queue's work matters more; with a single queue the value does not matter, but it must be given.

## 2. Which features

<Step file="05_logical_device" region="enable-features" />

Here we turn on the two features the course needs everywhere: **dynamic rendering** and **synchronization2**. They
became core in Vulkan 1.3, so they live in `VkPhysicalDeviceVulkan13Features` even though we target 1.4. We set the
two flags to true and hang the struct directly onto `VkDeviceCreateInfo` through `pNext` - the specification allows
the per-version feature structs there, so the `VkPhysicalDeviceFeatures2` wrapper we used for *querying* in the [physical devices lesson](lesson:physical-devices)
is not needed. Only what we enable is on - even features that every Vulkan 1.3 or 1.4 device must support, like
these two, stay off until you enable them.

<Aside type="caution" title="One way or the other">
`VkDeviceCreateInfo` also has an old `pEnabledFeatures` field for Vulkan 1.0 features. You can use it together with
the per-version structs, but if you put `VkPhysicalDeviceFeatures2` into the chain (the other common way to enable
1.0 features), that field must be null (`VUID-VkDeviceCreateInfo-pNext-00373`).
</Aside>

## 3. Create the device

<Step file="05_logical_device" region="create-device" />

Two things are *not* here on purpose:

- **Device layers** - an old feature, deprecated. Layers are enabled on the instance only.
- **Device extensions** - none yet. The first one we will need is `VK_KHR_swapchain`, to show images in a window.

## 4. Get the queue

<Step file="05_logical_device" region="get-queue" />

The device already made the queue; we only fetch its handle by family index and queue index.

## 5. Clean up

<Step file="05_logical_device" region="cleanup" />

`vkDeviceWaitIdle` waits until the GPU has finished everything submitted to this device. Destroying a device while the
GPU still works on its commands is an error, so this wait is the safe way to shut down. We have not submitted anything
yet, but the habit matters.

## Underneath

- `vkCreateDevice` is the first point where the driver prepares the GPU itself for your process. What exactly happens is up to the
  vendor, but typically it sets up a GPU context and the hardware queues you asked for, allocates internal tables and
  configures itself for the enabled features.
- Device-level functions (everything called with a `VkDevice`, `VkQueue` or `VkCommandBuffer`) can skip the loader's
  dispatch: bindings like ash and Vulkan-Hpp load them with `vkGetDeviceProcAddr`, which returns the driver's (or
  layer's) function directly. One less jump per call.
