In [talking to the GPU](lesson:talking-to-gpu) we said work is submitted to a **queue**. A GPU usually offers several
kinds of queues, because inside the chip there are several independent **engines**: the big graphics/compute engine,
copy engines that move memory, video encoders and decoders. Vulkan groups queues of the same kind into **queue
families**.

## Where this fits

This lesson connects the **Vulkan API** layer to the **hardware** engines from the [GPU](lesson:gpu) and
[talking to the GPU](lesson:talking-to-gpu) lessons. Before: the [physical device](lesson:physical-devices) we picked.
After: the [logical device](lesson:logical-device), which creates queues from the families we choose here. The chain:

`VkPhysicalDevice → queue family (queues with the same flags) → VkQueue (one line of work) → command processor / engine`

A queue family is a property of a physical device, read like features and limits; a queue is built on a family and
belongs to the logical device. Like departments in a studio, each family takes the kinds of jobs its flags allow (plus
copies on graphics and compute families, as we will see).

## What a queue family is

A **queue family** is a group of queues of one GPU with identical capabilities: the same flags, the same timestamp
support. Its flags reflect a *kind* of engine - "this can draw", "this can only copy" - but Vulkan does not say which
hardware engine stands behind which family: that mapping is the driver's business, and several families may share one
engine.

## Asking for the families

<Step file="04_queue_families" region="families" />

Each family reports:

- **queueFlags** - what its queues can do: `GRAPHICS`, `COMPUTE`, `TRANSFER`, `SPARSE_BINDING`, video decode/encode...
- **queueCount** - how many queues of this family you may create.
- **timestampValidBits** - how many bits of a GPU timestamp are meaningful (0 = no timestamps on this family).

## A real GPU

This is what step 04 printed on the RTX 3080 Ti of the development machine, rearranged as a table (timestamp bits
left out):

| family | queues | flags |
| --- | --- | --- |
| 0 | 16 | GRAPHICS, COMPUTE, TRANSFER, SPARSE_BINDING |
| 1 | 2 | TRANSFER, SPARSE_BINDING |
| 2 | 8 | COMPUTE, TRANSFER, SPARSE_BINDING |
| 3 | 1 | TRANSFER, SPARSE_BINDING, VIDEO_DECODE |
| 4 | 1 | TRANSFER, SPARSE_BINDING, VIDEO_ENCODE |
| 5 | 1 | TRANSFER, SPARSE_BINDING, OPTICAL_FLOW (an NVIDIA extension) |

How to read it:

- **Family 0** is the "do everything" family. Almost every program needs only this one.
- **Family 1** can only copy. Copies submitted here can run on the GPU's copy (DMA) engines *while* family 0 renders -
  useful for streaming textures in the background.
- **Family 2** computes but cannot draw: **async compute**. Compute work here can overlap with rendering.
- **Families 3-5** feed the video and optical-flow hardware.

Vulkan does not say which hardware unit backs which family - that is the driver's business, and several families may
share one engine - but the flags make the intent clear. Other GPUs show different tables: some integrated GPUs have a single family that does everything.

<Aside type="note" title="Graphics and compute queues can always copy">
The spec allows a family with `GRAPHICS` or `COMPUTE` to leave out the `TRANSFER` flag: copy commands work on such
queues anyway. So never conclude "no transfer support" from a graphics family's flags.
</Aside>

## Finding the families we need

<Step file="04_queue_families" region="find-graphics" />

For this course we need one family that can draw: the first family with `GRAPHICS`. The dedicated transfer and async
compute families are printed to show they exist; we use them in the advanced part.

<Aside type="tip" title="CG analogy">
Think of a studio pipeline with separate departments: lighting renders, a data team moves files, editorial encodes
dailies. Each has its own queue of jobs and they work at the same time. Queue families are the departments of the GPU.
</Aside>

## Underneath

- Each queue you submit to is a stream that the GPU's command processor ([talking to the GPU](lesson:talking-to-gpu))
  or a dedicated engine front end reads from. Multiple queues let independent work overlap instead of waiting in one line.
- Submission order within one queue is the *logical* order that barriers and semaphores refer to; by itself it
  does not make later work wait for earlier work: they may overlap and finish out of order. Between different queues -
  even two queues of the same family, which **may run in parallel** - there is not even that order, and priorities do
  not create one. As soon as two pieces of work touch the same resource, you need explicit synchronization - a topic
  for the synchronization module.
