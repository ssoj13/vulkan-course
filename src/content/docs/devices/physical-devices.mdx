The instance knows about every GPU in the machine. A laptop may have two (integrated + discrete); a workstation may
have several; a CI server may have none but a software renderer. Before we can use one, we pick it - and to pick, we
ask each one what it is.

## Where this fits

This is the **Vulkan API** layer touching the **hardware** for the first time, but only to read facts: nothing runs on
the GPU yet. Before: the [instance](lesson:loader-and-instance) with [validation](lesson:validation) watching it. The
chain:

`VkInstance → VkPhysicalDevice → properties / features / limits`

A physical device is built on the instance (found through it) and stands for one GPU (or software implementation)
behind one driver.
Properties say what it is, features what it could switch on, limits how far it goes. What we read here decides the two
next steps: its [queue families](lesson:queue-families), and then the logical device, which enables the features we
picked.

## Physical devices are found, not created

A **`VkPhysicalDevice`** is a handle to one GPU as the instance sees it. You do not create it and you never destroy
it: the instance **enumerates** the GPUs that exist, and the handles live as long as the instance.

## Three questions to every GPU

### What are you? - properties

<Step file="03_physical_devices" region="properties" />

- **deviceType**: discrete, integrated, virtual, CPU (a software implementation) or other.
- **apiVersion**: the highest Vulkan version the driver supports for this GPU. The version you may actually use is the
  *lower* of this and the `apiVersion` you asked for in the instance.
- **driverVersion**: encoded differently by each vendor; `vulkaninfo` decodes it.
- **vendorID**: a PCI vendor id - `0x10DE` NVIDIA, `0x1002` AMD, `0x8086` Intel.

### What can you do, if asked? - features

<Step file="03_physical_devices" region="features" />

**Features** are optional capabilities: anisotropic filtering, geometry shaders, dynamic rendering... A feature that a
GPU supports is still **off** until you enable it when creating the [logical device](lesson:logical-device). This is
Vulkan's "say everything up front" again: the driver can prepare for exactly what you will use.

Features introduced in later Vulkan versions live in extra structs (`VkPhysicalDeviceVulkan13Features`,
`VkPhysicalDeviceVulkan14Features`...). To ask for them we chain those structs onto `VkPhysicalDeviceFeatures2` through
`pNext` - the same chain trick as in the [validation lesson](lesson:validation). One call fills every struct in the
chain. One rule applies: every struct in a `pNext` chain must belong to a core version the device supports or to an
enabled extension, so the code chains the 1.3 struct only when the device's `apiVersion` is at least 1.3, and the 1.4
struct only from 1.4.

<Aside type="tip" title="CG analogy">
Features are like render-farm node capabilities: a node may *have* a GPU and 128 GB of RAM, but a job only gets them
if its submission asks for them. Asking up front lets the farm plan.
</Aside>

### How far can I go? - limits

<Step file="03_physical_devices" region="limits" />

**Limits** are numbers the GPU guarantees: the largest 2D image, how many bytes of push constants, the alignment
required for uniform buffer offsets. You cannot change them; your code must respect them.

## A real answer

This is the complete output of step 03 on the machine the course was built on (Rust and C++ print the same; the first
line is the Bandicam layer's warning from the [loader lesson](lesson:loader-and-instance)):

```txt
[WARNING][GENERAL] Layer VK_LAYER_bandicam_helper uses API version 1.2 which is older than the application specified API version of 1.4. May cause issues.
Found 1 GPU(s)

GPU 0: NVIDIA GeForce RTX 3080 Ti
  type:       DISCRETE_GPU
  api:        1.4.351
  driver:     0x9a100000
  vendor id:  0x10de
  features:
    sampler_anisotropy (1.0): true
    dynamic_rendering  (1.3): true
    synchronization2   (1.3): true
    push_descriptor    (1.4): true
    maintenance5       (1.4): true
  limits:
    max_image_dimension_2d:               32768
    max_push_constants_size:              256 bytes
    min_uniform_buffer_offset_alignment:  64 bytes
    timestamp_period:                     1 ns/tick

Picked: NVIDIA GeForce RTX 3080 Ti
```

The driver supports Vulkan 1.4 and our instance asks for 1.4, so we can use 1.4. All five flags above are in fact
guaranteed on any 1.4 device - the spec makes them mandatory - so the check matters for older devices and for truly
optional features, which later lessons will meet. The `(1.3)` and `(1.4)` marks show
which version's feature struct each flag comes from.

## Picking one

<Step file="03_physical_devices" region="pick" />

First filter out GPUs that cannot run our program at all (too old, missing features), then prefer the likely fastest:
a discrete card over an integrated one. Real applications often also let the user choose.

## Underneath

- Each driver reports its own GPUs; the loader merges the lists from all drivers. That is why the physical device
  handle is dispatchable: the loader must know which driver owns it.
- Properties, features and limits are read from the driver - nothing runs on the GPU yet. The GPU is not even
  "opened" until we create a logical device.
