In step 09 the CPU waits for the GPU at the start of every frame, so the two take turns: while one works, the other
idles. How do we let them work at the same time, what has to be duplicated so they do not step on each other, and how
much does it really buy? This lesson answers with step 10 and a measurement.

## Where this fits

The second lesson of the synchronization module, on the concept and API layers. It takes the fence from
[fences and semaphores](lesson:fences-and-semaphores) and multiplies it: one per frame that may be "in flight" at once.
The chain of one frame becomes:

`frame N → slot N % F → wait the slot's fence (frame N - F) → acquire → record the slot's command buffer → submit (signals the slot's fence) → present`

[Frames in flight](term:frames-in-flight) are built on the [frame loop](term:frame-loop) of the
[first triangle](lesson:first-triangle) with one set of per-frame resources per slot. The
[timeline semaphores lesson](lesson:timeline-semaphores) later replaces the F fences with one counter.

## Taking turns, then overlapping

Think of an artist and a render farm. If the artist preps shot 2 only after shot 1 has come back from the farm, both
sit idle half the time. The obvious fix: send shot 1, start prepping shot 2 at once, and only before sending shot 3
check that the farm is done with shot 1. The farm always has the next job waiting; the artist never waits for the
current one.

With one frame in flight, step 09 does the first thing:

```text
CPU  [record 1]  wait.......  [record 2]  wait.......  [record 3]
GPU              [render 1]               [render 2]
```

With two frames in flight, step 10 does the second:

```text
CPU  [record 1][record 2][record 3]  [record 4]  ...
GPU            [render 1][render 2]  [render 3]  ...
                          ^ frame 3 waits for frame 1, not for frame 2
```

The CPU now waits for the frame *two* back. If one side is much slower, it sets the pace and the other side still
waits, but the waits no longer add up: the frame time becomes the time of the slower side instead of the sum of both.

## What must exist once per frame

The rule is simple to state: **everything the CPU writes for frame N+1 while the GPU may still use it for frame N**
needs its own copy per frame in flight. In step 10 that is three things:

- the **command buffer**: a buffer that is *pending* (submitted, not finished) must not be reset or re-recorded;
- the **fence**: it tells when that slot's buffer is free again;
- the **`image_available` semaphore**: its wait belongs to that slot's submit, and the fence proves the wait is over.

Two other kinds of objects are not per frame. `render_finished` stays **per swapchain image** (the present's wait on it
ends for sure only when that image is acquired again). The pipeline, its layout and the swapchain are shared: nothing
writes them per frame. Later modules add more per-frame things: uniform buffers that the CPU fills every frame,
descriptor sets pointing at them.

<Step file="10_frames_in_flight" region="frame-resources" />

The slot of frame N is `N % frames in flight`. One struct per slot keeps the three objects together, so a frame cannot
pick up the command buffer of one slot and the fence of another.

<Step file="10_frames_in_flight" region="command-buffers" />

One primary command buffer per slot, all from the same pool. The pool has `RESET_COMMAND_BUFFER`, so each buffer can be
reset on its own while its neighbor is still pending.

## 1. Wait for the slot, not for the last frame

<Step file="10_frames_in_flight" region="wait-fence" />

The same `vkWaitForFences` as in step 09, but on the fence of *this slot*. With two frames in flight, frame N waits for
frame N - 2; frame N - 1 may still be rendering, and that overlap is the point of the step. The fence is still reset
only after a successful acquire, for the reason the first triangle gave: a reset fence that no submission will signal
would hang the next wait.

The time measured around the wait goes into the statistics: it is exactly the time the CPU spent doing nothing while
the GPU caught up.

## 2. Simulated work on both sides

A triangle costs nothing on either side, and frames in flight only matter when both sides are busy. Step 10 therefore
has two knobs:

filling per-frame data:

The GPU half is `--draws` instances of the triangle (default 5000), all on the same pixels: pure fill work.

## 3. Why every frame records its own buffer

<Step file="10_frames_in_flight" region="animate" />

The clear color changes every frame, and it is a value **inside** the command buffer (`vkCmdBeginRendering` records it).
If frame N+1 re-recorded the buffer that frame N still executes, the GPU could read a half-rewritten buffer: that is
exactly what the per-slot command buffers prevent. The same logic will apply to every per-frame resource later.

## 4. Next frame, next slot

<Step file="10_frames_in_flight" region="advance-frame" />

Incrementing the frame number is all it takes to move to the other slot. Nothing waits here: the CPU goes straight on
to the next frame, and only the wait-fence of the *next use* of a slot brings the CPU and the GPU back in step.

## 5. The end

<Step file="10_frames_in_flight" region="cleanup" />

With several frames in flight, more than one submission may still be running when the window closes, so one
`vkDeviceWaitIdle` before destroying anything replaces "wait for the last fence". It waits for queue work: our
submissions and the presents' queue operations (their semaphore waits). It does not wait for the presentation engine;
present fences (`VK_KHR_swapchain_maintenance1`, in [swapchain recreation](lesson:swapchain-recreation)) exist to know
when a present's resources can be released.

## The measurement

Each run: 4 seconds, defaults otherwise, validation on (synchronization validation off), release builds of both
languages, the course machine (RTX 3080 Ti). The machine was shared with other work, so the runs alternated (Rust and
C++, frames 1, 2, 3, five rounds), and the table shows the **medians of 5 runs** per configuration, taken from the
total lines:

| Frames in flight | fps, Rust / C++ | Fence wait per frame, Rust / C++ | Share of time in the fence wait |
|---|---|---|---|
| 1 | 227 / 228 | 2.032 / 2.072 ms | 46.3% / 47.4% |
| 2 | 419 / 432 | 0.048 / 0.048 ms | 2.0% / 2.1% |
| 3 | 420 / 429 | 0.047 / 0.046 ms | 2.0% / 2.0% |

The two languages are within 1% of each other with one frame in flight and 2-3% apart with two and three (C++ ahead);
the shape of the result is the same in both.

Reading the numbers (Rust; C++ is the same within those few percent):

- **One frame**: 227 fps is 4.41 ms per frame. Of that, 2 ms is the simulated CPU work and 2.03 ms is waiting for the
  GPU; the remaining ~0.38 ms is the real CPU work of a frame (recording, the validation layer checking every call,
  submit, present). The two sides add up.
- **Two frames**: 419 fps is 2.39 ms per frame: 2 ms of work, 0.05 ms of fence wait and ~0.34 ms of the rest, the same
  ~0.35 ms as with one frame. The fence wait has dropped from 2.03 ms to 0.05 ms: the GPU's work is now completely
  hidden behind the CPU's. The frame rate nearly doubled without making anything faster.
- **Three frames**: no further gain (420 against 419, well inside the noise). The CPU is the bottleneck now, and a
  third slot only lets the CPU run further ahead of a GPU that is already never waited for.
The extra slot is not free either: each frame in flight is one more frame between "the CPU read the input" and "the
image reaches the screen". That is why two is the usual choice, and why engines that care about latency keep it at two
or even make it adaptive.

## Underneath

- With one frame in flight the GPU's queue runs dry at the end of every frame: the command processor finishes the
  batch, and there is nothing behind it until the CPU has recorded and submitted the next one. With two, the next
  batch is usually already queued when the current one ends, so the GPU goes from one frame straight to the next.
- The CPU side of "waiting" is `vkWaitForFences` blocking a thread; the measured 2.03 ms per frame is time the driver
  spent letting our thread sleep or spin until the GPU reported the frame complete.
- MAILBOX lets the GPU render far faster than the display refreshes: a newer frame replaces the one waiting for the
  vblank. With FIFO, the loop would block in the acquire or the present instead, and the frame rate would be capped
  by the display's refresh, whatever the number of frames in flight.
