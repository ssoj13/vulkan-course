Fences and semaphores order whole submissions. Inside one queue, between one command and the next, the tool is the
**pipeline barrier**, and so far we have used two of them by recipe. This lesson takes the recipe apart: what exactly
does a barrier guarantee, why does it need four masks and two layouts, and what does the validation layer say when one
of them is wrong? Step 12 gives us a frame with real hand-overs: render into an offscreen image, copy it to the
swapchain image, present.

## Where this fits

The third lesson of the synchronization module. It goes one layer deeper than the previous two, from the API down to
what the driver and the GPU's caches do. The concepts form a ladder, each rung built on the one below:

`submission order → execution dependency (stage masks) → memory dependency (access masks: availability + visibility) → layout transition (a write inside the memory dependency)`

[Fences and semaphores](lesson:fences-and-semaphores) introduced the
[execution dependency](term:execution-dependency); here it gains a memory half, the
[memory dependency](term:memory-dependency), made of [availability and visibility](term:availability-visibility),
chosen with [stage masks](term:stage-mask) and [access masks](term:access-mask). A
[layout transition](term:layout-transition) of an [image layout](term:image-layout) rides inside it. The tool that
carries all of it is the [pipeline barrier](term:pipeline-barrier).

## Four kinds of conflict

Two commands touch the same memory. Depending on who reads and who writes, there are four cases, and only three of
them are [data hazards](term:data-hazard):

| Earlier | Later | Name | What can go wrong | What it needs |
|---|---|---|---|---|
| write | read | read-after-write (RAW) | the reader sees old data | a memory dependency |
| write | write | write-after-write (WAW) | the older write lands last | a memory dependency |
| read | write | write-after-read (WAR) | the writer overwrites data still being read | an execution dependency |
| read | read | read-after-read | nothing | nothing |

The last column is the spec's own rule: "Write-after-read hazards can be solved with just an execution dependency,
but read-after-write and write-after-write hazards need appropriate memory dependencies to be included between them."
Why the difference? A WAR conflict is only about *time*: the write must not start before the read is done. RAW and WAW
are also about *where the data is*, and that needs the second rung of the ladder.

## Why order alone is not enough

On a CPU, if thread A writes a value and thread B reads it later, the cache hardware makes sure B sees it (atomics only
have to order the accesses). A GPU is built differently. The color writes of a draw may sit in the cache of the
render-output units; the copy engine or the texture units have their own caches, possibly holding stale lines of the
same memory. Nothing keeps them coherent automatically. So "the draw finished before the copy started" is not enough:
the draw's writes must also be **pushed out** where the copy can find them, and the copy's view of that memory must be
**refreshed**.

The spec names exactly these two steps, without talking about caches:

- an **availability operation** makes the values of chosen *writes* available to a memory domain (think: flushed out of
  the writer's caches);
- a **visibility operation** makes available values visible to chosen *accesses* (think: the reader's stale cache lines
  dropped).

A [memory dependency](term:memory-dependency) is an execution dependency with both inside it, in a fixed order: the
first set of operations happens-before the availability operation, availability happens-before visibility, visibility
happens-before the second set. "Most synchronization commands in Vulkan define a memory dependency": semaphore signals
and waits do, with *all* device accesses; a barrier does, with the accesses you choose.

The CPU analogy is release and acquire: the writer *releases* (publishes) its writes, the reader *acquires* them.
Where it breaks: on a CPU release/acquire only order accesses and the hardware does the rest, while on a GPU the barrier
may really cause the flush and the invalidate, so a missing one is not a theoretical problem. And the cache picture is
only a model: the spec defines availability and visibility, and a driver is free to implement them however its
hardware needs.

## Stage masks: which work waits for which

A barrier's execution dependency is chosen with two masks of pipeline stages:

- `srcStageMask`: the stages of **earlier** commands that must complete. The spec adds the logically *earlier* stages
  automatically: naming `COLOR_ATTACHMENT_OUTPUT` also covers vertex and fragment shading of those commands;
- `dstStageMask`: the stages of **later** commands that must wait. The logically *later* stages are added
  automatically: naming `FRAGMENT_SHADER` also holds back color output.

Everything outside the two masks keeps running. That is the whole point of being precise: a barrier with
`ALL_COMMANDS` on both sides is always correct, and it also drains the whole pipeline at that point.

"Earlier" means earlier **in submission order on the same queue**, not "in this command buffer". The spec: the first
scope of `vkCmdPipelineBarrier2` is "applied to operations that occurred earlier in submission order". A barrier at the
start of frame N's command buffer therefore reaches back into frame N-1's command buffer, submitted before it. Step 12
depends on exactly that.

## Access masks: which memory

The memory half is chosen with two masks of access types:

- `srcAccessMask`: the **writes** of the first scope that are made available (`COLOR_ATTACHMENT_WRITE`,
  `TRANSFER_WRITE`...);
- `dstAccessMask`: the accesses of the second scope that the available writes are made visible to (`TRANSFER_READ`,
  `SHADER_SAMPLED_READ`, also writes such as `COLOR_ATTACHMENT_WRITE`).

Two details. Unlike the stage masks, access masks do not grow by logical order: "only the stages the application
specifies are considered part of each access scope". And every access must belong to a stage in its mask: a barrier
with `srcAccessMask = COLOR_ATTACHMENT_WRITE` must name `COLOR_ATTACHMENT_OUTPUT` (or an all-stages flag) in
`srcStageMask` (`VUID-VkImageMemoryBarrier2-srcAccessMask-03911`), and `TRANSFER_WRITE` needs a transfer stage such as
`BLIT` (`VUID-VkImageMemoryBarrier2-srcAccessMask-03915`).

For a WAR conflict the source access is simply `NONE`: there are no writes to publish, only a read to wait for.

## Layouts and their transitions

An [image layout](term:image-layout) is the arrangement of an image's memory for one kind of use. Step 12 uses five:

- `UNDEFINED`: "the contents do not matter"; as the old layout it lets the GPU throw them away;
- `COLOR_ATTACHMENT_OPTIMAL`: rendered into;
- `TRANSFER_SRC_OPTIMAL` and `TRANSFER_DST_OPTIMAL`: the source and the destination of a copy or blit;
- `PRESENT_SRC_KHR`: handed to the presentation engine.

A [layout transition](term:layout-transition) is part of an image barrier: `oldLayout → newLayout`. The old layout
must be `UNDEFINED` or the layout the image really has (`VUID-VkImageMemoryBarrier2-oldLayout-01197`). And the
transition is not a label change, it is work on the image's memory. The spec places it precisely: it "happens-after
the availability operations in the memory dependency, and happens-before the visibility operations", and it "may
perform read and write accesses on all memory bound to the image subresource range".

So a layout transition is a **write**, sitting in the middle of the barrier. That one sentence explains most barrier
rules for images: earlier writes must be made available before it (or the transition may shuffle stale data), and an
earlier *read* must have finished before it (a WAR conflict, solved by the source stage alone).

## The barrier itself (synchronization2)

`vkCmdPipelineBarrier2` takes a `VkDependencyInfo` with three lists: global memory barriers, buffer memory barriers
(a range of a buffer), and image memory barriers (a subresource range of an image, plus the two layouts and the queue
family ownership fields we leave at `QUEUE_FAMILY_IGNORED`). In synchronization2 (core since Vulkan 1.3) every barrier
in those lists carries its own four masks; the Vulkan 1.0 `vkCmdPipelineBarrier` had one pair of stage masks for the
whole call. Several independent barriers in one call let the driver merge their waits and cache operations, which
separate calls may not.

## Step 12: render, blit, present

Step 12 renders the triangle into a 400x300 **offscreen** image and then **blits** it (a copy that may scale) onto the
800x600 swapchain image. Two images, three kinds of work, five barriers.

### 1. The offscreen image

<Step file="12_timeline" region="offscreen-image" />

Our first image that does not come from a swapchain. Its usage says what it will be: `COLOR_ATTACHMENT` (rendered
into) and `TRANSFER_SRC` (blitted from); its format must support rendering and blitting on optimal tiling. Unlike a
swapchain image it has no memory of its own, so the program allocates video memory and binds it; how a memory type is
chosen is the subject of [memory types](lesson:memory-types); here it is just "the first `DEVICE_LOCAL` type the image accepts" (memory
type 1 on the course GPU). The swapchain images, in turn, need `TRANSFER_DST` to be a blit destination; that and a
surprising second usage flag are shown in [swapchain recreation](lesson:swapchain-recreation#who-else-uses-the-swapchain-images).

There is **one** offscreen image for all frames in flight. That is deliberate: it makes the barriers at the edge
between two frames necessary, and it is what real renderers do with big intermediate images they do not want to
duplicate.

### 2. The five barriers

<Step file="12_timeline" region="barriers" />

Each barrier is "after *this* (stage + access), before *that* (stage + access)", recorded where an image changes hands:

| # | Image | Layout | After (src stage / access) | Before (dst stage / access) | Why |
|---|---|---|---|---|---|
| 1 | offscreen | `UNDEFINED → COLOR_ATTACHMENT_OPTIMAL` | `COLOR_ATTACHMENT_OUTPUT` / `NONE` | `COLOR_ATTACHMENT_OUTPUT` / `COLOR_ATTACHMENT_WRITE` | WAW with the previous frame's color writes; chained behind barrier 5, so also after the previous frame's blit |
| 2 | swapchain | `UNDEFINED → TRANSFER_DST_OPTIMAL` | `BLIT` / `NONE` | `BLIT` / `TRANSFER_WRITE` | waits for the acquire: the submit waits on `image_available` at `BLIT` |
| 3 | offscreen | `COLOR_ATTACHMENT_OPTIMAL → TRANSFER_SRC_OPTIMAL` | `COLOR_ATTACHMENT_OUTPUT` / `COLOR_ATTACHMENT_WRITE` | `BLIT` / `TRANSFER_READ` | RAW: render → copy |
| 4 | swapchain | `TRANSFER_DST_OPTIMAL → PRESENT_SRC_KHR` | `BLIT` / `TRANSFER_WRITE` | `BLIT` / `NONE` | before `render_finished` is signaled at `BLIT` |
| 5 | offscreen | none (`TRANSFER_SRC_OPTIMAL` stays) | `BLIT` / `NONE` | `COLOR_ATTACHMENT_OUTPUT` / `NONE` | WAR: the next frame writes the image this blit reads |

Barrier by barrier, in the order they run:

1. **Before rendering into the offscreen image.** The old contents do not matter (we clear), so the old layout is
   `UNDEFINED`. But the image is not idle: the *previous* frame wrote it (its rendering) and read it (its blit), and with
   frames in flight both may still be running. This frame's transition and clear are writes. The source stage is
   `COLOR_ATTACHMENT_OUTPUT`, and that one stage covers both conflicts, explained in detail
   [below](#where-two-frames-meet). The previous frame is in another command buffer and another submission; the
   barrier's first scope reaches it anyway, because it is earlier in submission order on the same queue.
2. **Before the blit writes the swapchain image.** The image has just been acquired; its old contents do not matter.
   The source stage `BLIT` is the stage at which the submit waits on `image_available`, so the transition is chained
   behind the semaphore wait and cannot start before the presentation engine has released the image.
3. **The render → copy hand-over.** A RAW conflict: the color writes must be finished *and* made available
   (`COLOR_ATTACHMENT_WRITE`), and made visible to the blit's reads (`TRANSFER_READ`). The layout changes to what a copy
   source wants.
4. **Before presenting.** The blit's writes are made available; the destination is `BLIT` with no access, the stage at
   which `render_finished` is signaled, so the transition is ordered before the signal. The present needs no access
   mask: the presentation engine makes the writes visible to itself.
5. **After the blit, for the next frame.** The blit only *reads* the offscreen image, and the next frame will write it.
   WAR: an execution dependency is enough, so both access masks are `NONE`, and the layout stays. The destination stage
   `COLOR_ATTACHMENT_OUTPUT` holds back the color output of every later command on the queue: the next frame's barrier 1
   and its rendering. With old and new layout equal, an image barrier is a pure dependency, no transition.

### Why the WAR protection sits at the end of the frame

The obvious place for "wait for the previous frame's blit" is barrier 1 itself, with `BLIT` as its source stage. An
earlier version of step 12 did exactly that, and it was correct, but it quietly cancelled the reason the semaphore
wait is at `BLIT`. Two rules meet here:

- a semaphore wait's second synchronization scope is the wait's stage mask (and logically later stages) of every
  command in the batch, so `image_available` holds back the `BLIT` stage of this frame's commands;
- dependencies chain when the second scope of one overlaps the first scope of the next. A barrier at the start of the
  frame with source stage `BLIT` has a first scope that overlaps the wait's second scope, so it is ordered after the
  wait, and so is everything in *its* second scope: the transition, the clear and the draw.

So with `BLIT` in barrier 1, the rendering waited for the acquire after all, which is exactly what waiting at `BLIT`
was meant to avoid. The fix moves the `BLIT` dependency to where the read happens: barrier 5, at the end of the
frame that blits. Barrier 1 then names only `COLOR_ATTACHMENT_OUTPUT`, a graphics stage that is not logically later
than `BLIT` (transfer stages have their own order), so its first scope no longer overlaps the wait, and nothing chains
the rendering to the acquire. The next frame is still ordered after this frame's blit: barrier 5's second scope
(`COLOR_ATTACHMENT_OUTPUT` of every later command in submission order) overlaps barrier 1's first scope
(`COLOR_ATTACHMENT_OUTPUT` of every earlier command), so the chain blit → barrier 5 → barrier 1 → transition and clear
holds across the two submissions.

### Where two frames meet

At barrier 1 of frame N the offscreen image has two earlier users from frame N-1, and the one source stage covers both:

- **WAW with frame N-1's color writes.** Frame N's transition and clear are writes after writes. A WAW conflict needs
  a memory dependency: the earlier writes must be made available, or they could land after the new ones. Barrier 3 of
  frame N-1 already made them available (`COLOR_ATTACHMENT_WRITE` in its source access), and barrier 1's source stage
  `COLOR_ATTACHMENT_OUTPUT` orders frame N's writes after them in execution. Availability is done once; it does not
  have to be repeated, so the source access of barrier 1 stays `NONE`.
- **WAR with frame N-1's blit read.** Covered by the chain through barrier 5, as above.

Synchronization validation (next section) tracks exactly these accesses and reports neither conflict.

### 3. Render into the offscreen image

<Step file="12_timeline" region="render" />

Barrier 1, then the dynamic rendering of the [first triangle](lesson:first-triangle#two-layout-transitions), only
smaller: render area, viewport and scissor are 400x300. The query and timestamp calls around it belong to the

### 4. Blit to the swapchain image

<Step file="12_timeline" region="blit" />

Barriers 2 and 3 go into **one** `vkCmdPipelineBarrier2` call: they concern different images and do not depend on each
other. Then the blit: the whole 400x300 source onto the whole swapchain image, scaled by 2 with `NEAREST` filtering, so
each rendered pixel becomes a 2x2 block on screen. `vkCmdBlitImage2` names the layouts the images are in at that moment,
and they must be the real ones (`VUID-VkBlitImageInfo2-srcImageLayout-00221`, `VUID-VkBlitImageInfo2-dstImageLayout-00226`):
that is what barriers 2 and 3 arranged. Barriers 4 and 5, again independent images in one call, close the command
buffer.

## Proof: take one stage away

A barrier that is too weak usually *works* on your machine: the timing happens to be right. The Khronos validation
layer has a mode that tracks every access and every barrier and reports hazards: **synchronization validation**,
switched on here with the environment variable `VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true`. With it, steps 10, 11 and
12 run without a single message apart from the bandicam layer's warning: both languages, step 10 with the defaults,
step 11 with `--demo-resize` with and without present fences, step 12 with the barriers above.

Then we removed the source stage `BLIT` from barrier 5, the WAR barrier at the end of the frame (its source became
`NONE`). The layer reported (handles differ from run to run):

```text
[ERROR][VALIDATION] vkQueueSubmit2(): WRITE_AFTER_READ hazard detected. vkCmdPipelineBarrier2 (from VkCommandBuffer 0x25b9ab310d0 submitted on the current VkQueue 0x25b9a7d14d0) writes to VkImage 0x1b000000001b, which was previously read by vkCmdBlitImage2 (from VkCommandBuffer 0x25b9ab2d8d0 submitted on VkQueue 0x25b9a7d14d0). 
The current synchronization defines the destination stage mask as VK_PIPELINE_STAGE_2_BLIT_BIT, but layout transition does not synchronize with these stages.
Vulkan insight: If the layout transition is done via an image barrier, consider including VK_PIPELINE_STAGE_2_BLIT_BIT in srcStageMask. If the transition occurs as part of the render pass begin operation, consider specifying an external subpass dependency (VK_SUBPASS_EXTERNAL) with srcStageMask that includes VK_PIPELINE_STAGE_2_BLIT_BIT, or perform the transition in a separate image barrier before the render pass begins.
Vulkan insight: an execution dependency is sufficient to prevent this hazard.
```

Everything this lesson said is in that message:

- the hazard is **write-after-read**, and the "write" is `vkCmdPipelineBarrier2` itself, barrier 1 of the next frame:
  the layout transition is a write to the image;
- the read is `vkCmdBlitImage2` from **another command buffer**, the previous frame's: the conflict crosses command
  buffers and submissions on one queue;
- the fix is a source stage `BLIT` somewhere in the chain. The layer suggests the nearest place, barrier 1's
  srcStageMask: correct, and exactly the version that chained the rendering to the acquire. Barrier 5 is the other
  place, and the one step 12 uses;
- and the last line is the WAR rule: "an execution dependency is sufficient to prevent this hazard". No access mask is
  needed.
Core validation alone does not report this: every call is valid on its own, and only synchronization validation
tracks which access happened before which.

## Does the rendering really run before the acquire?

The barriers *allow* the GPU to render before the swapchain image is free. Whether it gains anything is a question for
a measurement, and the tool is the GPU's own clock: **timestamp queries**.

<Step file="12_timeline" region="timestamps" />

Each frame writes three timestamps with `vkCmdWriteTimestamp2` (shown in the render and blit regions above): at
`TOP_OF_PIPE` when the GPU starts the command buffer, at `COLOR_ATTACHMENT_OUTPUT` after the rendering (written once
the color writes are done), and at `BLIT` after the blit. A query must be reset before it is written again, hence the
`vkCmdResetQueryPool` at the start. Once the timeline says a slot's frame is complete, its timestamps are read back:

<Step file="12_timeline" region="read-timestamps" />

The idea: if the GPU ever had to wait for `image_available`, the wait would sit between "render done" and "blit done",
because only the blit waits. That interval would then be much longer than the blit itself. From the run in the
[timeline lesson](lesson:timeline-semaphores#what-the-program-prints), Rust, MAILBOX, two frames in flight:

```text
[timing] 1s, GPU timestamps of 1825 frames: render 3.8 us avg, 7.0 us max; render done -> blit done 6.7 us avg, 8.2 us max
[timing] 2s, GPU timestamps of 2056 frames: render 3.8 us avg, 5.2 us max; render done -> blit done 6.7 us avg, 8.2 us max
[timing] 3s, GPU timestamps of 2144 frames: render 5.3 us avg, 10.7 us max; render done -> blit done 10.4 us avg, 22.5 us max
[timing] 4s, GPU timestamps of 2134 frames: render 10.5 us avg, 16.6 us max; render done -> blit done 22.8 us avg, 37.9 us max
```

The answer on the course machine is honest and a little disappointing: **not measurable**. "Render done → blit done"
is the blit's own few microseconds, and its maximum stays within a few times its average; where it grows (seconds 3
and 4), the rendering grows by the same factor, so the GPU itself ran slower (we did not investigate why), it did not
wait for the semaphore. For a test we also forced FIFO, where the presentation engine releases images only at the
display's refresh, with one, two and three frames in flight: in the first two seconds of each run the interval was
7.5-7.6 µs on average and at most 9.2 µs (later seconds grew together with the rendering, as above). In every frame the acquire semaphore was already signaled by the time the GPU reached the
blit, so there was nothing to overlap. The timestamps cannot tell us more than that: they do not show when the
semaphore was signaled, nor whether a driver waits for it before starting the batch at all.

So what does the fix buy? Correctness of the claim, and the permission: on a system where the semaphore is still
pending when the batch starts, the rendering is now allowed to run. Measure on your target before counting on it.

## Underneath

- A barrier is translated by the driver into whatever the hardware needs: waiting until the named source stages of
  earlier work have drained (only those, if the hardware can tell them apart), writing back the caches that hold the
  source writes, invalidating the caches the destination accesses will read through. A precise barrier lets the rest
  of the GPU keep running; `ALL_COMMANDS` stops everything.
- Layout transitions are where image compression lives. Many GPUs keep render targets in a compressed form that only
  the render-output units understand; before a copy engine, a texture unit or the display reads the image, the
  transition may have to decompress it in place. `UNDEFINED` as the old layout lets the driver skip that work, because
  the old contents are declared garbage.
- Synchronization validation does on the CPU what the spec does on paper: it keeps, for every image region, the last
  write and the reads since, and checks each new access against the barriers in between. That is why it is slow (the
  frame rate of step 10, medians of 5 alternating release runs on a shared machine, went from 419 to 408 fps in Rust
  and from 432 to 418 in C++; small here only because the frame is dominated by a 2 ms busy loop) and why it is worth
  running regularly.
