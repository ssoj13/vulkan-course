Step 10 keeps one fence per frame in flight, and each one is waited on, reset and handed to a submission again, a
little bookkeeping ritual per slot. A binary semaphore is not better: one signal, one wait, and the host cannot touch
it. Could one object simply say *how far the GPU has got*? That is a **timeline semaphore**, and this lesson replaces
step 10's fences with one.

## Where this fits

The fourth lesson of the synchronization module, on the API layer. It merges the two tools of
[fences and semaphores](lesson:fences-and-semaphores) into one, applied to the slots of
[frames in flight](lesson:frames-in-flight), in the render-then-blit frame of the
[barriers lesson](lesson:barriers-and-layouts). The chain:

`binary semaphore (one signal, one wait) → timeline semaphore (a counter: signal n, wait for ≥ n) → host wait (vkWaitSemaphores) instead of a fence per slot; binary semaphores stay for acquire and present`

A [timeline semaphore](term:timeline-semaphore) is a [VkSemaphore](term:vk-semaphore) built on a 64-bit counter; it
does the job of the per-slot [fences](term:vk-fence), while the [binary semaphores](term:binary-semaphore) keep their
place at the swapchain.

## From flags to a counter

A render farm does not hang a "done" flag on every job and reset it for the next one. It has a counter: "frames done:
41". Whoever needs frame 39 checks that the counter is at least 39; whoever needs frame 45 waits until it gets there.
Nothing is reset, nothing is consumed, and many people can look at the same counter.

A timeline semaphore is that counter:

- it starts at an **initial value** given at creation, and only ever grows;
- a **signal** sets it to a value, which must be greater than the current one
  (`VUID-VkSubmitInfo2-semaphore-03882`); a queue submission signals it when the work in its first scope completes, and
  the **host** can signal it too, with `vkSignalSemaphore` (`VUID-VkSemaphoreSignalInfo-value-03258`);
- a **wait** for value *v* lasts until the counter is **≥ v**. It consumes nothing: any number of waits, on queues or on
  the host (`vkWaitSemaphores`), may wait for the same or different values;
- the host can read the counter at any time with `vkGetSemaphoreCounterValue`.

Compared with the binary semaphore of the first lesson, three restrictions are gone. Waits and signals no longer pair
1:1. A wait may be **submitted before** the signal it waits for: the spec only says the wait "will not complete until at
least one semaphore signal operation" meets its criteria. And the host can take part on both sides. Compared with a
fence, there is nothing to reset, and one object covers every frame.

The CPU analogy is an atomic 64-bit counter paired with a condition variable, "sleep until the counter is at least
*n*". D3D12 programmers know it as `ID3D12Fence`: the issues of `VK_KHR_timeline_semaphore` call D3D12 fence objects
"semantically close/identical" to it, and `VK_KHR_external_semaphore_win32` can import a D3D12 fence handle into a
`VkSemaphore`. Where the analogy breaks: the counter must never be set backwards or to the same value, a signaled value
must not differ from the current value, or from the value of any outstanding wait or signal, by more than the device limit
`maxTimelineSemaphoreValueDifference` (`VUID-VkSubmitInfo2-semaphore-03883`), and GPU-side waits happen inside the
queue, not on any thread.

## Why acquire and present stay binary

The swapchain functions predate timeline semaphores and accept only binary ones: the semaphore of
`vkAcquireNextImageKHR` must be binary (`VUID-vkAcquireNextImageKHR-semaphore-03265`), and so must every wait semaphore
of `vkQueuePresentKHR` (`VUID-vkQueuePresentKHR-pWaitSemaphores-03267`). So step 12 has both kinds: binary semaphores
at the two ends of the frame where the presentation engine is involved, one timeline semaphore for everything the CPU
needs to know about the GPU's progress.

## 1. Enable the feature

<Step file="12_timeline" region="pick-device" />

Timeline semaphores are core since Vulkan 1.2, and every Vulkan 1.2+ device must support the `timelineSemaphore`
feature. Supported is not enabled: like every feature, it has to be switched on in `VkPhysicalDeviceVulkan12Features`
when the device is created. The picking loop checks it anyway, the same way it checks dynamic rendering and
synchronization2.

## 2. Create the counter

<Step file="12_timeline" region="timeline-semaphore" />

A semaphore is binary unless its create info carries a `VkSemaphoreTypeCreateInfo` with `TIMELINE`. The initial value 0
means "no frame has completed yet"; frames are therefore numbered from 1.

## 3. The binary semaphores that remain

<Step file="12_timeline" region="binary-semaphores" />

Exactly the binary semaphores of step 10: `image_available` per frame in flight, `render_finished` per swapchain image.
What is gone is the fence, as the per-frame resources show:

<Step file="12_timeline" region="frame-resources" />

## 4. Wait for frame n - F

<Step file="12_timeline" region="wait-timeline" />

Frame *n* uses slot `(n - 1) % F`. The last frame that used that slot is *n - F*, and when the counter has reached
*n - F*, that frame's command buffer and its `image_available` are free. So the CPU waits for "counter ≥ n - F" with
`vkWaitSemaphores`; `VkSemaphoreWaitInfo` accepts only timeline semaphores (`VUID-VkSemaphoreWaitInfo-pSemaphores-03256`).
The first *F* frames have nothing to wait for.

Notice what is missing compared with step 10: no reset. The fence ritual of the first triangle, "reset only after a
successful acquire, or the next wait hangs", has no counterpart, because a wait does not change the counter.

## 5. Signal frame n

<Step file="12_timeline" region="submit" />

One batch, three semaphore operations:

- **wait** on `image_available` (binary) at the stage `BLIT`. Rendering into the offscreen image does not need the
  swapchain image, so it may run before the presentation engine has released it; only barrier 2 and the blit wait.
  That holds only because no barrier in front of the rendering has `BLIT` in its source stage: a barrier whose first
  scope overlaps the wait's stage chains behind the wait, and so does everything it holds back. The
  [barriers lesson](lesson:barriers-and-layouts#2-the-five-barriers) shows how step 12 keeps it that way. That is the
  stage-mask precision of the [first lesson](lesson:fences-and-semaphores#semaphores-one-queue-operation-tells-another);
  whether it buys time on a given machine is a measurement, and on the course machine it did not (same lesson);
- **signal** `render_finished` (binary) at `BLIT`, for the present;
- **signal** the timeline with value *n* at `ALL_COMMANDS`: the counter becomes *n* once everything in the batch, and
  everything submitted before it on the queue, has completed. The value of a binary semaphore operation is ignored.

The fence argument of `vkQueueSubmit2` is now null. Since frame numbers grow by one per submission, every signal is
greater than the last one: the rule "a timeline only grows" is kept by construction.

## 6. The end

<Step file="12_timeline" region="cleanup" />

The timeline tells when *our* work is done: waiting for the last frame's number covers every submission. Destroying the
swapchain, though, also requires the presents to be finished (`VUID-vkDestroySwapchainKHR-swapchain-01282`), and the
counter knows nothing about them. So `vkDeviceWaitIdle` stays: it waits for queue work, the presents' queue operations
included; it does not wait for the presentation engine. Present fences, which exist to know when a present's
resources can be released, are part of the [next lesson](lesson:swapchain-recreation).

the rest is identical in C++. With synchronization validation on, as in
this run (`VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true` and `VK_KHRONOS_VALIDATION_SYNCVAL_SHADER_ACCESSES_HEURISTIC=true`,

(shortened):

```text

Frame 3: slot 0, the CPU waits until the counter reaches 2, the submit will signal 3
[timing] frame 3: the counter read after the wait: 2
```

With three (`--frames 3`) the CPU runs up to three frames ahead (shortened):

```text
Frame 1: slot 0, no earlier frame used this slot, the submit will signal 1
Frame 2: slot 1, no earlier frame used this slot, the submit will signal 2
Frame 3: slot 2, no earlier frame used this slot, the submit will signal 3
Frame 4: slot 0, the CPU waits until the counter reaches 1, the submit will signal 4
[timing] frame 4: the counter read after the wait: 3
```

At the exit the counter equals the number of submitted frames in every run: each frame added exactly one.

## Beyond one queue

The frame loop uses only a sliver of what a timeline can do. With several queues, one timeline per queue turns
"wait for that upload" or "wait for that simulation step" into "wait for value *n*", and a wait may be submitted
before the work that will signal it. The [queue-sync interactive](lab:queue-sync) has a scenario for exactly that,
*Async compute + timeline*: remove the wait of the second simulation step and see it overwrite particles the draw is
still reading.

## Underneath

- A timeline semaphore maps naturally onto how GPUs report progress: a 64-bit value in memory that the command
  processor writes when work completes, and that a waiting queue or the host compares against. On Windows the driver
  model has such progress counters of its own (the same idea as D3D12 fences), and Vulkan can import a D3D12 fence
  handle into a `VkSemaphore` (`VK_KHR_external_semaphore_win32`).
- A binary semaphore carries extra state (signaled or not, consumed by one wait). What the spec requires is only that
  the swapchain's acquire and present take binary semaphores (the VUIDs above); it gives no reason, and we do not
  guess one.
- Waiting on the host with `vkWaitSemaphores` is the same kind of host wait as `vkWaitForFences`: the driver lets our
  thread sleep or spin until the value is reached. The frame rate does not change by switching; the bookkeeping does.
